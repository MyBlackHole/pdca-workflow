# rdbcomm 与 aio-speed 独立 mTLS 配置设计（草案）

## 现状

公共握手层支持客户端显式传递 mTLS 开关与算法，但工具高层仍通过共享安全配置读取。共享配置适合统一部署策略，不适合两个工具在同一环境中采用不同 TLS 策略。

## 待确认的配置组织

### 方案 A：同一配置文件、独立 section（推荐）

在既有配置文件中使用 `[rdbcomm]`、`[rdbcommd]`、`[aio-speed]` 与 `[aio-speedd]` section，分别提供 `mtls_enable` 与 `tls_algorithm`；证书路径和 `ca_cn` 继续沿用现有共享 TLS 配置。环境变量只作为各工具对应配置的覆盖层。

优点是部署文件集中、工具边界清晰、可继续复用现有配置加载器；缺点是需要定义 section 与兼容优先级。

### 方案 B：每个工具独立配置文件

由 rdbcomm 和 aio-speed 分别加载自己的配置文件。

优点是隔离最强；缺点是新增配置路径管理和运维文件，可能与现有 `RDB_CONFIG` 机制重复。

### 方案 C：仅新增 CLI 参数

通过命令行传递 mTLS 开关和算法。

优点是显式；缺点是长期运行工具和多层调用不适合，且用户明确提出“配置独立”。

## 初步建议

采用方案 A：沿用现有配置文件和加载器，通过四个独立 section 形成工具级配置对象，再传入客户端/服务端握手配置；保留环境变量覆盖，但每个工具使用自己的变量命名空间。工具只配置 mTLS 开关与具体算法名，不再使用 `CLASSIC` 这种抽象算法名。

## 算法命名

配置和 help 使用具体 TLS 算法名：`TLS_SM4_GCM_SM3`（国密，默认）与 `TLS_AES_256_GCM_SHA384`（经典 AES）。握手内部枚举也应改为对应具体算法名，避免 `RPC_HS_ALG_CLASSIC` 造成歧义；协议字段仍保持 uint16，不增加字段。
