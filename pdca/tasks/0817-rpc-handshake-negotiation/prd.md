# PRD — RPC 层自定义握手包协商（单端口加密/明文并存）

## 问题陈述

- **现状**: RPC 层（aio-speed↔aio-speedd）在 `sec_tls_enabled()` 开启时，连接建立后**直接** TLS 握手（`rpc-io.cpp:260` connect_server、`rpc-server.cpp:199` StartRPCServiceWoker），即"端口即模式"——TLS 一开，所有连接强制 TLS，无加密/明文并存能力，也无法在连接级按配置协商。
- **目标**: 对齐设计文档 §5"单端口协商（NBU 实证模型）"：同一服务端口同时服务加密与非加密连接；客户端 connect 后先发**独立专用协商头**（magic+版本+capability），服务端响应能力，客户端按配置与双方能力决定**同连接内升级 TLS（国密）或保持明文**；配置变更不重启，仅影响新连接。
- **差距**: RPC 层当前无任何协商层；帧格式为 4 字节长度前缀 + msg_base_t（uiMT/uiLEN），无 capability 扩展位；T0253 父任务拆解的 6 个子任务均未覆盖 RPC 层协商（T0254 后端 vtable、T0255 keygen、T0256 配置、T0257/0258 SBT、T0259 oss）。

## 解决方案

在 RPC 连接建立路径（`connect_server` / `StartRPCServiceWoker`）的 TCP 建立之后、TLS 握手之前，插入**独立专用协商层**：

1. **客户端**（aio-speed）：`connect()` 成功后发送协商请求头 `NEGOTIATE_REQ`（magic `AIO-NEG1` + 版本 + 本端能力位图：加密开关、国密就绪、常规就绪、协议版本），等待服务端 `NEGOTIATE_RESP`（magic + 版本 + 服务端能力位图 + 结果码）。
2. **服务端**（aio-speedd）：`accept()` 后先读协商头。识别到协商 magic → 回能力响应；未识别到（存量明文客户端，超时后判定）→ 按不要求加密处理（存量兼容）。
3. **判定**（客户端侧，连接级）：读取**本工具**的传输加密开关与算法配置（每工具配置键 + 命令行参数覆盖 + 全局兜底，见实现决策）：
   - **开关决定是否加密，算法决定套件**：开关关闭 → 明文路径（发完协商后直接走 RPC 消息帧，不升级 TLS）；开关开启 → 按算法配置选择套件（国密 SM 或常规），同连接升级 TLS
   - 开关开启且双方就绪（按算法配置声明的国密/常规能力）→ 同连接升级 TLS（`tls_cert_client_handshake`，对应套件）
   - 开关开启但目标不支持所选算法 → 作业失败（ENC-004），连接关闭，不降级明文
4. **帧切换**：协商阶段为明文专用头；升级 TLS 后数据面走 **SSL 通道**（保留 `SSL*`，不再 detach）：服务端 woker 路径经 `rpc_ssl_bind(fd, ssl)` 绑定表使既有 `rpc_send`/`rpc_recv` 透明走 `rpc_ssl_send`/`rpc_ssl_recv`（帧协议不变，仅底层换 SSL 记录层）；session 与 rpc_conn 对象显式持有 `SSL*` 并经 `rpc_session_set_ssl`/`rpc_conn_set_ssl` 切换收发分派函数。明文连接不受影响。

**设计要点**：
- 协商头独立于 RPC 消息帧，避免污染 uiMT 类型空间；TLS 升级后协商头不再出现。
- 存量明文客户端（无协商头）→ 服务端默认按"不要求加密"兼容（对齐设计文档 §5"SBT 服务端默认兼容无协商头存量客户端"，此处为 RPC 服务端）。
- 配置开启时若连接未协商（存量 client 直接发 RPC 消息）→ 视为不支持加密，按 ENC-004 拒绝并关闭。

## 用户故事

1. 作为 DBA，我希望开启传输加密后 RPC 链路（Agent↔Worker）为国密 TLS 密文，以便满足等保 L3-CES7-25。
2. 作为管理员，我希望同一 RPC 端口同时服务加密/明文连接且配置变更不重启，以便平滑升级存量环境。
3. 作为运维，我希望加密建立失败时作业明确失败并提示原因，以便不在"以为加密实则未加密"状态运行。

## 实现决策

**不包含具体文件路径或代码片段**。记录：

- **协商头协议**：独立专用二进制头（`AIO-NEG1` magic 4-8 字节 + 版本 1 字节 + 能力位图 1 字节 + 结果码 1 字节 + 校验），与 RPC 消息帧（msg_base_t）无关；TLS 升级后帧格式仍为 rpc_send/recv。
- **能力位图**：bit0=传输加密开关开启、bit1=国密套件就绪（SM4-GCM-SM3 可用）、bit2=常规套件就绪（AES 可用）、bit3=协议版本匹配；预留位。就绪状态按**本工具算法配置**声明（算法配置含 TLS_SM → bit1；含常规 → bit2）。
- **判定逻辑**：`配置开关=关 → 明文`；`=开 ∧ 算法配置为国密 ∧ 双方 bit1 → 升级 TLS(国密套件)`；`=开 ∧ 算法配置为常规 ∧ 双方 bit2 → 升级 TLS(常规套件)`；`=开 ∧ 目标缺对应能力位 → 失败(ENC-004)`。
- **默认算法为国密**：工具与全局均未显式配置算法时，按国密套件（TLS_SM）声明能力并升级（对齐设计文档"国密为默认传输加密算法"）。显式配置常规套件时覆盖为国密之外的常规算法。
- **配置来源（每工具独立）**：每个数据链路工具支持**自己的配置项**控制 TLS 开关与算法（套件字符串），优先级：**命令行参数 > 工具配置键 > 全局 [security] 默认**：
  - 开关：`--tls-enable 0/1` + 工具配置键（如 `[security] rpc_tls_enable`）> 全局 `[security] tls_enable`
  - 算法：`--tls-ciphersuites <套件串>` + 工具配置键（如 `[security] rpc_tls_ciphersuites`）> 全局 `[security] ciphersuites`
  - aio-speed/aio-speedd（单一二进制，本任务实现）；其他工具（dmsbtex/libobk/oss/dm-ftp/FileTransferAgent）在各自子任务（T0257/T0258/T0259）实现同款配置模型
  - 连接建立时读取，配置变更不重启生效；依赖 T0256（`dependencies: [T0256]`）提供全局默认读取接口
- **存量兼容**：服务端协商超时（如 2s）未收到协商头 → 视为明文存量连接；配置开启时明文存量连接按 ENC-004 拒绝。
- **失败语义**：ENC-004 对齐，日志含"传输加密失败"与原因。
- **国密承载**：TLS 升级复用 tls_cert 库（T0254 双后端完成后含国密路径）；本任务只做协商与升级决策，不重复实现后端。

## 验收标准

- [ ] AC-1: RPC 连接建立路径插入协商层，配置关闭时（协商后）走明文存量路径，行为与现状完全一致（rpc_send/recv 帧不变）
- [ ] AC-2: 客户端发送独立协商头（magic+版本+能力位图），服务端识别并回能力响应，抓包可见协商头字节
- [ ] AC-3: 配置开启且双方国密就绪时，同连接升级国密 TLS 握手成功，RPC 消息为密文（抓包验证）
- [ ] AC-4: 配置开启但目标不支持国密 → 作业失败，连接关闭，日志含"传输加密失败"且不降级明文（ENC-004）
- [ ] AC-5: 存量明文客户端（无协商头）连接服务端被识别为明文兼容；配置关闭时该连接正常工作
- [ ] AC-6: 配置开启时存量明文客户端（无协商头）连接被拒绝（ENC-004），日志有原因
- [ ] AC-7: 协商超时（服务端未收到协商头）按明文存量处理，配置开启时按 ENC-004 拒绝
- [ ] AC-8: 配置变更不重启：新连接按新配置协商，存量连接不受影响（连接建立时读配置）
- [ ] AC-9: aio-speed/aio-speedd 各支持独立 TLS 开关与算法配置，优先级**命令行 > 工具键 > 全局默认**：`--tls-enable` 覆盖工具键覆盖全局 `[security] tls_enable`；`--tls-ciphersuites` 覆盖工具键覆盖全局 `[security] ciphersuites`
- [ ] AC-10: 全局 `[security] tls_enable=0` 且工具未显式配置时默认明文；工具配置键或命令行显式开启时强制协商加密（ENC-004 语义不变）
- [ ] AC-11: 算法配置决定协商能力声明：配置含 `TLS_SM`（国密）时协商头声明国密就绪，升级用国密套件；配置为常规套件时声明常规就绪，升级用常规套件；目标不支持所选算法 → ENC-004 失败
- [ ] AC-12: 默认算法为国密：工具与全局均未显式配置算法时，开关开启按国密套件协商升级；显式配置常规套件后按常规套件协商升级
