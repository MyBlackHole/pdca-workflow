## 1. 设计目标与范围

设计一套**自研完整备份产品**，覆盖五大子系统：客户端、服务端、存储、调度、恢复。
本设计为顶层架构（非代码实现），每个关键决策回溯到调研证据（`[R:x.y]` 标注，映射
`research-report.md` 章节）或既有 RPC 能力。

### 1.1 非目标
- 不做多租户/企业计费
- 不做跨公网海量节点集群（优先单机/小规模多机）
- 不做数据加密于客户端之外的第二层合规体系（但保留扩展点）

## 2. 系统总体架构

### 2.1 组件图

### 2.2 数据流（备份一次作业）

1. **枚举**：客户端文件扫描器遍历目录树，产出文件清单（路径、大小、mtime、权限）。
2. **分块**：按 CDC（内容定义分块）把文件切成变长块，计算块指纹（hash）。
3. **去重查表**：客户端携带块指纹列表，服务端索引查询是否已存在 → 仅上传新块
   `[R:1.2][R:1.3]`。
4. **压缩+加密**：新块先压缩再加密（先压缩后加密保证去重命中率）`[R:1.2]`。
5. **上传**：分片并行上传（复用 PAR 并发读、RANGE 区间语义反向）`[R:4]`。
6. **提交**：全部块写完后，以 manifest（快照元数据）原子提交，生成新版本 `[R:1.2]`。
7. **索引**：更新块索引与快照表 `[R:2.4]`。

### 2.3 数据流（恢复一次作业）

1. **选快照**：从快照表挑选目标时间点（PITR）`[R:5]`。
2. **解析 manifest**：得到文件→块列表。
3. **并发拉取**：按块 hash 从块池顺序读，用 PAR/RANGE 并发下载重拼 `[R:4][R:5]`。
4. **解密解压**：还原原始块，组装文件，恢复元数据（权限/时间戳）。
5. **校验**：按块指纹与文件级校验确认完整性 `[R:1.3]`。

## 3. 客户端设计

### 3.1 文件扫描器
- **职责**：目录树遍历，输出文件元数据清单；支持 include/exclude 过滤、符号链接策略。
- **关键决策**：复用既有 `--fb-item` 批量目录树枚举（`do_batch_list_dir_tree`）能力；
  扫描与上传分离，扫描结果先落临时清单再调度上传 `[R:1.1]`。
- **增量判定**：用 mtime+size 初筛（对应既有 `load_rsync_meta` 增量机制），
  命中则跳过或进入差分流程 `[R:1.1]`。

### 3.2 分块器（CDC）
- **算法**：内容定义分块（Buzhash/滚动哈希族），块边界随内容确定。
- **收益**：文件头尾增删只影响局部块，跨版本去重稳定 `[R:1.2][R:1.3]`。
- **参数**：平均块大小（如 4MB~1MB 可配），最小/最大块边界钳制，防止极端块。
- **决策依据**：Borg/Restic 均采用 CDC，去重率与重拼开销的平衡点。

### 3.3 去重查表
- **设计**：客户端不持有全量指纹，每次作业把本次块指纹集批量发送服务端查询；
  服务端返回"新块集合"，客户端仅上传新块 `[R:1.3]`。
- **内存**：指纹列表为一次性查询，避免客户端长期持有全局索引 `[R:1.3]`。

### 3.4 压缩与加密
- **顺序**：压缩在前、加密在后（压缩后密文再去重意义已失，故压缩应先于指纹查重，
  即"指纹算在压缩后块"或"压缩后重新指纹"——设计上选择：**先分块→压缩→压缩块指纹→
  查重**，保证去重与加密兼容）`[R:1.2]`。
- **算法**：压缩 zstd（高吞吐可配）；加密 AES-256-GCM（认证加密），密钥独立于
  客户端配置管理（keyfile/口令派生）`[R:1.2][R:1.3]`。
- **可选**：明文模式（去重优先、无密文），配置开关。

### 3.5 上传调度
- **分片**：大块按 1~4MB 分片（multipart），并行上传。
- **并发**：令牌桶限流，避免打满带宽/拖垮服务端 `[R:2.5]`。
- **断点续传**：记录已完成分片集合，中断后从断点继续（对应 RPC 连接重连语义）。

## 4. 服务端设计

### 4.1 网络层
- **模型**：多 Reactor epoll 事件循环 + 线程池（既有 `rpc-epoll` ONESHOT 事件驱动）。
  - 事件循环：接收/读写事件分发 `[R:2.2]`。
  - 业务线程池：块校验、去重查表、写盘在独立线程执行，避免阻塞事件循环
    `[R:2.2][R:2.5]`。
- **传输**：复用 PAR（并发块读）+ RANGE（区间推流）协议族；备份方向新增
  PUT/PAR_WRITE 类消息，恢复方向复用既有下载消息 `[R:4][R:1.1]`。

### 4.2 接收与校验
- **接收**：分片流式写入接收缓冲，校验分片长度与序号。
- **校验**：按压缩块指纹（hash）在写入前验证传输完整性；写入后 fsync 保障持久性
  `[R:2.4]`。
- **错误处理**：单分片失败仅重传该分片，不整块重传。

### 4.3 存储引擎
- **布局**：仿 Borg/Restic 的
  `keys/ data/ snapshots/ index/ config` 仓库布局 `[R:1.3]`。
- **写入策略**：数据块**顺序追加**写（append-only log 式），后台 compact 回收孤儿块
  `[R:2.4][R:2.5]`。
- **校验**：块内容自带 checksum，read 时懒校验；周期性 `check --read-data` 全量校验
  `[R:1.3]`。
- **随机写规避**：避免原地更新块，快照/索引以新版本覆盖提交（manifest 原子提交）
  `[R:1.2][R:2.4]`。

### 4.4 索引服务
- **数据模型**：
  - 块索引：hash → 块文件位置/引用计数（refcount）。
  - 快照表：snapshot_id → manifest（文件树 + 权限时间戳 + 块列表）`[R:1.3]`。
  - 任务表：作业状态（0 未初始化/1 进行中/2 完成，对应既有 `proc-status` 语义）。
- **持久化**：索引入独立元数据库（SQLite/自定义键值），与数据块存储分离 `[R:2.4]`；
  与既有 `--meta` 文件、`--meta-find-range` 精准查询能力衔接。

### 4.5 并发控制
- **写入并发**：令牌桶限制并行写入连接数，保护磁盘顺序写吞吐 `[R:2.3][R:2.5]`。
- **refcount**：多快照共享块，删除快照只减引用；引用归零的块进入回收候选。

## 5. 存储设计

### 5.1 存储介质选择
- **主选**：本地文件系统（data/ 目录）承载块池，顺序写友好。
- **扩展**：REST/S3 后端抽象（Restic 模式），便于切对象存储 `[R:1.3][R:1.4]`。
- **快照源**：可选用 ZFS send/recv 或 LVM 快照做源卷一致性拍摄，作为备份触发点
  `[R:1.8][R:1.9]`。

### 5.2 版本管理
- **快照即版本**：每次成功备份提交一个新 snapshot_id；manifest 只读、不可原地改。
- **保留策略**：按时间/数量/大小保留快照（仿 Borg prune），自动清理过期快照
  `[R:1.2][R:1.6]`。

### 5.3 一致性保障
- **原子提交**：所有块落盘并 fsync 后，再写 manifest（先数据后元数据）。
- **崩溃恢复**：重启时扫描未完成作业，清理半写块；manifest 未提交则该作业整体回滚
  `[R:1.2]`。

## 6. 调度设计

### 6.1 备份策略
- **全量/增量**：首备全量，后续走增量（mtime+size 初筛 + CDC 去重）`[R:1.1][R:1.2]`；
  支持定期全量合并（既有 `--backup-merge` 能力）`[R:1.1]`。
- **级联增量**：可选 dump 层级策略（Amanda 思想），控制增量链长度 `[R:1.7]`。

### 6.2 任务队列
- **模型**：中心调度器持任务队列 + 并发度上限；每个作业有状态机
  （枚举→查重→上传→提交→完成）。
- **优先级**：高优小作业可插队；带宽/IO 限流按作业共享配额。
- **调度参考**：Director 集中调度（Bacula）、任务队列 + 限流（Rclone 并发控制）
  `[R:1.6][R:1.4][R:2.4]`。

### 6.3 断点续传
- 作业进度（已上传分片、已完成块）周期持久化；中断后从断点恢复。
- 依赖既有 `--fb-progress` 进度文件与 `--proc-progress` 任务状态查询。

### 6.4 节流
- 客户端令牌桶 + 服务端写入配额双端限流；低谷窗口批量执行。

## 7. 恢复设计

### 7.1 恢复类型
- **文件级恢复**：从 manifest 取指定文件/目录的块列表，重拼还原 `[R:5]`。
- **整机/全量恢复**：恢复完整文件树，重建权限、时间戳、owner（保留元数据）。
- **点时间恢复（PITR）**：选择目标 snapshot_id（或其增量链基线），按快照还原。
- **增量链重放**：若为 delta 链存储，需顺序重放多个 delta（Duplicity 教训：链长时
  慢）`[R:1.5]` → 设计上默认 CDC 快照型，避免长链重放。

### 7.2 恢复并发
- 复用既有 PAR/RANGE 并发下载：多连接分片拉取 + 并发块读，恢复吞吐最大化
  `[R:4][R:1.1]`。
- 恢复目标写盘同样顺序化，避免碎片化。

### 7.3 恢复验证
- 还原后按块指纹 + 文件级 checksum 校验（`restore-file`/`restore-meta` 能力扩展）。
- 可选"恢复演练"作业：定期随机抽一个快照做 dry-run 恢复校验，确保可恢复性。

## 10. 风险与演进

- **去重率依赖 CDC 参数**：块过大去重率低、块过小索引膨胀 → 提供可配默认值 + 基准。
- **加密与去重的冲突**：密文不可再去重 → 已通过"压缩后指纹查重"规避 `[R:1.2]`。
- **索引扩展性**：PB 级仓库需分片索引/数据库 → 预留索引服务独立部署。
- **多机横向扩展**：Bacula 式控制面/数据面分离作为演进方向 `[R:1.6]`。
- **加密性能**（POC 实证）：gpg 外置加密开销显著 → 内置 AES-256-GCM 为必须。
