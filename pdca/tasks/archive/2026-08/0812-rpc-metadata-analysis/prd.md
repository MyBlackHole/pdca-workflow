# rpc/rpc-metadata.c 海量文件元数据管理分析 — 规格文档

## 问题陈述

- **现状**：元数据管理实现分布在 `rpc/rpc-metadata.c`、`rpc/rpc-metadata.h` 和 `libs/lmdb_dict.c`，已有基本测试与调用方，但缺少面向海量文件规模的整体说明。
- **目标**：输出一份可复核的中文分析文档，解释数据模型、生命周期、读写路径、事务与游标、复杂度、容量模型、并发/一致性边界和主要风险。
- **差距**：现有 README 主要描述命令用法，不能支持维护者判断海量元数据场景下的瓶颈、失效模式和改进优先级。

## 解决方案

以源代码为主要证据，补充现有测试和调用方配置，按 PDCA 组织文档：Plan 定义分析目标，Do 汇总实现事实，Check 对结论进行静态复核，Act 给出分级建议与后续验证项。文档明确区分“当前实现事实”“分析推断”“建议动作”。

## Seam 分析

### 测试接缝

本任务为 research/documentation，不新增代码测试。复核接缝为现有 `rpc/tests/metadata.cpp` 与元数据 API；容量与性能结论以静态证据和可执行验证建议呈现。

### 验收可测性

每条关键结论都能回溯到源文件、函数或配置；文档覆盖新增、查询、删除、目录遍历、事务提交、重启恢复和容量边界；未实测的性能数字不得写成事实。

## 用户故事

1. 作为维护者，我想知道一个文件的元数据如何落库和被定位，以便评估数据规模增长的影响。
2. 作为性能/可靠性负责人，我想看到复杂度、容量和一致性风险，以便安排后续验证和改造。

## 实现决策

- 产物为仓库内 Markdown 分析文档。
- 分析范围包括 `rpc/rpc-metadata.c` 及其直接依赖/调用证据，不修改业务代码。
- 结论按事实、推断、风险、建议分层，并标注源码位置。

## 测试决策

- 使用静态源码复核：结构体、键比较器、LMDB API、事务包装、游标遍历和调用方 map size。
- 使用现有 `rpc/tests/metadata.cpp` 作为行为先例，不把其小规模通过等同于海量规模验证。

## 验收标准

- [ ] AC-1: 文档说明键和值的数据布局、inode 分配与持久化方式，并能回溯到具体源码位置。
- [ ] AC-2: 文档覆盖增删改查、路径解析、目录范围查询/遍历和事务生命周期。
- [ ] AC-3: 文档分析海量文件下的时间复杂度、空间组成、map size、事务批量和 cursor 行为，并标出未实测项。
- [ ] AC-4: 文档列出至少一致性、并发、容量、异常恢复、路径/名称边界方面的风险及优先级建议。
- [ ] AC-5: 完成 Check 复核，确保文档中的源码引用、结论分层和 PDCA 记录一致。

## 范围外

- 不修改 `rpc/rpc-metadata.c` 或 LMDB 封装。
- 不进行大规模基准测试、生产数据迁移或容量承诺。
- 不分析与元数据存储无直接关系的 RPC 协议细节。
