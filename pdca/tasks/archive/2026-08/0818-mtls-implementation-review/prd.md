# 审查最近 mTLS 实现方案并提出优化建议

## 问题陈述

- **现状**：最近变更为 rpc 与 rdbcomm 增加了统一的首阶段明文协商、获取时间、mTLS 升级和应用数据帧处理；同时补充了 RPC 应用路径测试握手。当前需要确认实现是否满足已确认的协议约束和备份复制传输加密基线。
- **目标**：输出一份基于代码、提交记录、测试结果和需求文档的审查结论，明确已满足项、缺陷/风险、证据和可执行的优化建议。
- **差距**：尚未系统核对两个组件的状态机对称性、TLS 密文数据面、证书 ca_cn/算法选择、配置强制语义、错误可观测性及测试覆盖。

## 解决方案

对最近 mTLS 相关提交进行静态代码审查和可复现验证，逐项映射到备份复制传输加密文档中适用于 RPC/rdbcomm 的要求及当前会话确认的补充约束。审查报告按 P0/P1/P2 分级，给出证据、影响、最小优化方向和后续验证建议；本任务不直接修改代码。

## Seam 分析

### 测试接缝

- 协议接缝：首阶段握手解析、响应和状态转换。
- TLS 接缝：SSL 握手完成后的读写、关闭和错误传播。
- 证书接缝：ca_cn 目录选择、服务端算法配置、客户端证书验证。
- 集成接缝：RPC/rdbcomm 客户端与服务端的真实连接及时间功能。
- 回归接缝：已有应用数据帧、异常帧和工具测试。

### 验收可测性

审查结论必须对每一项给出“满足/部分满足/不满足/无法证明”，并绑定代码或测试证据；建议必须能转化为独立修复或测试任务。

## 用户故事

1. 作为传输加密实现维护者，我想知道最近修改是否正确保持 TLS 密文数据面，以便避免 mTLS 握手后意外回退到裸 fd。
2. 作为 RPC/rdbcomm 使用者，我想确认两套协议和配置语义一致，以便时间获取、明文和强制 mTLS 场景行为可预测。
3. 作为运维人员，我想获得明确的证书/算法/握手失败结论，以便定位加密作业失败原因。

## 实现决策

- 审查范围覆盖最近的握手协议、RPC、rdbcomm、tls_cert、相关测试和配置使用。
- 以用户最终确认作为实现约束：默认明文；服务端启用 mTLS 即强制；客户端不新增参数；握手结构体持有读写指针；mTLS 后使用密文 I/O；不兼容旧版协议。
- 以外部基线文档为需求映射来源，但区分其超出本任务范围的 SBT、UI、GMSSL/国密专项和存储加密内容，不将未实现的外部范围误判为 RPC/rdbcomm 缺陷。
- 证书身份重点核查 ca_cn 是否被正确解释为客户端用于匹配服务端 CA/证书目录的标识，以及服务端多证书和算法选择是否一致。

## 测试决策

- 复核已有单元、socketpair、真实进程和业务路径测试的行为覆盖。
- 对关键静态不变量执行检索/构建/测试：mTLS 应用阶段不得绕过 SSL；两组件首阶段状态机和错误码语义应一致；强制 mTLS 不得降级。
- 如现有证据不足，报告中明确列出应补充的测试，不在本任务中实施。

## 验收标准

- [ ] AC-1: 审查报告覆盖最近 mTLS/握手相关变更，并对 RPC、rdbcomm、tls_cert、配置和测试分别给出结论。
- [ ] AC-2: 报告逐项核对首阶段三场景：仅获取时间并关闭、协商 mTLS 后进入第二阶段应用帧、未知数据帧返回明确错误。
- [ ] AC-3: 报告证明或指出 RPC/rdbcomm 在协议状态机、时间功能、默认明文、服务端强制 mTLS 和失败不降级语义上的一致性。
- [ ] AC-4: 报告核查握手结构体读写指针、SSL 所有权、mTLS 后密文 I/O、部分读写、超时、关闭和错误传播风险。
- [ ] AC-5: 报告核查服务端算法配置、多证书选择、ca_cn 语义及客户端验证链，并指出身份或配置歧义。
- [ ] AC-6: 报告将实现映射到备份复制传输加密基线中适用的 RPC/rdbcomm 要求，并明确超出当前范围的条款。
- [ ] AC-7: 报告给出按 P0/P1/P2 排序的优化建议，每项包含影响、最小修改方向和验证方式。
- [ ] AC-8: 审查过程产出可复核证据，包括提交/工作树快照、静态检查结果和相关测试结果；不引入代码改动。

## 范围外

- 不实现旧版协议兼容。
- 不审查或实现 SBT、UI、作业配置传递、存储加密和完整国密工具链，除非用于说明外部基线与当前实现的边界。
- 不替代后续 T0307 的补测与业务回归执行任务。
