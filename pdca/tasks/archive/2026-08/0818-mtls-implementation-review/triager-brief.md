# Triage Brief

## 分类

- category: enhancement
- scenario_type: review
- priority: P1
- source: 用户要求审查最近 mTLS 实现方案修改，并核对备份复制传输加密基线

## 问题摘要

审查最近 rpc/rdbcomm 首阶段明文协商、时间获取、mTLS 升级及应用数据帧改造，判断实现是否满足当前确认的协议要求以及备份复制传输加密设计文档中适用于 RPC/rdbcomm 的约束，并提出按优先级排序的优化建议。

## 已知边界

- 审查对象以最近 mTLS/握手相关提交及其测试为主。
- 当前协议不要求旧版协议兼容。
- 默认明文；服务端配置启用 mTLS 时必须进行 mTLS，不允许静默降级。
- 客户端证书按服务端证书的 ca_cn 目录区分；服务端支持配置算法类型，并据 ca_cn 选择证书。
- mTLS 握手完成后，应用数据必须继续通过 TLS 密文读写接口处理。
- 不在本任务中直接修改实现；仅形成证据化审查结论和优化建议。

## 初步审查问题

1. 首阶段三种场景（仅获取时间后关闭、协商并进入 mTLS 后进入应用帧、无法识别帧返回明确错误）是否在 RPC 与 rdbcomm 中完全一致。
2. mTLS 的 SSL 对象、读写指针、关闭和错误路径是否存在裸 fd 绕过、资源泄漏或状态错乱。
3. ca_cn、服务端算法配置、多证书选择和客户端验证语义是否吻合实际证书身份。
4. RPC/rdbcomm 客户端是否复用既有参数，配置开启/关闭和失败语义是否符合“不新增参数、开启即强制”。
5. 测试是否覆盖真实 RPC/rdbcomm、时间功能、异常帧、证书缺失、握手超时、不同算法及全量业务回归。
