# rdbcomm 与 RPC 明文握手协商 mTLS 算法及统一时间协议

## 问题陈述

- **现状**: RPC 已有获取时间入口，但 RPC 与 rdbcomm 的连接建立和 TLS 处理路径不共享统一的明文握手协商协议；rdbcomm 也没有等价的获取时间能力。
- **目标**: 两个协议栈使用同一套明文握手协商报文和 mTLS 算法能力判定，在连接级选择明文或 mTLS；同时保持 RPC 获取时间兼容，并为 rdbcomm 增加协议一致的获取时间请求/响应。
- **差距**: 需要抽取/复用协议定义与判定逻辑，接入两套客户端/服务端连接路径，处理 TLS 数据面生命周期，并补充跨模块协议与回归测试。

## 解决方案

统一第一阶段使用独立明文协议，位于 TLS/mTLS 和 APP 原始数据帧之前，并由 rpc/rdbcomm 共用。第一阶段明确处理三类场景：获取时间并返回后关闭连接；协商需要 mTLS 时由服务端按配置算法类型选择证书并返回证书 CN，客户端按 CN 选择本地证书后完成升级，再进入第二阶段 APP 原始数据帧；无法识别的数据帧返回明确错误。默认传输模式为明文，只有显式配置要求 mTLS 时才进行算法能力协商与升级；能力不匹配或客户端找不到服务端指定证书时不得静默降级。

## 用户故事

1. 作为部署管理员，我希望 rpc 和 rdbcomm 通过同一明文握手协商 mTLS 算法，以便两类链路拥有一致的安全策略。
2. 作为兼容性维护者，我希望明文路径和已有 RPC 获取时间调用继续工作，以便升级不破坏存量功能。
3. 作为 rdbcomm 使用者，我希望能以与 RPC 一致的协议获取服务端时间，以便时间校验逻辑可复用。

## 实现决策

- 统一第一阶段协议由 rpc/rdbcomm 共用，独立于各自 APP 原始数据帧。
- 第一阶段结果分为：时间响应后关闭、mTLS 升级后进入 APP 帧、未知帧明确错误。
- mTLS 响应必须携带服务端选择的证书标识；客户端按标识选择证书，找不到则报错关闭。
- 服务端算法类型为配置项，协商响应返回选定的 `ca_cn`；客户端沿用 `cert_dir/<ca_cn>/` 规则选择证书材料。
- 第一阶段确定 `ca_cn` 后，TLS 阶段由客户端显式加载该目录对应证书；不再依赖证书选择回调，TLS 阶段只执行证书链、签名和 CN 校验。
- mTLS 握手成功后必须保留 SSL/TLS 连接对象，第二阶段 APP 帧全部通过密文通道收发；禁止 detach 后回到原始 fd，连接关闭时必须完成 TLS 关闭和资源释放。
- 默认明文；客户端显式请求 mTLS，或服务端 mTLS 配置开启时进入算法能力协商；服务端开启时 mTLS 为强制模式，失败不降级。
- 时间能力使用新的统一协议；TIME 只允许第一阶段完成后返回并关闭连接，不进入第二阶段，也不兼容旧时间 wire 协议。既有 `rpc_get_time` 保留 API 入口但改为调用新 TIME 协议。

## 测试决策

- 以外部 wire 行为和连接结果为主，不绑定内部函数实现。
- 单元测试覆盖编解码/判定；集成测试覆盖两模块的明文协商、mTLS 升级、失败不降级和时间收发；保留既有 RPC 全量回归。

## 验收标准

- [ ] AC-1: 运行统一协商协议编解码测试，rpc 与 rdbcomm 对相同固定头得到相同 magic、版本、operation、payload 长度、能力字段和结果码。
- [ ] AC-2: 运行 TIME 集成测试，rpc 与 rdbcomm 均收到统一格式的时间响应，随后服务端关闭连接且不进入 APP 帧。
- [ ] AC-3: 运行默认明文 NEGOTIATE 集成测试，rpc 与 rdbcomm 均收到“明文继续”结果并完成各自原始 APP 数据帧收发。
- [ ] AC-4: 运行 mTLS 算法协商测试，在客户端请求、服务端允许且能力交集满足时完成 TLS/mTLS 升级，并在升级后完成 APP 数据收发。
- [ ] AC-5: 运行多证书 mTLS 测试，服务端按配置算法类型选择 `ca_cn` 并返回，客户端按 `cert_dir/<ca_cn>/` 选择对应证书完成握手并完成 APP 收发。
- [ ] AC-6: 运行 mTLS 密文数据面测试，抓包确认握手后的 APP 数据不以明文出现，并验证代码路径未 detach SSL 后使用原始 fd；连接关闭完成 TLS 资源释放。
- [ ] AC-7: 运行客户端缺少服务端指定证书、能力不匹配、服务端不允许、坏包、半包和超时测试，连接收到明确错误并关闭，禁止回退为未声明的明文连接。
- [ ] AC-8: 运行未知 operation 测试，服务端返回明确协议错误并关闭连接；不要求兼容旧客户端直发 APP 帧。
- [ ] AC-9: 运行 rdbcomm 时间协议测试，得到与 RPC 相同格式、字节序和语义的时间响应。
- [ ] AC-10: 运行既有 RPC 时间回归测试，`rpc_get_time` 的调用方式和成功/失败语义保持兼容。
- [ ] AC-11: 运行配置和全量回归测试，默认明文、显式 mTLS、rpc/rdbcomm 两端判定结果和既有业务行为均符合协议约定。
- [ ] AC-12: 运行服务端算法配置测试，算法类型改变时服务端选择的 `ca_cn` 和 mTLS 套件随配置生效，未匹配到 CN 目录时返回明确错误。
