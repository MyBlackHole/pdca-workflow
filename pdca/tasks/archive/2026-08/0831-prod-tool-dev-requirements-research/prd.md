# 调研生产级别工具开发应具备的要求与条件

## 背景

用户提出发起调研任务：系统性梳理“生产级别的工具”在开发过程中应具备的要求与条件。该调研将作为后续工具类项目立项、设计、验收与演进的依据，需具备全面性、权威性与可落地性，避免经验性、碎片化罗列。

“生产级别”隐含：面向真实用户/真实环境、可长期维护、可规模化部署、故障可诊断可恢复、变更可控可回滚、安全合规。

## 目标

产出一份结构化的调研报告 `research-report.md`，系统回答“一个工具要达到生产级别，需要在哪些维度满足哪些要求、具备哪些条件”，并给出分级（基础/进阶/卓越）与可直接复用的检查清单。

## 范围界定

- **研究对象**：广义“工具”——包括但不限于 CLI 工具、开发者工具、运维工具、自动化脚本平台化后的工具、AI 辅助工具、后台服务配套工具。需在调研中明确分类并指出差异。
- **视角**：以“工具开发者/提供方”视角为主，兼顾“使用者/运维方”视角。
- **来源优先级**：官方文档与权威工程实践 > 知名开源生产级工具案例剖析 > 行业标准与规范 > 二手转述。

## 调研维度（初拟，Grill 后收敛）

1. **功能与正确性**：需求边界、输入校验、幂等性、事务性、数据一致性
2. **可靠性与可用性**：容错、重试、降级、熔断、备份恢复、SLA/SLO
3. **安全性**：认证鉴权、权限最小化、数据保密与完整性、供应链安全、漏洞响应
4. **可维护性与可演进性**：架构分层、模块化、代码规范、版本策略、兼容性与迁移
5. **可观测性**：日志、指标、追踪、告警、审计
6. **性能与资源**：性能基线、压测、资源隔离与限流、成本
7. **兼容性与可移植性**：多平台/多环境、多版本依赖、配置管理
8. **测试与质量保障**：单元/集成/E2E、回归、混沌、覆盖率门禁
9. **文档与用户体验**：安装部署文档、API/CLI 帮助、示例、错误提示可用性
10. **发布与运维**：CI/CD、灰度/回滚、变更管理、依赖管理、生命周期
11. **合规与治理**：许可证、数据合规、审计留痕、开源治理（如适用）
12. **组织与流程条件**：团队能力、流程规范、外部依赖与生态

## 验收标准

- [ ] AC-1：调研报告包含“调研目标、方法、发现、结论与建议、参考资料”五节，结构符合 `ontology:domain/skill-research` 要求
- [ ] AC-2：覆盖上述 12 个维度中的至少 9 个核心维度（1-10 为核心），每维度给出“基础要求（Must）/进阶要求（Should）/卓越实践（Excellent）”分级
- [ ] AC-3：每条关键结论附至少一条可复核验证途径（权威来源链接、知名工具案例 file:line 式引用、标准编号）或明确标注“待验证假设”与置信度
- [ ] AC-4：产出独立的 `checklist.md`（或报告附录）——生产级工具就绪检查清单，条目可直接用于立项评审与发布门禁
- [ ] AC-5：产出成熟度分级模型（如 L1 可用 → L2 可靠 → L3 可运维 → L4 可规模化），每级有明确判定条件
- [ ] AC-6：报告经 `register-evidence` 登记为不可变证据

## 非目标

- 不针对某一具体工具做深度竞品分析（仅作案例佐证）
- 不产出可执行代码，仅产出调研报告与清单
- 不涉及具体业务域的合规细节（如金融/医疗强监管），仅给出通用合规框架

## 关联本体节点

- `ontology:concept/pdca-task`
- `ontology:domain/skill-research`
- `ontology:concept/pdca-architecture`（工具作为可复用能力单元）

## 风险

- 范围过宽导致泛化空洞 → 通过 Grill 收敛边界与优先级，聚焦“通用 + 2-3 类典型工具差异”
- 来源权威性不足 → 坚持 primary source 优先，二手结论标注置信度
- 清单落地性差 → 清单条目需可判定（是/否/度量值），避免模糊描述

## 开放问题（待 Grill）

- Q1：调研对象是否需聚焦某几类工具（如仅 CLI/开发者工具）还是保持广义？
- Q2：是否有对标的标杆工具或团队规范希望纳入？
- Q3：输出是否需包含本团队（PDCA Workflow / CDM 相关工具）的定制化建议？
- Q4：时限与深度期望：快速全景 vs 深度剖析？
