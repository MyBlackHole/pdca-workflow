# 备份限流/带宽控制实证（场景10）— 规格文档

## 问题陈述

- **现状**: POC 仓库已实证备份引擎大量基础技术（网络时序 01-04、增量/去重/
  加密压缩 05-07、并行分块 08、事件模型+流式 09），但**尚未实证调度子系统
  的节流（限流）原语**。产品 `bwlimit` 模块采用动态阈值窗口限流，但缺少
  自研基础实现的精度/平稳性/并发公平性数据，也缺少与经典令牌桶的对比。
- **目标**: 以基础技术实现为准（POC 原则，单一变量），自研两种带宽控制原语
  ——动态阈值窗口限流（镜像产品 bwlimit 思路）+ 经典令牌桶限流——实测其在
  单线程与多线程下的速率精度、平稳性和并发公平性，给出适用于备份引擎的
  节流设计结论。
- **差距**: 缺少可运行的自研限流原语、可量化的对照数据（平均速率偏差、
  突发幅度、公平性指数），以及"备份流量不挤占业务带宽"的验证依据。

## 解决方案

自研限流库（`lib/bwlimiter.*`）+ 场景程序（`scenarios/10-bandwidth-control/`），
对比两种算法在 3 个验证点下的行为：

1. **动态阈值窗口限流**（产品 bwlimit 思路）：每 `thresh` 字节为一个窗口，
   统计窗口内实际耗时，睡眠 `(已传字节×8/目标速率 − 已耗时)`，并根据耗时
   偏差自适应调整窗口大小（`thresh`）。窗口自适应避免"窗口过大导致单次
   睡眠过长（吞吐锯齿）"和"窗口过小导致频繁唤醒（精度差）"。
2. **令牌桶限流**：以固定速率 `rate` 向桶注入令牌，容量 `burst`；每写
   `buflen` 前取令牌，无令牌则 sleep 到下一个令牌可用时刻。可突发的上限
   由桶容量决定。

验证点：
- V1 速率精度：限定目标速率（如 4 MB/s、32 MB/s），统计整体平均速率
  偏差是否在可接受范围（如 ±5%）。
- V2 平稳性：把传输时间切成小窗口，统计各窗口速率的标准差/最大偏离，
  对比两种算法的抖动（sawtooth 程度）。
- V3 并发公平性：多个线程共享同一限流器（总带宽受限），统计各线程实际
  吞吐的公平性（最大/最小比值或 Jain 公平性指数），并确认**总速率不超
  上限**（并发场景最易超速：各线程独立计时不加锁会各自按目标速率跑）。

## Seam 分析

### 测试接缝
- 限流原语以 `bwlimiter_wait(op, nbytes)` 形式暴露：调用方在"写入前/后"
  调用，内部负责 sleep。测的是外部行为（吞吐、平滑度、公平性），不测内部
  计时细节。
- 基准"未限流"对照组：同样字节流无任何等待，仅测机器写入速度作为上界，
  与限流后对比。

### 验收可测性
- 速率精度：用 `clock_gettime(MONOTONIC)` 计时传输总字节数，算平均速率，
  断言 `|实测 − 目标| / 目标 ≤ 阈值`。
- 平稳性：将传输时间等分 N 段，每段记录传输字节，计算各段速率的标准差。
- 并发公平性：N 线程各传同样总量，记录每线程耗时，算公平指数。

## 用户故事

1. 作为备份引擎设计者，我想要知道动态窗口限流与令牌桶哪个精度更高、
   抖动更小，以便选择节流实现。
2. 作为实现者，我想要一个可复用的自研限流原语（供发送/接收两方向使用），
   以便在网络层接入限流而不改业务代码。
3. 作为运维者，我想要确认多并发备份时总带宽不会超过设定上限、且各任务
   分配公平，以便保证业务带宽不被挤占。
4. 作为评审者，我想要一个可复现的数据集（固定随机种子）和对照结论，
   以便审查限流实现是否满足备份场景要求。

## 实现决策

**不包含具体文件路径或代码片段。**

- 新增模块：
  - `lib/bwlimiter.h/.c` — 自研限流库：两种算法（动态窗口、令牌桶），
    全局限流器 + 每调用方（线程）登记，`bwlimiter_wait` 接口。
  - `scenarios/10-bandwidth-control/main.c` — 场景程序：三档速率 × 两种
    算法 × 单线程/多线程 × 数据量，输出对比表。
  - `scenarios/10-bandwidth-control/README.md` — 原理图 + 实测结论。
- 接口定义（原型级）：
  - `bwlimiter_init(cfg)` / `bwlimiter_destroy()`
  - `bwlimiter_wait(size_t nbytes)` — 写入 nbytes 前调用，内部阻塞至
    允许写入。
  - 多线程共享：单一全局限流器（共享总带宽），内部加锁；并发下总速率
    由锁保护不超上限。
- 技术澄清：
  - 目标速率单位采用 bit/s（与产品 bwlimit 一致），字节流按 ×8 换算。
  - 参考产品 `bwlimit/lib/bandwidth.c` 的动态阈值自适应算法，但自研实现
    不直接复用其共享内存/配置层，保持单一变量。
  - 为公平比较，两种算法使用相同的定时原语（clock_gettime + nanosleep）。

## 测试决策

- 好的测试定义：仅测外部行为——平均速率、速率波动、并发公平性，
  不测内部睡眠逻辑。
- 被测模块：`lib/bwlimiter.c`（两种算法）+ 场景 main 的三项断言。
- 现有测试先例：POC 顶层 `make test` 聚合回归（PASS: N  FAIL: 0 格式），
  各场景输出 `RESULT: ALL PASS`。

## 验收标准

- [ ] AC-1: 单线程下，动态窗口限流与令牌桶限流的整体平均速率均落在目标速率 ±5% 内（覆盖 4 MB/s 与 32 MB/s 两档）
- [ ] AC-2: 单线程下，两种算法均给出抖动度量（分窗速率标准差），且结论可对比（至少一档速率下指出抖动更小的算法）
- [ ] AC-3: 多线程共享限流器（≥4 线程）时，实测总速率不超过目标上限（并发不超速），并给出公平性指数
- [ ] AC-4: 提供"未限流"对照组作为速率上界参考
- [ ] AC-5: 场景程序输出 `RESULT: ALL PASS`，且纳入顶层 `make test` 聚合回归（PASS: 10）
- [ ] AC-6: `README.md` 含限流原理图（动态窗口 vs 令牌桶）、并发共享限流图与实测结论

## 范围外

- 不直接编译/复用产品 `bwlimit` 模块的共享内存与配置层（仅概念对照）。
- 不做真机网络限流实测（socket 发送），本场景以自研原语的字节流计时为准。
- 不做限流参数的运行时动态调整（先固定速率）。
