# PostgreSQL/MySQL 逻辑导出转换 Parquet 性能 POC — 规格文档

## 问题陈述

- **现状**: 已完成 Parquet 格式、类型映射和数据库转换方案调研，但缺少针对 PostgreSQL、MySQL 逻辑导出再转换为 Parquet 的本地可复现实测数据。
- **目标**: 通过 POC 获得 PostgreSQL 逻辑导出到 Parquet 的端到端性能、资源消耗、文件体积和类型保真风险，支撑后续工程化路径选择。
- **差距**: 现有资料能说明方案优劣，但无法回答当前环境中导出链路的吞吐、瓶颈在数据库导出还是 Parquet 写入、以及是否值得继续工程化。
- **范围变更（2026-07-31）**: 用户决策取消 MySQL 实测，本 POC 仅覆盖 PostgreSQL。MySQL 侧仅保留方案缺口记录（mysqlsh 原生 Parquet 导出未覆盖），不再作为本任务验收项。

## 解决方案

使用 Podman 创建本地临时 PostgreSQL 实例，构造可重复测试数据集，执行逻辑导出并转换为 Parquet，记录导出耗时、转换耗时、端到端耗时、行数、输出文件大小、压缩比、CPU/内存/磁盘 I/O 观察值和类型校验结果。优先使用本地可控容器环境；若数据库镜像、服务或依赖不可用，记录环境阻断并产出可执行实验方案与缺口。MySQL 实测按用户决策取消。

## Seam 分析

### 测试接缝
- 实验边界: 数据库容器/实例、逻辑导出命令、转换脚本、Parquet 校验命令。
- 证据边界: 原始命令、版本信息、数据规模、计时输出、资源采样、Parquet metadata、行数校验。
- 隔离策略: 使用 Podman 临时容器创建测试库和测试表；测试数据可重建；输出目录独立，不依赖生产数据。

### 验收可测性
- 每次实验必须记录可复现命令和输入规模。
- PG 与 MySQL 使用同一类数据模型和相近行数，避免只比较不等价负载。
- 端到端指标和阶段指标分开记录，便于定位瓶颈。

## 用户故事

1. 作为数据迁移方案设计者，我想知道 PostgreSQL 逻辑导出转换 Parquet 的吞吐和瓶颈，以便判断是否适合作为批量迁移路径。
2. 作为数据迁移方案设计者，我想知道 PostgreSQL 逻辑导出路径的复现成本、类型保真风险和可工程化程度。
3. 作为项目决策者，我想看到 PostgreSQL 单库链路的实测指标、瓶颈定位和下一步工程化建议，并明确 MySQL 路径未覆盖导致的决策缺口。

## 实现决策

- 场景类型: research。Do 阶段走调研/实验路径，产出实验报告而非产品代码。
- 数据规模: 推荐先使用可在本机稳定运行的中等规模数据集，默认目标为每库 100 万行；若资源不足，降级到不低于 10 万行并记录原因。
- 实例方式: 使用 Podman 启动 PostgreSQL 临时容器；容器名称、镜像版本、端口、初始化命令和清理命令必须写入报告。
- PostgreSQL 路径: 优先测试 `COPY ... TO STDOUT`/`\COPY` 逻辑导出，再用 PyArrow 或 DuckDB 转 Parquet。
- MySQL 路径（已取消实测）: 原计划测试逻辑查询导出路径；`mysqlsh` 在本机不可用，MySQL Shell Parquet 导出记为环境缺口，不执行实测。
- Parquet 参数: 至少固定一种压缩方式，推荐 `zstd`；必要时追加 `snappy` 作为速度优先对照。
- 报告内容: 实验环境、数据模型、命令、指标表、瓶颈判断、类型保真检查、推荐路径和后续风险。

## 测试决策

- 被测对象: PG/MySQL 逻辑导出加 Parquet 转换流程。
- 校验方法: 对源表和 Parquet 文件进行行数一致性检查，抽样检查关键类型列，记录 Parquet schema。
- 性能测量: 使用 `/usr/bin/time -v` 或等价工具记录耗时和峰值 RSS；必要时记录 `du -h`、`iostat`/`pidstat` 是否可用。

## 范围外

- 不接入生产数据库。
- 不实现持续 CDC/增量同步链路。
- 不做 Spark 集群级别大规模压测。
- 不承诺最终生产吞吐，仅验证本地 POC 环境下的相对表现和瓶颈。
- 不执行 MySQL 实测（用户决策 2026-07-31）；MySQL 路径仅保留方案缺口记录。
