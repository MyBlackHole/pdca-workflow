# 两份 shqddb2 内核崩溃报告差异审计 — 规格文档

## 问题陈述

- **现状**：`vmcore_analysis_report.md` 与 `shqddb2内核崩溃根因分析报告v2.md` 对同一次 panic 给出了明显不同的结构字段解释、UAF 形成路径和 iSCSI 因果定位。
- **目标**：解释两份报告为什么会产生如此大的差异，并基于可追溯证据判断哪些结论成立、哪些被反证、哪些仍证据不足。
- **差距**：目前缺少一份逐项、同口径的证据审计；单看报告篇幅或结论措辞无法判断可信度。

## 已知信息

- 输入 A：`/home/black/Downloads/vmcore_analysis_report.md`，SHA-256 为 `f087f00ae06379347d63462b0a4ee42f50ffb70ed52a9efeb56b6559147bc771`，291 行。
- 输入 B：`/home/black/Downloads/shqddb2内核崩溃根因分析报告v2.md`，SHA-256 为 `c9642f9a8f6c9b49354c58704a3fc2aeff1e6c8e3580b285a4c318f3525655a0`，1103 行。
- 用户确认输入 A 是在 `10.6.67.187` 上分析生成；当时没有下载到与崩溃内核对应的正确源码树。
- 用户提供报告 A 的原始分析会话 `/home/black/ses_06dffb331ffe4IGZS3WxGNQQ5X.json`，SHA-256 为 `9b4a9c6c57e502b84fdf1c53563e3dc28526c686b38dd19ea9a6a3ee6925cb59`，共 34 条 message。
- 会话元数据表明报告 A 由 `deepseek-v4-flash-free` 会话生成。会话实际核验到目标版本 `kernel-debuginfo-3.10.0-1160.83.1.el7.x86_64` 未安装。
- 会话尝试过不存在的 `3.10.0-1160.119.1` vmlinux、不存在的目标版本 vmlinuz，以及自行解压但格式无效的文件；所有 crash 启动均失败，没有形成 `bt`、`struct -o`、`vtop` 或对象遍历 transcript。
- 会话随后明确决定依赖 `vmcore-dmesg.txt`、`messages.txt` 和互联网搜索到的其他版本补丁/源码类比形成结论。输入 A 末尾列出的目标版本 crash 命令属于参考命令，不是成功执行记录。
- 因此报告 A 可直接支持的主要是日志中已有的 panic、寄存器文本、调用栈文本和事件时间线；其 `RDI` 对象身份、`+0x8` 字段、`clone == NULL` 分支、SLUB 对象解释、非 blk-mq 生命周期和补丁同源性均需由独立证据重新裁定。
- 两份报告认同 panic 位于 `dm_softirq_done+0x61` 且属于 UAF，但对 `RDI` 指向的对象、偏移 `+0x8` 对应字段、对象释放路径和 iSCSI 角色的解释冲突。
- 管理中心已有三轮相关归档：T0142 的浅层结论被用户驳回；T0143 与独立复核 T0144 的代码级根因被确认。
- T0144 已明确区分直接 NVMe I/O 路径和未闭合的 iSCSI 间接触发分支，并保留独立 crash 会话、源码映射和补丁等价性证据。

## 解决方案

以“主张—证据—推理—判定”矩阵审计两份报告：

1. 建立报告来源和历史版本谱系，避免把早期稿、修订稿和独立复核稿当成同等证据。
2. 对报告 A 增加“会话取证账本”：逐项区分成功命令、失败命令、原始输出、搜索材料、模型 reasoning 和写入报告的确定性表述。
3. 分开审计四类输入：vmcore 原始数据、实际加载的 vmlinux/debuginfo、用于阅读控制流的源码树、报告作者的推理；任何一类不匹配都必须限定其影响范围。
4. 对关键冲突使用相同判定基准：反汇编有效地址、DWARF 字段偏移、请求/target 对象身份、页表状态、指定内核源码生命周期、实际底层设备、上游补丁语义。
5. 将差异成因分为：分析环境/版本输入不同、结构体或寄存器误读、错误分支假设、相关性升级为因果、修订报告新增验证、叙事篇幅差异。
6. 产出逐项判定和总解释；不以报告长度、措辞强度或历史 verdict 单独代替技术证据。

方向已于 2026-07-30 获用户确认。

## 备选方案与取舍

- **采用：证据谱系与针对性复核**。直接回答“为什么差异大”，复用 T0144 已确认的独立 crash 证据，并把报告 A 的生成过程纳入审计。
- **不默认采用：完整重跑 vmcore**。T0144 已完成两轮独立复跑，当前再次全量执行的新增信息价值较低；只有现有证据无法裁定的关键冲突才提出最小复跑命令。
- **不采用：仅按两份报告文本做语言比较**。这无法判断哪份技术主张成立，也无法识别“参考命令被写成已验证结论”的证据谱系问题。

## Seam 分析

### 测试接缝

- 文档边界：两份输入报告中的明确主张、引用的 crash 输出和源码片段。
- 谱系边界：报告 A 的原始 JSON 会话；只引用与取证和推理相关的内容，不复制其中的认证信息。
- 证据边界：T0144 不可变记录、已登记证据、指定版本内核源码和必要的只读版本控制历史。
- 一致性检查：相同机器指令、寄存器值和结构字段偏移必须导出相同的有效地址解释。
- 外部依赖：不依赖网络搜索作为核心证据；如需核验上游提交，只把官方内核 Git/发行商材料作为补充，并单独标注。

### 验收可测性

- 每个关键分歧必须同时列出 A 的主张、B 的主张、判定依据和 verdict。
- 所有“成立/错误/证据不足”结论必须至少回链一个可定位证据。
- 事实、推断、假设必须分层，不能用时序邻近替代对象链因果证明。

## 用户故事

1. 作为事故复盘负责人，我想知道两份报告为何得出不同根因，以便判断应采信哪一份。
2. 作为内核问题审查者，我想看到关键分歧对应的原始证据和源码语义，以便独立复核。
3. 作为运维决策者，我想区分内核缺陷、直接 I/O 路径和可能的外部诱因，以便制定不误导的整改措施。

## 实现决策

- 场景类型为 `research`。
- 主要产物为差异分析报告和证据矩阵，不修改 kernel-rpm 源码。
- 当前拟采用现有独立 crash 证据与指定源码做针对性复核，不默认重新运行完整 vmcore 调查。
- 不需要子任务拆分；本任务可在一个 PDCA 周期内完成。
- 未发现需要新增 ADR 的不可逆架构决策。

## 测试决策

- 对偏移解释做反汇编、DWARF 和源码三方一致性检查。
- 对 UAF 根因做“保存旧引用 → 对象释放 → 再次解引用”的生命周期闭环检查。
- 对 iSCSI 角色做“事件存在 → 作用到 dm-19 → 导致 reload → faulting request”分层门槛检查。
- 对修复建议区分补丁静态语义等价与目标内核运行验证。

## 验收标准

- [ ] 列出至少 7 个关键分歧维度，并逐项给出两份报告的原文主张、证据依据和判定。

- [ ] 明确解释 faulting 指令 `mov 0x8(%rdi),%rdx` 中 `RDI` 的对象身份及 `+0x8` 的真实字段，结论可由 DWARF/源码复核。
- [ ] 明确判断两份报告各自提出的 UAF 生命周期是否闭合，并指出断裂或被反证的具体环节。

- [ ] 说明报告差异大的至少 4 类方法论原因，并将每类原因关联到具体文本实例。
- [ ] 单独说明错误源码树对源码行号、结构体语义、控制流和补丁匹配的影响，并区分仍可由 vmcore/反汇编/已验证 DWARF 独立支持的内容。
- [ ] 给出两份报告关键结论的 `supported`、`refuted` 或 `inconclusive` 判定及置信度。
- [ ] 最终报告明确当前最可信的代码级根因、证据边界、残余不确定性和最小后续验证建议。
- [ ] 所有关键引用均能定位到输入报告、既有不可变记录、证据文件或指定版本源码；输入文件哈希被记录。

## 范围外

- 默认不重新执行完整 crash/vmcore 调查。
- 不编译、回移植或压测内核补丁。
- 不对尚无对象链证据的 iSCSI 间接触发者作确定性归因。
- 不修改两份原始报告或历史 `records/` 内容。
- 不把内核升级版本是否已包含修复作为未经发行商资料核验的确定事实。
