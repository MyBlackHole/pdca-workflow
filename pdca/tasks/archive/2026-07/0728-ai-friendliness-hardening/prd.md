# 将 PDCA 的 AI 友好度审查工程化为可验证协议

## 问题陈述

现有 PDCA 流程具有较好的文档可读性，但入口引用、阶段门禁、任务状态、工具能力和 AI 友好度评分之间缺少统一的可执行合约。已有 T0119/T0131 审查依赖单模型主观评分，且存在入口断链、归档状态不一致仍通过校验、工具接口硬编码和验收证据不足等问题。

## 已知目标

- 将关键门禁从“文件或字段存在”提升为“语义及跨文件不变量正确”。
- 为 `$PDCA_HOME`、索引、CLI、子代理等能力增加启动诊断和降级路径。
- 从 skill frontmatter 自动生成并校验技能索引。
- 审查全部 skill 的内容量、重复度、信息密度和渐进披露质量。
- 建立基于 GQM、认知维度、任务成功率和故障注入的可重复评测基线。

## 解决方案

1. 定义 task、clarification、evidence、verdict、disposition 的机器可验证 schema。
2. 增强阶段校验，覆盖确认语义、证据完整性、状态一致性和归档不变量。
3. 增加环境能力诊断，并用抽象能力与 fallback 取代具体平台工具名。
4. 自动生成技能索引并在验证流程中检查引用完整性。
5. 建立 skill 内容量审查器，输出 UTF-8 bytes、结构、重复片段和引用关系；认知维度由独立 rubric 审查。
6. 对候选精简项做压缩前后配对实验，只有在任务成功率和门禁正确率不下降时才接受压缩。
7. 建立覆盖六类 scenario 的正常路径与故障路径基准。

任务拆分为四个独立交付面：

1. 状态机 schema、门禁验证和历史清理 dry-run。
2. 环境 doctor、通用能力协议和技能索引生成。
3. skill 内容量审查及通过配对验证的候选精简。
4. 六场景确定性 harness。

父任务负责统一 schema、度量口径、证据聚合和最终综合验证。

已确认内容量审查不仅产出报告，也实施通过配对验证的精简；未保持任务效果的候选改动必须撤回或重新设计。

历史数据采用清理策略，不为旧格式增加兼容规则。仅清除不符合新 schema 的历史任务目录及重复审查产物；保留 `records/` 中不可变证据、`knowledge/` 和 `journal/`。强制执行顺序为：冻结并测试新 schema → dry-run 生成逐项清单与理由 → 校验保留目录不在清单 → 通过 Git 执行可恢复删除。禁止边定义 schema 边删除数据。

工具适配采用通用能力协议；本任务只实现当前执行环境的能力映射与主会话降级路径，不覆盖所有第三方 Agent 平台。

首版评测只保留仓库内可立即执行的确定性测试夹具，覆盖六类 scenario 和故障注入。当前没有独立 Agent runner，相关 trial schema、协议和未来接口不提高当前 AI 效率，终止并删除。

skill 精简只处理 Pareto 高成本候选。每项候选必须同时满足：UTF-8 bytes 至少下降 15%；所有既定确定性夹具、门禁夹具和任务验收夹具零回归。未达到最小效果量的改动不实施。零回归结论只适用于既定夹具，未覆盖场景必须披露，不得外推为所有真实任务零回归。

内容量审查默认报告 UTF-8 bytes。对比实验表明 tokenizer 与 bytes 产生相同 Pareto 候选，而字符数会漏掉 flow-plan，因此按“不能改善 AI 效率或审查决策的内容应删除”原则，不引入 tokenizer 并删除字符指标。模型真实 token 只允许由未来独立 Agent runner 实测。

## Skill 内容量审查方法

内容量不以单一行数判断，采用以下指标：

| 维度 | 指标 | 判定目的 |
|------|------|----------|
| 绝对成本 | UTF-8 bytes | 提供零模型依赖且经 tokenizer 候选对照的内容成本 |
| 信息密度 | 可执行步骤、输入输出、门禁、失败处理占总内容比例 | 区分指令与教程性内容 |
| 重复度 | skill 内重复、跨 skill n-gram/语义重复、公共收尾重复 | 识别可提取的共享协议 |
| 导航成本 | 标题深度、关键步骤定位距离、引用扇入/扇出 | 评价 AI 找到目标动作的难度 |
| 渐进披露 | 主文件是否只保留必需路径，详细参考是否按需加载 | 防止一次加载全部背景知识 |
| 效果保持 | 同一任务压缩前后成功率、门禁错误率、工具调用和人工干预 | 防止以删减换取表面 token 降低 |

T0130 的行数与引用数结果作为历史基线，但不直接视为任务效果已提升；本任务补充 bytes 计量和执行结果验证。

自动指标严格限定为可复现且能影响决策的 bytes、文档结构、规范化文本重复和引用图。信息密度、渐进披露、角色表达等认知维度使用预定义 rubric 单独报告，不与自动指标合成单一总分。

## 用户故事

1. 作为首次进入仓库的 AI Agent，我希望入口和技能引用可以被自动解析，以便不会沿断链执行。
2. 作为阶段执行者，我希望转换命令拒绝语义不完整或跨文件不一致的数据，以便不能通过伪造空文件绕过门禁。
3. 作为不同 Agent 环境的使用者，我希望流程声明抽象能力和降级路径，以便环境缺少特定工具时仍有确定行为。
4. 作为技能维护者，我希望获得每个 skill 的可复现内容量和重复度报告，以便只精简真正高成本的候选。
5. 作为审查者，我希望改进前后使用同一组确定性夹具，以便区分真实改善和主观印象。
6. 作为仓库维护者，我希望旧格式任务按可审计清单清理，同时保留 records、knowledge 和 journal，以便减少兼容负担而不破坏不可变证据。

## 实现决策

- 使用 JSON Schema Draft 2020-12 描述任务与关联记录的结构；跨文件和时间顺序不变量由验证器补充。
- 阶段验证采用 fail-closed：解析错误、未知字段组合、缺失证据或不一致状态均拒绝推进。
- schema 冻结和测试先于历史清理；清理器默认 dry-run，删除目标必须来自版本化 manifest。
- 能力协议包含能力名、required/optional、检测结果和 fallback；核心流程不含平台专用工具名。
- 技能索引从 frontmatter 生成，不维护易漂移的手工行数。
- 内容量审查使用模型无关的 bytes；真实 token 留给未来 runner 实测。
- 自动内容指标与认知维度 rubric 独立输出，不计算综合主观分。
- 没有当前执行路径的 Agent 行为实验不实现；未来需要时另立任务并用实际 runner 验证。
- 架构硬决策记录于 `docs/adr/ADR-0002-strict-contract-and-capability-adapter.md`。

## 测试决策

- schema 单元夹具：每个合法 phase 至少一个正例；每条不变量至少一个反例。
- 门禁故障注入：拒绝未确认的 final_confirmation、无效 evidence、缺 verdict、空 disposition 和矛盾 archive 状态。
- doctor 夹具：`PDCA_HOME` 未设、入口缺失、CLI 缺失、agent.spawn 缺失及 fallback 成功。
- 索引测试：生成两次字节一致；所有目标存在；frontmatter 必填字段完整。
- 内容量测试：同一输入 bytes 结果稳定；重复检测与引用图使用固定 fixture。
- 压缩配对测试：改动前后运行同一夹具；UTF-8 bytes 降幅至少 15%，所有既定夹具通过。
- 清理安全测试：dry-run 不修改文件；保留目录永不进入 manifest；目标均位于明确任务目录。
- 集成测试：覆盖 development、bugfix、research、documentation、design、review 六类场景。

## 验收标准（待 Grill 后定稿）

- [ ] 所有权威入口的本地引用均可解析，断链数为 0。
- [ ] 合法阶段转换测试全部通过，预定义非法转换测试全部被拒绝。
- [ ] 已归档任务不存在 phase/status/active/states 互相矛盾的状态。
- [ ] 不符合新 schema 的历史任务和重复审查产物已按确认清单清除，保留 records、knowledge、journal。
- [ ] 缺少可选 CLI 或子代理能力时能明确降级，不调用未定义工具。
- [ ] 技能索引完全由 frontmatter 生成，生成结果可重复且可校验。
- [ ] 每个 skill 都有内容量指标，能定位高成本、高重复、低信息密度的候选项。
- [ ] 任一内容压缩均有压缩前后配对结果；所有既定确定性夹具不得回归，未覆盖场景已披露。
- [ ] 被接受的单项 skill 精简 UTF-8 bytes 降幅不低于 15%。
- [ ] 确定性报告包含夹具通过率及可判定错误码；不包含未执行 Agent 实验的字段或结论。

## 方法论依据

- Goal–Question–Metric：确保每项度量直接服务于明确目标。
- Cognitive Dimensions of Notations：评价隐藏依赖、易错性、黏滞性、角色表达和冗长度。
- AgentBench / SWE-bench 式任务评测：以交互任务和可执行结果作为能力依据。
- 故障注入与配对实验：比较改进前后的成功率、恢复能力和资源消耗。
- NIST AI RMF 的 Govern–Map–Measure–Manage 闭环。
