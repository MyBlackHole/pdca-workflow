# vmcore 崩溃与内核 bug 根因独立分析 — 规格文档

## 问题陈述

- **现状**：给定 vmcore 尚需在本轮通过指定 tmux pane 从零分析；任何历史分析都不属于本轮输入。
- **目标**：从本轮新采集的异常现场、寄存器、内存对象和调用路径建立可复核、可证伪的根因链，并将关键逻辑逐环对应到指定版本源码的具体位置。
- **差距**：尚未由本轮证据确认直接崩溃点、异常对象、对象生命周期、竞争路径、触发条件和对应源码 bug；不能预设根因，也不能把相关性写成已证实因果。

## 解决方案

在 tmux pane `0:0.0` 上建立带有本轮标记的全新 crash 会话，严格使用用户指定的 vmlinux 与 vmcore。保存完整交互输出，并从概览、日志、崩溃栈、寄存器、反汇编、结构体字段、页表/地址状态和相关设备对象逐层取证。随后对照 `/home/black/shqddb2/kernel-rpm/src/linux-3.10.0-1160.83.1.el7`，将汇编和内存状态映射到源码文件、函数、行号、条件分支和对象生命周期；从这些新证据独立形成 bug 根因并检验合理替代解释。

分析过程采用逐步调查日志。每条 crash 命令在执行前说明目的、待验证假设和预期信号，执行后记录实际结果、解释、证据强度以及它如何决定下一步；失败、空结果和反证也必须保留。

同时把 iSCSI 作为候选触发因素单独审查：先确认崩溃时间窗内是否存在 iSCSI session/connection/path 事件，再确认该事件是否作用于崩溃涉及的同一设备或对象，最后检查它是否通过源码中的状态转换进入 bug 窗口。时间相邻本身不构成触发证据。

## Seam 分析

### 测试接缝

- 运行时接缝：tmux pane 中的新 crash 会话及其原始 transcript。
- 调查过程接缝：逐条命令调查日志，将“目的/假设 → 命令 → 原始结果 → 解释 → 下一步”串成可审计决策链。
- 符号/内存接缝：crash 的 `bt`、`log`、`dis`、`struct`、`rd`、`kmem`、`sym` 等只读取证命令。
- 源码接缝：指定源码树中的对应 C 文件、结构定义和行号。
- 证据管理接缝：先将 pane 原始输出复制到 PDCA task 的 evidence 目录，再通过 evidence manifest 登记；不以历史报告替代本轮原始输出。
- 不使用 Mock/Stub；研究对象就是给定 vmcore 和与之匹配的 vmlinux。

### 验收可测性

- 每项结论必须反向链接到本轮原始命令输出和/或指定源码位置。
- 每条 crash 命令都必须有执行理由；不得先批量执行再事后补写无法验证的目的。
- “事实”“证据支持的推断”“未证实假设”分别标注，避免不可验证的因果跳跃。
- 至少检查一组与主根因竞争的替代解释；若无法排除，必须降低结论置信度而不是宣称确认。
- 对源码行号使用当前指定源码树的实际行号，并展示足以理解分支的最小上下文。

## 用户故事

1. 作为内核故障分析人员，我想独立重跑 crash，以便确认结论来自当前 vmcore 而非历史报告复述。
2. 作为源码维护人员，我想看到 fault 指令、结构字段与具体源码位置之间的映射，以便审查推理是否成立。
3. 作为事故负责人，我想区分直接原因、促成条件、触发事件和尚未证实的猜测，以便制定风险相称的处置建议。
4. 作为存储维护人员，我想知道 iSCSI 是否触发此次 bug，以及中间证据是否完整，以便避免错误归因于传输层。

## 实现决策

- 新会话使用明确的开始/结束标记，完整保存原始 transcript；在启动前确认 pane 位于 shell 提示符。
- 每一步先登记命令目的、待验证假设和预期观察，再通过 tmux 发送命令；捕获输出后立即登记结果、解释和下一步。
- 失败、拼写错误、无输出或推翻主假设的命令同样进入原始 transcript 和调查日志，不得删除。
- 启动命令必须与用户给定的 vmlinux、vmcore 参数一致，不使用历史轮次出现的替代路径。
- 先收集最小现场，再根据现场动态追加只读取证命令；禁止在远端执行修复、配置变更或内存写入。
- 源码映射以指定源码树为唯一行号基准；调试符号、反汇编和源码若不一致，必须显式记录差异。
- R0142/R0143 只保留在 Plan 的查重记录中；Do 与 Check 不读取、不引用，也不用于形成假设、选择命令或验证结论。
- 该任务是单一研究闭环，不拆分子任务；拆分会割裂 crash 对象地址与源码推理上下文。
- 无架构变更、不可逆决策或数据模型变更，不创建 ADR。

## 测试决策

- 使用 crash 成功加载信息验证 vmlinux/vmcore 匹配。
- 使用独立 transcript 中的命令提示符、输出和会话标记验证证据新鲜度。
- 对照调查日志与 transcript，验证命令顺序、原始结果及逐步解释没有缺项或事后选择性遗漏。
- 使用结构字段偏移、寄存器和反汇编交叉验证 fault 指令的 C 语义。
- 使用源码检索和带行号上下文验证调用路径、同步机制与对象生命周期。
- 使用替代假设矩阵检查每个候选解释的支持证据、反证和剩余缺口。
- 使用四层门槛验证 iSCSI 触发假设：事件存在、对象同一、状态转换连接、进入 bug 时间窗口。

## 验收标准

- [ ] 用户指定的 crash 命令在 tmux `0:0.0` 中全新执行并成功加载；原始输出能确认 kernel release、dumpfile 和基本系统信息。
- [ ] 本轮保存完整、带会话边界的 crash transcript，且报告引用的关键命令均能在 transcript 中定位，未将 R0142/R0143 输出冒充新证据。
- [ ] crash 分析的每一步均记录目的、待验证假设、预期信号、实际结果、解释和下一步决策；失败、空结果和反证步骤也完整保留，并与 transcript 顺序对应。
- [ ] 直接异常现场得到确认：fault 类型、CPU/任务、RIP、fault 地址、调用栈和关键寄存器均有本轮原始输出支撑。
- [ ] fault 指令被反汇编并映射到具体 C 表达式；寄存器、地址偏移与结构字段之间的对应关系有调试符号或结构偏移支撑。
- [ ] 关键对象的有效性和生命周期状态得到检查，包括导致 fault 的指针、当前/历史对象关系及相关页表或 slab 线索；无法确认的部分明确标为不确定。
- [ ] 根因链的每个关键环节均给出指定源码树中的文件、函数和实际行号，并说明该段源码如何支持或限制该环节。
- [ ] 至少评估 use-after-free、普通 NULL/野指针、硬件内存损坏或其他合理候选中的一组替代解释，记录排除依据或未排除原因。
- [ ] 对“iSCSI 是否触发此次 bug”给出 `triggered`、`not_triggered` 或 `inconclusive`；结论分别覆盖 iSCSI 事件、同一设备/对象关联、源码状态转换和 bug 时间窗，且不以时间相关性单独证明因果。
- [ ] 最终报告明确分层直接原因、根本原因、触发/促成因素、适用边界和证据局限，不把时间相关性单独当作因果证明。

## 范围外

- 不修改内核源码或构建 RPM。
- 不在远端主机实施升级、补丁、重启、设备操作或配置变更。
- 不复现线上竞态；只分析静态 vmcore。
- 不把未经当前源码和 vmcore 支撑的上游补丁/CVE 对应关系写成确定结论。
