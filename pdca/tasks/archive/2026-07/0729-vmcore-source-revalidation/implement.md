# T0144 预计分析过程

## 总体原则

- 只使用本轮新启动的 crash 会话、给定 vmcore/vmlinux 和指定源码树。
- 每条命令执行前记录：目的、待验证假设、预期信号。
- 每条命令执行后记录：原始结果、解释、证据强度、下一步决策。
- 命令失败、字段不可读、页不在 dump 中、结果与假设冲突时，原样保留并调整路径。
- 不预设具体模块或根因；后续分支由本轮现场决定。

## 0. 建立可审计的新会话

目的：确保分析确实是本轮从零执行，输入路径正确，后续输出不会与 pane 历史混淆。

1. 捕获 pane 当前状态，确认位于远端 shell 提示符。
2. 输出本轮唯一开始标记和时间。
3. 再次只读核验 vmlinux、vmcore 的路径和元数据。
4. 原样执行：

   `crash /usr/lib/debug/usr/lib/modules/3.10.0-1160.83.1.el7.x86_64/vmlinux /nbudata/vmcore/vmcore`

5. 捕获 crash 启动摘要，验证 release、dumpfile、CPU 数、内存、panic task 和 uptime；加载失败则停止根因推理，先解决输入匹配问题。

## 1. 固定最小崩溃现场

目的：先回答“哪里崩、谁在崩、因为什么异常崩”，避免过早推测根因。

预计从以下只读命令开始，并根据 crash 版本支持情况调整：

- `sys`：确认内核、机器、崩溃时间、uptime 和 panic 字符串。
- `bt`：取得 panic task 的主调用栈、异常 RIP 和寄存器。
- `bt -f`：补充栈帧内容，寻找函数参数和保存的对象地址。
- `log`：取得崩溃附近内核日志、异常类型、CR2、error code 和 call trace。

本阶段出口：

- 已确认 fault 类型；
- 已确认 faulting CPU/task；
- 已确认异常 RIP、fault 地址和最短可信调用链；
- 若多个栈或 panic task 不一致，先解释 kdump/NMI 上下文再进入下一步。

## 2. 锁定 fault 指令及 C 语义

目的：把“函数名附近崩溃”收敛到准确机器指令、操作数和 C 表达式。

预计命令：

- `sym <RIP>`：验证 RIP 的符号及偏移。
- `dis <fault-function>`：反汇编完整相关函数。
- 若支持，使用带源码行信息的反汇编或 GDB `list`；否则由反汇编地址和本地源码交叉定位。
- `rd <fault-address>` 或适当页表/内存检查：区分未映射、不可读、零值或可读但内容异常。

分析动作：

1. 找出 fault 指令读取或写入的有效地址表达式，例如 `base_register + offset`。
2. 用异常寄存器代入，复算得到 fault 地址。
3. 确定 base register 代表哪个 C 对象，offset 对应哪个结构字段。
4. 对照指定源码树，记录文件、函数、实际行号和最小必要上下文。

本阶段出口：机器指令、寄存器、fault 地址、结构字段和 C 表达式形成闭环。

## 3. 还原关键内核对象

目的：确认异常地址来自哪一个对象，指针为何异常，以及周围对象是否仍自洽。

预计按现场选择：

- `struct -o <type>`：取得关键字段偏移。
- `struct <type> <address>`：解析对象字段。
- `rd <address> <count>`：核对结构解析所依赖的原始内存。
- `kmem <address>` 或同类命令：检查地址的页/slab 状态（以 crash 实际支持为准）。
- `sym <function-pointer>`：解析函数指针或类型对象。

检查内容：

- 指针是 NULL、非 canonical、未映射、已释放样式、被覆写，还是指向仍有效但类型错误的对象；
- 父对象、子对象、链表、回指、引用计数、状态位和函数指针是否互相一致；
- vmcore 是 partial dump 时，区分“页未保存”和“运行时确实未映射”，避免误判；
- 关键地址是否属于 slab、vmalloc、module 或直接映射区。

本阶段出口：给出异常对象状态；无法确认释放状态时只写“失效/不可访问指针”，不越级宣称 UAF。

## 4. 向前追踪对象来源和生命周期

目的：回答“异常指针在哪里被赋值、正常应由谁保护、何时可能失效”。

源码分析路径：

1. 从 fault C 表达式反向追踪字段赋值点。
2. 找出对象分配、初始化、发布、获取、引用、替换和释放路径。
3. 标注涉及的锁、RCU/SRCU、引用计数、队列冻结、barrier 和 completion。
4. 检查提交路径与完成路径是否跨越对象生命周期边界。
5. 为每个关键环节记录源码文件、函数和实际行号。

vmcore 取证路径：

- 根据对象地址追踪所有者、请求、设备、队列、映射或模块对象；
- 检查当前对象与请求保存的历史快照是否一致；
- 必要时检查其他 CPU、相关 task 或 pending work，以寻找并发现场；
- 只在现场指向并发问题时扩大到 `bt -a` 等高输出命令。

本阶段出口：形成候选 bug 机制，但仍作为待证假设。

## 5. 检查时间线和触发/促成因素

目的：区分代码 bug、直接触发事件和仅仅时间相邻的噪声。

预计动作：

- 从 `log` 中围绕崩溃时间建立最小时间窗；
- 仅提取与候选对象、设备、模块或生命周期事件相关的日志；
- 对每个事件判断它是否具备连接到源码状态转换的中间证据；
- 没有中间证据时只标为相关事件，不写成触发原因。

本阶段出口：直接原因、根本代码缺陷、触发条件和促成因素分层描述。

## 6. 主动证伪与替代解释

目的：避免看到一个坏指针就直接归因于某种竞态或 UAF。

至少建立以下候选矩阵，并根据实际现场增删：

| 候选解释 | 需要观察的支持信号 | 主要反证方向 |
|---|---|---|
| NULL/普通非法指针解引用 | base 值为零或明显非法，字段链可直接解释 | base 非零且曾是合法对象地址 |
| use-after-free/生命周期竞态 | 原对象失效、当前替代对象存在、分配释放路径与并发窗口闭合 | 无释放路径、地址只是 partial dump 缺页 |
| 越界写或其他内存破坏 | 邻近字段同时异常、poison/覆写模式、多个对象不自洽 | 只有单一生命周期指针陈旧且其他字段稳定 |
| 硬件内存错误 | MCE/EDAC/硬件日志、随机多点破坏 | 无硬件错误且破坏符合确定的软件状态转换 |
| 调试符号或 vmcore 不匹配 | 类型偏移、release、反汇编与日志明显冲突 | release/build-id/结构布局相互一致 |

每个候选输出 supported、rejected 或 inconclusive，并列出具体证据。

## 7. iSCSI 候选触发因素专项审查

目的：判断 iSCSI 是否触发此次 bug，同时避免把存储日志中的时间相邻事件误写成因果关系。

调查分为四个连续门槛：

1. **事件存在性**：检查崩溃时间窗内是否有 iSCSI 登录、登出、重连、connection error、timeout、session recovery 或相关 SCSI path 变化。
2. **对象同一性**：把日志中的 host/session/target/LUN/path 映射到崩溃涉及的 block、SCSI、device-mapper 或其他实际对象；不同设备的事件不能作为触发证据。
3. **状态转换连接**：在指定源码树中定位 iSCSI/SCSI 事件引发的队列、设备、映射或请求状态转换，说明它如何到达候选 bug 路径。
4. **时间与并发窗口**：证明该转换发生在异常对象生命周期或竞争窗口内；只有时间接近但无中间对象连接时，最多判为相关事件。

根据现场可能使用：

- `log` 中针对 iscsi、scsi、session、connection、target、LUN、path、timeout、recovery 等关键词和已识别设备标识的定向检查；
- 与实际崩溃对象相匹配的 SCSI host/device、request queue、block device 或映射结构检查；
- 对相关 task、workqueue、timer、request 或连接对象进行只读解析；
- 对照指定源码树中的 iSCSI、SCSI、block 和最终 fault 路径，验证中间调用或状态转换。

最终只允许三种结论：

- `triggered`：四个门槛均有证据闭合；
- `not_triggered`：存在明确反证，例如无相关 iSCSI 事件、设备不相同或状态转换无法到达 bug 路径；
- `inconclusive`：关键页、日志、对象标识或中间转换证据缺失。

## 8. 建立源码闭环

目的：让最终根因逻辑可以由源码审查者逐项复算。

最终因果链中的每一环都必须包含：

1. 本轮 crash 证据 ID 或 transcript 位置；
2. 对应对象/字段；
3. 指定源码树的文件、函数和实际行号；
4. 该代码如何支持此环；
5. 该证据不能证明什么。

若任一关键环只有推测，没有 vmcore 或源码连接证据，则降低最终结论置信度并明确缺口。

## 9. 证据收尾与进入 Check

预期产物：

- `evidence/crash-session.log`：完整新会话原始输出；
- `evidence/investigation-log.md`：逐步目的、假设、命令、结果、解释和下一步；
- `evidence/source-map.md`：反汇编、字段和源码行映射；
- `evidence/alternative-hypotheses.md`：替代解释矩阵；
- `evidence/iscsi-trigger-review.md`：iSCSI 四层触发证据及三态结论；
- `evidence/convergence.json` 与 `evidence/manifest.jsonl`：验收条件到证据的登记映射。

Do 完成后才读取 Check 流程，形成 `conclusion.md`。结论需由用户 verdict 确认，随后才能进入 Act 与 Archive。
