# TDD 工作流（RED→GREEN→REFACTOR）

## 概述

先写测试。看它失败。写最小代码通过。

**核心原则：** 如果你没有看到测试失败，你就不知道它测的是不是对的。

**违反规则的字面意思就是违反规则的精神。**

## 铁律

```
无失败测试则无生产代码
```

写了代码再写测试？删掉。从头开始。

- 不要留着当"参考"
- 不要"边写测试边改"
- 不要看它
- 删就是删

从测试开始实现。句号。

## RED→GREEN→REFACTOR

### RED：写失败测试
1. 写一个测试，描述你期望的行为
2. 运行测试，确认它失败
3. 确认失败原因是"功能不存在"而非语法错误

### GREEN：写最小代码
1. 写刚好能让测试通过的代码
2. 运行测试，确认全部通过
3. 不要多写——最小即可

### REFACTOR：清理
1. 消除重复
2. 改善命名
3. 拆分过大的函数/类
4. 运行测试，确认仍然通过

## 接缝（Seams）

**接缝**是你测试的公共边界。只在预商定的接缝处测试。写任何测试前，先写下测试的接缝并获得用户确认。

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 实现耦合 | mock 内部协作者、测试私有方法 | 只测公共接口行为 |
| 同义反复 | 断言用和代码相同的方式重算期望值 | 断言应独立验证 |
| 横向切片 | 先写所有测试，再写所有实现 | 按纵向切片工作：一个接缝、一个测试、一个最小实现 |

## 反合理化守卫

| 你的理由 | 真相 | 你应该做 |
|---------|------|---------|
| "太简单了不需要测试" | 越简单越容易有 off-by-one 和边界问题 | 至少一个 happy path 测试 |
| "先写代码再补测试效率更高" | 补的测试往往只验证实现而非行为，且容易通过 | 删掉代码，从测试开始 |
| "这个函数没有外部依赖不需要 mock" | 任何外部输入都需要隔离 | 至少 stub 控制返回值 |
| "测试太慢了" | 慢测试比没有测试好 | 标记为 slow，按需运行 |
| "等全部写完再统一测试" | 最后发现的问题修复成本最高 | 每个切片完成后立即测试 |
