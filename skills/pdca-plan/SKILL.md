# Plan：确认问题，建立可验收计划

## 先定位，不以加载当授权

核对本文件经符号链接解析后的真实路径，定位集中 Git 工作副本 **PDCA_ROOT**。既有任务绑定优先于 cwd 或环境变量；与入口所在根冲突时停止，不在目标项目创建 `.pdca/` 或另一份 records。定位不等于批准业务操作。

先读[共同恢复入口](../../ontology/contracts/entry-recovery.md)，再读当前绑定项目 context、自己的 task/原 Agent 绑定、最后完整事件和当前请求。核对记录的 `rules_git_head`/`rules_git_status`；每次获准写入记录前按共同入口重新采集当前 Git 来源。已有任务不自动改绑或升级规则，原依据缺失或规则冲突时停止；不复制规则、不自动 checkout，不以新规则改写原授权。

当前会话不是该任务执行者时，只把真实用户操作路由回原 Agent 后停止本地执行；不可路由就阻断。**切换 Skill 不换 Agent**，不要调用新建工具、设置自动 fork 或由父 Agent 接管。加载方法、文件存在和上一阶段 PASS 都不授权本阶段。

开始前核对匹配 task/attempt/phase/run/subject 的原始用户回应、固定输入及撤权状态，并核验集中资源预约及实际写权。缺项时展示本阶段目标和缺项后等待；已有明确确认不要重复盘问。无任务时返回总入口定位，不在阶段 Skill 中新建。

## 当前 run 的动作

1. Plan 启动对象先包含用户问题、目标、范围/非目标、约束和预期产物；正式 Plan 未获准前只沟通，不生成业务模型或写代码。
2. 获准后读取[Plan 方法](../../ontology/process/flow-plan.md)与[三场景义务](../../ontology/process/work-scenarios.md)。按 task.scene **只读取**对应场景 Skill 的"阶段方法"，不重新调用其建任务分支。
3. 固定需求和事实来源，查找可复用定义，区分已知、假设和未知。提出实质方案取舍与再评估条件，不为机械工作强造多方案。
4. 列出模型/实体交付、对象路径、AC/oracle、正反测试、业务和记录写域、资源保证、停止条件。独立孩子仅作为种子候选，用户选择后才派生。
5. 保存集中任务 plan、输入清单、验收基线及必要 seed 草案。Plan 草案不冒称最终模型已建成；所有产物可定位且有真实字节摘要。
6. **占位符禁令**：计划文档中禁止以下模式——"TBD"、"TODO"、"之后实现"、"填写细节"、"添加适当的错误处理"、"添加验证"、"处理边缘情况"、"为上述编写测试"（无实际内容）、"类似于任务N"（重复引用）。每个任务步骤必须包含：具体操作、预期结果、验证方法。缺失项必须在 Plan 完成前补齐，不进入 Do 阶段。简单任务可简化记录，但不能跳过用户审批。
7. **任务右切**：每个任务步骤应是"最小的自带验证周期 + 值得一次独立审查"的交付单元。太大的步骤拆分，太小的步骤合并。判断标准：能否在一次 Do run 中完成并产生可验证的增量？能否用一句话描述其验收方式？
8. **范围锁定**：Plan 获用户批准后，范围冻结。Do 阶段任何范围变更（新增产物、修改 AC、调整写域）必须用户显式审批，不静默接受"顺便做了"的产物。

## 决策复杂度处理

当 Plan 发现决策依赖关系复杂（多个决策互相依赖、无法一次理清）时，使用**设计树**展开：

1. 列出所有待决策项
2. 画出依赖关系：决策 B 依赖决策 A 的结果
3. 每轮只问**前沿**（所有前置已解决的决策）中的问题
4. 用户回答后，更新设计树，新解锁的决策进入下一轮前沿
5. 前沿为空 = 所有决策已明确，Plan 可以完成

每个问题附**推荐答案**，用户可直接采纳或修改。事实性问题（文件存在、API 签名等）由 Agent 自查，不问用户。

## 大型工作拆分

当任务超出单个 PDCA 周期（预计 > 8 小时或涉及 > 3 个独立模块）时：

1. 建议拆分为多个子任务，每个子任务是独立的 Plan→Do→Check→Act 周期
2. 声明子任务间的**阻塞边**：子任务 B 依赖子任务 A 的产出
3. 计算**前沿**：所有阻塞项已完成的子任务可立即开始
4. 拆分方案需用户确认粒度和依赖关系后才执行

## 自审清单

Plan 完成后，逐项自审：

| 检查项 | 通过标准 |
|--------|---------|
| 覆盖度 | 用户的每个需求都有对应的 AC 或验证方式 |
| 占位符 | 无 TBD/TODO/模糊描述 |
| 依赖完整 | 每个步骤的前置条件已明确 |
| 可验证 | 每个交付物有具体的验收方式 |
| 范围合理 | 无"顺便做了"的未批准范围 |

## 反合理化守卫

Plan 阶段必须警惕以下常见自欺模式：

| 你的理由 | 真相 | 正确做法 |
|---------|------|---------|
| "这只是小改动不需要 Plan" | 越小的改动越容易遗漏边界 | 至少列出目标、范围、验证方式 |
| "用户已经说了做什么" | 用户说的是目标，不是 Plan | 转化为可验收的步骤 |
| "之前做过类似的直接复制" | 每个任务有独特的上下文 | 确认当前任务的差异点 |
| "时间紧先跳过 Plan" | 跳过 Plan 的返工成本更高 | 精简 Plan，但不跳过 |

## 核心原则

**事实收集归代理，决策归用户。** 代理负责探索项目、收集信息、提出方案和评估取舍；用户负责选择方案、批准计划、决定优先级。代理不替用户做决定，用户不替代理做调查。

## 报告与停止

报告计划版本、验收方法和未决风险，提出 Do 的目标、写域和固定计划对象。保存 phase_completed 后等待，不能因为用户最初说"开始"就执行 Do。

**幂等性：** 用户说"继续 Plan"时，从固定输入重新开始，不依赖前一次中断的隐式上下文。重复执行不产生重复产物。
