# 用户态适配

适用于 Linux 用户态 C、以 C 风格编写的 C++ 和 Rust。共同原则见 [工程原则](engineering-principles.md)；接口类型定义仍以实际库与系统契约为准。

## C 与 C 风格 C++

- 默认沿用构建指定的 C 标准；不要因为内核使用某编译器扩展就直接加入用户态代码。
- C++ **不使用 C++ 库**。使用 C 头文件和接口，如 `<stdlib.h>`、`<pthread.h>`；不添加 `std::`、STL 容器/算法、智能指针、iostream 或库式 RAII。资源采用明确 create/destroy、init/fini 和错误清理路径。
- 新增 C++ 代码保持 C 风格函数与数据结构，不为“现代化”引入类框架、模板、异常、RTTI、`new/delete`。是否关闭异常、RTTI 属于项目构建决策，不擅自改全局选项。
- `.cc/.cpp` 不等于 C 语义：检查 `void *` 转换、关键字、C 专属扩展、初始化和跳转约束。共享 C API 按头文件惯例使用 `__cplusplus` 条件下的 `extern "C"`；不改 C 调用约定或公开布局。
- C++ 中 C 分配接口只用于符合对象生命周期规则的数据；不要用 malloc 后强转来绕过非平凡 C++ 对象的构造。混合编译确有需求时分别以目标 C、C++ 模式验证。
- 不把内核依赖的编译参数或有符号溢出语义视为用户态默认保证。

## 错误与 I/O

| 接口类别 | 按什么约定处理 |
| --- | --- |
| 系统调用/libc 包装 | 通常失败为 `-1` 并设置 `errno`；指针返回有各自失败值，逐 API 核对 |
| pthread | 许多函数直接返回错误号，不读 `errno` 判断其失败 |
| 项目内部接口 | 保持既有约定；可以定义负 errno，但不能假定所有用户态接口都采用它 |
| Rust | 按项目使用 `Result`；FFI 显式转换错误，不让 panic 越过不支持展开的 C 边界 |

- read/write/send/recv 分别处理短操作、EOF、EINTR、EAGAIN 与部分成功。重试策略按操作语义决定，不能把任意失败包进无穷循环。
- 事件循环/非阻塞 fd 在 EAGAIN 时等待就绪；长期循环维护单调时钟的截止时间，不能每次 EINTR 后重置总超时。
- Linux 上不要盲目重试 `close()`：fd 可能已经被释放并由其他线程复用。需要数据持久性时，明确应用语义并检查相关同步操作；“write 成功”并不自动代表掉电后保留。
- 需要阻止 fd 跨 exec 泄漏时采用接口支持的原子 CLOEXEC 方式；日志保留已保存的错误原因。

## 线程、信号与取消

- pthread mutex/条件变量或 C 原子优先；用户态不复制内核的 kref、spinlock、READ_ONCE 或屏障宏来替代语言同步。
- `volatile` 不提供线程同步。单生产者/消费者、单槽反复复用需要两个方向的所有权交接，而不仅是发布一次 ready。

单槽协议示意（不是可直接用于任意多生产者/消费者的代码）：

| 执行者 | 操作 | 保证 |
| --- | --- | --- |
| producer | acquire 观察 EMPTY → 写 payload → release 发布 FULL | 只能在已归还的槽位写入 |
| consumer | acquire 观察 FULL → 完整读取 payload → release 发布 EMPTY | 读取结束后才允许覆盖 |

初态为 EMPTY；同一状态变量必须采用兼容的原子访问。消费者归还后不能保留指向槽内容的借用。退出、超时、背压不能靠此表自动解决；需要这些能力时优先采用 mutex + 条件变量实现完整谓词和停止协议。

- 条件变量在同一互斥保护下循环检查谓词，处理虚假唤醒；shutdown 更新状态并唤醒相关等待者，join/等待所有回调后释放。不要持有退出线程所需的锁去 join。
- 是否使用自旋锁需看等待时间、调度、超额线程与实际基准。进程间共享对象要使用适用的 process-shared 同步和恢复约定；不能假设普通进程内锁自动适用。
- 信号处理器是特殊上下文，仅调用允许的异步信号安全接口；不调用 malloc、普通日志或 pthread mutex。按架构使用 sigwait 或信号到事件循环的通知机制；不要把信号模型与线程模型混成一套协议。
- 采用 pthread cancellation 时明确取消点与 cleanup；否则采用协作停止，避免取消留下持锁或半完成状态。

## 接口与 Rust 适配

- 复用系统公开 UAPI；不要包含内核私有头文件。兼容行为以实际运行内核的能力检测为准，而不是只比较版本字符串。
- ioctl 的 libc 返回值与内核 handler 返回值不同。内核返回负 errno 会被系统调用包装转换为用户态失败表示；不能在用户态直接按负 errno 判断 ioctl。
- Rust 用户态可按项目使用 `std`、`Result`、拥有/借用类型和同步库；“不用 C++ 库”的要求不等于禁用 Rust 库。FFI 用稳定布局与明确所有权，`unsafe` 注明成立条件。
- Rust 引用计数保障存活，不自动保证内部状态同步；`Send`/`Sync`、原子序和取消后的借用分别验证。内核 Rust 另见 [内核态约束](kernelspace.md)。

## 常见误用

| 误用 | 应采取的决策 |
| --- | --- |
| 为采用内核规范重排现有四空格代码 | 保留项目风格，将相关逻辑约束落实到本次改动 |
| 为方便清理在 C++ 中加入 unique_ptr/标准容器 | 使用 C 接口、显式所有权与清理函数 |
| 每种 callback 失败都改成 `-EINVAL` | 查调用契约并保留真正的错误原因 |
| 测得原子引用计数开销后立即换 kref | 先查是否需要共享所有权，选择用户态可用且适用的设计 |
