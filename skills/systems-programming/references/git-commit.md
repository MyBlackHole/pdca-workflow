# Git 提交与变更说明

提交范围、格式和版本策略服从用户及目标项目规则。本资料不自动授权提交、推送、合并、发信或发布。

## 确定提交内容

1. 确认本次授权的文件及逻辑改动，分别查看工作区、暂存区和相关测试证据。审查最终提交差异，不只看工作区 diff。
2. 将一个可独立理解的逻辑目的放入一次提交；保留其他人的改动、已有暂存和未跟踪文件。不使用无范围的 `git add -A` 收集混合工作区。
3. 整份文件均属于本次范围时，可按精确路径暂存或选择提交；同一文件混有无关改动时，按 hunk 构造本次内容。**`git commit --only -- <路径>` 会取所选文件的工作区内容，不能用它实现同文件内的部分提交。**
4. 暂存区已有无关内容时，选择能保留它的提交方法；需要独立索引时先保存原索引状态，事先确定它与提交后新 HEAD 的衔接方式。不为方便提交执行全局 reset、restore、stash 或清理。
5. 检查 diff、必要的空白/格式规则及与变更相关的验证。提交后核对实际提交内容与剩余改动，报告提交标识；检查失败或未运行如实说明。

独立索引提交会推进 HEAD，原索引不会自动适配，可能出现本次修改的反向暂存差异。某个提交路径原本没有暂存内容时，可仅将原索引该路径同步到新 HEAD，再确认其无关工作区 hunk 保留；该路径原本也有暂存 hunk 时，按保存的原始状态重建并核对，不能直接整文件覆盖。保留其他路径原有暂存，不能把“使用独立索引”本身当成状态已正确恢复的证明。

## 写提交说明

先读取目标项目的提交模板与已明确采用的规范。标题说明模块和实际行为变化；正文按复杂度保留有助于理解的事实：

| 变更 | 重点内容 |
| --- | --- |
| 功能 | 需求或行为、背景、实现取舍、兼容及验证 |
| 修复 | 触发条件和影响、根因、修复机制、回归验证 |
| 配置/文档/重构 | 改变了什么、原因、相关检查；重构说明应保持的行为 |

简单改动可以是一句标题和少量正文；复杂或高风险改动补充影响、迁移、性能依据及回滚条件。没有规定统一的十项必填清单。

- 标题和正文语言遵守用户及项目约定；不要把特定项目的编号、全角前缀或模板推广到其他项目。
- 版本是否更新由项目版本域、发布流程和用户要求决定，不因每次提交自动升版。用户明确不升版时保留现状。
- 仅引用确有依据的需求/Issue、测试结果、覆盖率和性能数字。没有编号则省略或注明无关联，不编造；“无需运行”“未运行”和“通过”分别表述。
- 文档或无行为变化的低风险修改采用相称检查，不为凑模板新增业务测试。中文项目约定参见用户或项目配置，不自动改动源码注释语言及生产环境。

修复需要根因证据时参考 [调试方法](debugging.md)；系统资源改动的专项验证见 [验证与审查](verification.md)。仅按实际需要读取。
