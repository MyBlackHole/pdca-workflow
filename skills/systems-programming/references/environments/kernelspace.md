# 内核态约束

首先确认目标源码树、架构、配置、子系统及 PREEMPT_RT。以下为决策依据，不保证每个列出的 API 在目标内核都存在。具体函数及清理顺序核对树内声明、文档和调用者。

按需定位：执行环境与清理、锁与复杂读侧同步、等待/per-CPU/停止、分配/DMA、UAPI/poll/mmap、设备与时间、Rust、许可。容器与句柄按 [数据结构与接口](../principles/data-and-interfaces.md)，准备上游贡献时先采用 [内核贡献流程](../workflows/kernel-contribution.md)。

## 风格与执行环境

- 内核 C 的格式、类型、条件编译和接口文档按 [Linux 内核编码与文档](../principles/coding-and-documentation.md#linux-内核编码与文档) 及目标子系统规则。
- 代码不依赖 libc、C++ 库或普通用户态运行时。内核开发以目标树支持的 C/Rust 为准，不将 C 风格 C++ 推广为内核 C++ 开发。
- 不假设每种内核执行上下文均可睡眠。硬中断、softirq、持 raw 自旋锁、禁抢占等约束与可睡眠进程上下文区分；上下文也可能受调用者持锁影响。
- **workqueue 并不一律可睡眠**：普通 threaded workqueue 与 BH workqueue 的上下文不同；核对队列标志与具体 callback。
- 尽量缩小中断/不可睡眠路径，将可延迟操作交给合适线程上下文。访问调用进程的用户指针应在有正确用户地址空间和允许 fault 的上下文处理；移到普通 worker 不会自动让原始用户指针可用。

## C 作用域清理

目标树支持、子系统接受且工具链满足时，评估 `__free()`、`guard()`/`scoped_guard()`、`return_ptr()` 等内核 C 抽象；禁止 C++ 库不限制这些机制。旧树和用户态工程沿用各自清理方式，不强行移植宏。

- 清理按声明逆序发生，在真正取得资源的位置定义并初始化变量；需要持锁的对象清理必须先于锁释放。
- guard 持锁持续到对应作用域结束；用清晰作用域控制范围，不能把最后一处显式访问当作解锁点。
- 成功返回或移交对象时使用目标树适用的所有权释放标记，避免自动清理释放已交付对象；失败路径仍须正确清理。
- 遵守目标 cleanup 文档的函数内退出要求：同一函数不混用 goto 资源清理与作用域清理；需要转换时一致处理相关资源，否则保留原清理方式。不能只证明某条退出路径无重复释放就忽略该要求。
- 自动清理只处理当前作用域，不替代 [异步退出协议](../principles/memory-and-locks.md#生命周期与退出协议)。

## 锁、内存序与生命周期

- mutex 只用于允许睡眠的场合。spinlock/raw_spinlock 的选择来自上下文与共享关系；不要用关本 CPU 中断替代跨 CPU 互斥。
- PREEMPT_RT 下 `spinlock_t`、rwlock 等语义变化，不能套用非 RT 的禁抢占/IRQ 假设。确需硬中断级保护时审慎使用极短的 raw 锁区域，而不是把所有锁都替换成 raw 锁。
- 在不可睡眠上下文或持有禁止睡眠的自旋/raw 锁时，不调用可能 fault/睡眠的 uaccess、分配或阻塞等待。PREEMPT_RT 的锁约束单独核对。
- 可睡眠进程上下文中持 mutex 并不天然禁止 `GFP_KERNEL` 分配或 uaccess；核对回收、fault、回调及锁顺序是否产生同锁依赖或死锁。把慢操作移出 mutex 是需要维持生命周期和事务一致性的设计选择，不能一概当成正确性修复。
- cancel、flush 和 synchronize 等等待操作若可能等待需要当前持有锁的执行者，会形成死锁；按实际依赖安排等待点。
- mutex 及其所在对象至少存活到 `mutex_unlock()` 调用返回，并收敛其他使用者；内部发布点或其他线程观察到锁空闲均不构成回收证明。
- `READ_ONCE`/`WRITE_ONCE` 限定特定访问行为，不自动建立完整的跨 CPU 发布协议。原子 API 按具体操作/后缀核对排序，不能假定所有 `atomic_*` 都是全屏障。
- 对象引用采用适合的 `refcount_t`/kref；取得与交付引用的存活依据按 [生命周期与退出协议](../principles/memory-and-locks.md#生命周期与退出协议) 检查。
- 卸载/失败回滚遵循 [异步退出协议](../principles/memory-and-locks.md#生命周期与退出协议)，按设备依赖同步 IRQ、定时器、work、DMA 等。`cancel_work_sync` 不是阻止所有未来 queue 的开关；`devm_*` 也不自动消除活动回调的竞态。

## 复杂读侧同步

只有当前负载和正确性需求支持时才采用；使用前读取目标树的 [seqlock 与 RCU 原文](../sources/official-docs.md#并发生命周期与资源)，不能把“读多写少”当作充分条件。

- 裸 `seqcount_t` 不序列化多个写者；写侧须有外部串行化，序列为奇数的区间不得睡眠或被相应读者抢占/中断，否则高优先级或同 CPU 中断读者可能永久重试。关联锁变体可能提供部分配套保护，按具体类型、抢占、IRQ/softirq 和 RT 实现判断，不能一概认为 mutex 自动满足条件。
- seqcount 的重试检查不保护可替换指针的对象存活；写者若能释放读者正在跟随的指针，事后重试已经太晚。指针须有独立存活依据或换用适合的结构。快照复制在读区内完成，重试不得重复提交不可撤销副作用。
- RCU 分别证明读侧保护、初始化与指针发布、写者同步和延迟回收；引用计数不能替代 grace period，RCU 也不自动序列化写者。调用者需要主动阻塞时通常评估 SRCU 等合适家族；RT、追踪、NMI 等场合按所选家族原文判断，不概括为所有 RCU 均可或均不可睡眠。
- 停止后仍有模块内 RCU 回调时，等待 grace period 不等于等待已排队回调执行完。先阻止新增来源，再按实际采用的家族/实例核对 `rcu_barrier`、`srcu_barrier` 等回调收敛；它们也不反向替代所有 grace-period 要求。

## 内存、资源与设备

| 决策 | 约束 |
| --- | --- |
| kmalloc/kzalloc、数组、flexible array | 大小受上下文和分配器限制；数组用可检查溢出的 API，结构尾数组按目标树使用 struct_size 等 helpers |
| GFP | 根据是否允许直接回收、睡眠及回收递归选取；GFP_KERNEL 可睡眠；非睡眠路径评估 NOWAIT 及失败退路，访问保留资源有理由时再用 ATOMIC，仍须处理失败；核对 NMI、RT/raw 锁及禁抢占对分配器本身的限制 |
| 大块/连续性 | 区分虚拟连续和物理连续；不将 vmalloc 内存直接作为普通 DMA 缓冲；核对设备约束 |
| 回收路径 | 文件系统/块层等按调用路径评估 NOFS/NOIO 与作用域机制，避免回收递归死锁，不只局部改一个分配标志 |
| 用户触发分配 | 核对 memcg/kmem 归属及子系统计量；按上下文选用 `__GFP_ACCOUNT`/`GFP_KERNEL_ACCOUNT` 等适用机制，不重复计量，也不能用服务字节上限替代系统资源归属 |
| devres | 只管理与 device 生命周期相符的资源，核对解绑和手动释放，先停止活动使用者 |
| 栈 | 控制局部大对象与递归；不要假定用户态栈规模，敏感或大数据按上下文另行分配 |
| MMIO | 使用适用的 ioremap/readl/writel 等平台抽象；不能用普通内存原子/volatile 指针访问替代 |
| DMA | 区分 CPU 虚拟/物理/DMA 地址；设置 mask、处理 mapping error、方向和 map/unmap/sync 配对；CPU 锁不能代替设备可见性保证 |

错误结果逐 API 区分 NULL、`ERR_PTR`、可选资源不存在和有效对象。采用 `IS_ERR`/`PTR_ERR` 等适合的判定，保留 `-EPROBE_DEFER` 等原因；`IS_ERR_OR_NULL` 仅在两者都应走同一分支时使用。只清理真正取得的资源，不能解引用或释放错误指针，也不重复释放仍由 devres 持有的资源。

DMA coherent 提供相应的一致性保证，不自动排列描述符内容、所有权位及 doorbell。按硬件与目标 DMA/MMIO 契约核对 `dma_wmb`/`dma_rmb` 等排序；PCI 等 posted write 在需要确认已到达时采用适当的同设备读回/平台办法，不能把普通 CPU 锁或编译器屏障当成设备完成确认。

coherent 分配的 CPU 地址和 DMA handle 用途分开，采用匹配的 free；streaming 映射采用匹配的 unmap/sync、方向及原始参数。释放前确认硬件不再访问并收敛软件使用者；停止 IRQ 通知不等于停止 DMA，不能把所有映射都按同一 unmap 流程清理。

分配与映射均处理失败；内存压力、高阶分配失败和设备移除是正常错误分支。需要预分配、池化或保留资源时给出容量和耗尽策略。

PREEMPT_RT 下释放内存也可能涉及分配器内部锁；分配和释放均核对调用上下文，必要时将实际回收延后到允许的执行环境。

`mempool.min_nr` 是最小保留元素数，不是最大活跃分配数；常规分配先尝试底层分配器，失败再使用保留。硬上限另行计量和准入，进展还需核对资源需求、并发及等待依赖。

目标树的类型化分配 helper（如 `kmalloc_obj`、数组/柔性数组 helpers）核对实现、默认 GFP、溢出和计数字段规则；不能因省略参数而在不可睡眠路径隐含使用 GFP_KERNEL，也不要求旧树增加该 API。

回收路径依赖工作项时，结合 NOFS/NOIO 作用域核对队列进展保证和等待关系；`WQ_MEM_RECLAIM`/rescuer 与 mempool 分别解决特定问题，均不能据此假定所有依赖都会前进或资源/锁循环已消除。

## 等待、per-CPU 与停止

- `wait_event*` 等围绕持久状态谓词等待，包含正常就绪、停止、设备失效和适用的信号/超时。使用目标等待原语建立“登记后复查”协议，状态先以正确同步方式发布再唤醒；唤醒不是状态本身。手写 `waitqueue_active` 等锁外省略唤醒的优化，必须核对配对排序，不能用 `READ_ONCE` 或裸标志替代完整协议。
- completion 适合通知已发生事件，允许先完成后等待；不充当共享数据互斥锁。按具体 wait 变体区分完成、超时和信号的返回值，不能把“返回非负”统一当成功。
- 栈上 completion 只在所有异步访问确实早于栈退出时可用；等待超时/被信号打断不取消生产者。`reinit_completion` 清除状态但不收敛参与者，必须避免上一轮生产/等待与新轮复用竞争；`complete_all` 后的 done 状态不证明所有等待者已退出。
- `this_cpu_ptr` 等得到的本 CPU 地址不能在允许迁移后继续凭“当前 CPU 独占”使用；固定迁移、禁止抢占、IRQ 保护和互斥各有不同效果。复合操作、远端访问和 CPU 热插拔/回收按目标 per-CPU/RT 原文证明，不把单次 this_cpu 操作的保证扩展为整个多步协议。
- 普通 timer_list 回调按其实际 softirq/RT 上下文核对，不能因是回调就取得可睡眠 mutex。timer 与 worker 相互重新生产时，停止协议须覆盖所有 rearm 来源。目标支持且适用时采用 `timer_shutdown_sync` 等最终禁入机制；`timer_delete_sync` 等同步删除只有其禁止并发重启的前提成立才足够。
- 同步等待的锁依赖和总退出顺序仍按 [生命周期与退出协议](../principles/memory-and-locks.md#生命周期与退出协议)；不是把 shutdown/cancel 函数排列一次就证明模块可以释放。源码、等待及 per-CPU 依据见 [官方映射](../sources/official-docs.md#并发生命周期与资源)。

## UAPI、ioctl 与不可信输入

- 不直接解引用用户指针。`copy_from_user`/`copy_to_user` 返回未复制字节数，非零表示未完整复制，不能直接当成负 errno。固定请求结构必须完整取得后才校验使用；允许短读/短写的接口则按契约返回已复制字节并维护位置/消费进度，不能一律改成 `-EFAULT`。部分复制的未初始化字段不得用于后续操作。
- 固定请求头复制到内核后验证；嵌套缓冲区有独立的长度/方向/算术/权限检查。需要一致快照时复制一次后使用副本，不能重复读取用户内存形成 double-fetch。
- 异步任务优先持有内核副本。若性能确需固定用户页，另行证明 pin/unpin、进程退出、取消、内存失效、DMA 及长期固定约束；仅保存指针或固定页面都不代表内容不会并发变化。
- UAPI 使用明确位宽类型，布局避免本机 `long`、`size_t`、裸指针、enum 和隐含 padding。按需要使用 `__aligned_u64`、显式保留字段及正确的用户指针转换，验证 32/64 位布局及 compat 路径。
- 新接口清零输出和 padding，校验未知 flags、保留字段及长度上界；既有 ABI 先保留已发布语义，不盲目增加会拒绝旧应用的检查。
- ioctl 使用正确方向的 `_IO/_IOR/_IOW/_IOWR` 和类型参数，**不传 `sizeof(type)` 代替类型**。未知命令按接口约定返回 `-ENOTTY` 等正确结果。
- handler 返回值依回调契约，常见为 0/负 errno；不要把所有内核函数一概改为该约定，也不混淆 ERR_PTR 与 NULL。
- 已发布命令不因版本号重新解释旧字段。语义变化使用新命令并保留旧命令；大小可扩展结构需使用子系统既有协议、能力发现和兼容规则，不能只在结构末尾随意加成员。
- 时间表示明确定义位宽、单位、时钟域和绝对/相对语义；避免直接导出本机 timespec/timeval。持续时间/截止时间通常选择单调时钟，持久日历时间按实际需求另行定义。
- 对 read/write/poll/mmap、netlink、sysfs 等也明确权限、阻塞、取消、部分成功和文件/设备关闭后的生命周期；选用已有子系统接口，避免重复造通信协议。

## 文件操作、poll 与映射

- 驱动 `poll` 通常先 `poll_wait` 登记相关等待队列，再以正确同步读取 readiness，避免检查到登记之间丢事件；登记不等于等待就绪，其回调仍可能分配或睡眠，不能据此推定可在原子上下文调用。状态变化先发布再唤醒，返回当前适用的读/写/错误/挂断条件；read/write 在 O_NONBLOCK 下无可用进度且非终态时按契约返回 `-EAGAIN`，不能直接等待数据。
- `flush`、关闭单个 fd、最后 file 引用的 `release` 及设备解绑是不同事件。正常保留 `vm_file` 的映射持有 file 引用，close(fd) 后映射仍在不自动证明 use-after-free；必须追踪实际引用与释放路径，也不能把 file 存活当成物理设备仍可用。
- 映射检查 offset/长度/算术、权限、保护/缓存属性、支持的内存种类及 fork/拆分/失效行为。`vm_private_data` 的所有者可能由 file、独立 VMA 引用或其他明确协议维持；核对初始映射与后续 VMA open/close 的真实调用次数，不能假设初始 `.open` 自动替你取得引用。
- 新映射核对目标树的 `mmap_prepare`/`mmap` 入口及推荐方法，不从旧驱动直接复制平台特定 remap 或 fault 处理。相关 VFS/MM 和总线契约依 [专项原文](../sources/official-docs.md#接口设备与子系统) 读取；module owner、device 引用及 backing pages 的保证分别证明。

## 设备、时间与专项接口

- probe 缺少尚未就绪的依赖资源时核对 `-EPROBE_DEFER`，尽早退出并正确回滚；已创建子设备后不能靠删除子设备再返回该错误，否则可能形成重复 probe 循环。普通永久失败不伪装成延迟探测。
- remove、热拔插及 PM 路径沿用设备模型的依赖关系。核对仍持有 fd、映射、IRQ/DMA 或回调的执行者，不能把设备对象仍存活等同于物理设备仍可用。runtime PM 逐 API 检查引用取得、失败、副作用、回调上下文与对称释放。
- 延迟按目标树的 `fsleep`、`usleep_range`、`msleep`、`udelay` 等接口及精度/上下文限制选择；原子路径与可睡眠路径分开，不将长忙等或固定 sleep 当成完成同步。超时核对时钟域、挂起是否计时、换算和回绕，采用目标树适用的时间访问与比较 helpers。
- sysfs 使用简单文本属性，通常一个值或同类型数组；核对权限、show/store 计数、设备失效和目标树的 `sysfs_emit` 等 helpers。其 ABI 文档要求按 [编码与文档](../principles/coding-and-documentation.md#linux-内核编码与文档) 维护。
- netlink 按所属 family 的属性策略、权限、请求/回复、dump、多播及错误/截断语义处理；不能把一次 recv 当成完整交互。mmap/poll、文件系统、块层、网络、BPF、设备树、总线等只在任务触及时按 [专项来源](../sources/official-docs.md#接口设备与子系统) 读取目标文档、声明及相关调用者，再实现或审查。

## 可观测性、框架与 Rust

- 驱动优先 dev_*，其他路径适用 pr_*；选择日志级别、动态调试与限速。高频诊断按需采用 tracepoint/ftrace 等，勿用 printk 刷屏影响时序。
- 普通无效输入返回错误，不用 BUG/BUG_ON 或 WARN 当验证器。WARN 用于真正预期不可达的内部违约，考虑 panic_on_warn 的影响。
- 驱动优先接入设备模型和已有子系统框架；具体锁/回调契约依文档和调用者取得，不从通用清单猜测。
- Rust for Linux 使用目标树支持的 `no_std` 与 `kernel` 抽象，核对分配失败、锁保护、Pin、FFI 与 unsafe 不变量。C FFI 类型按树内 `kernel` prelude/bindings 规则选择，不默认套用用户态类型；格式、rustdoc 与 Safety 说明按 [内核编码与文档](../principles/coding-and-documentation.md#linux-内核编码与文档)。
- 外部模块没有稳定内核内部 API 保证，支持矩阵需要实际构建和行为证据。
