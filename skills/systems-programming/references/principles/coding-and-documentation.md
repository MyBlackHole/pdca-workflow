# 编码、注释与接口文档

普通系统代码开发使用本页，不额外加载中文补注流程。Linux 内核规范提供设计经验，目标项目、源码版本及子系统风格优先。

## 控制流与表示

- 命名表达角色、单位和状态；使用可局部理解的控制流、明确错误路径和项目已有抽象。函数长度、行宽等遵守目标规则，不为满足通用数量门槛拆出无意义包装。
- C/C++ 语言差异、错误约定与 FFI 见 [用户态适配](../environments/userspace.md)；资源清理见 [生命周期与退出协议](memory-and-locks.md#生命周期与退出协议)，目标内核的新写法按 [C 作用域清理](../environments/kernelspace.md#c-作用域清理) 核对。
- 优先用函数表达可类型检查的逻辑；确需预处理、类型泛化等能力时使用宏，避免隐藏控制流与参数多次求值。位操作和布局技巧检查对齐、端序、位宽及未定义行为，硬件/UAPI 布局与内部结构分开处理。`static inline` 可用于头文件实现、配置桩或替代函数式宏，不以基准为先决条件；为性能加入内联或缓存行填充时才要求相应测量依据。
- 只调整当前逻辑相关的格式和组织；纯重排、语言迁移和更换容器/依赖各有自己的授权范围。格式检查只是辅助，不替代语义证明。

字符串/二进制、长度与缓冲 API、结构布局及回调接口的设计规则见 [数据结构与接口](data-and-interfaces.md)，不以替换为“安全函数”代替边界证明。

## 说明维护者无法直接看出的契约

根据当前对象或接口的风险选择需要说明的事实：

| 对象或接口 | 文档中的关键契约 |
| --- | --- |
| 内存、fd、请求及回调参数 | owned/borrowed/transferred；成功、失败、取消及部分完成后的责任；谁能释放 |
| 共享状态与等待 | 锁或原子协议、可调用上下文、阻塞/重入条件、锁顺序、退出谓词及存活要求 |
| 外部 API/ABI、数据格式 | 长度与单位、布局/端序、错误约定、副作用、能力探测与兼容条件 |
| 非显然的实现选择 | 当前不变量、平台/硬件限制、取舍依据，以及改变条件后需要重新评估什么 |

文档描述实际实现和被证明的契约，不代替实现检查。使用目标项目的 kernel-doc、头文件注释或其他既有格式；不强制 `// 备注:`、固定模板、每个函数列出两个替代方案或补齐 FAQ。

注释解释原因、约束和容易破坏的不变量，不重复明显代码。原注释与代码不一致时核对真实契约，按本次范围修正或明确指出；不能仅因原文是英文就永久保留错误说明。许可证、版权和签署内容遵守其专门规则。

## Linux 内核编码与文档

本用户将 Linux 内核 C 风格选为 C 和 C 风格 C++ 新代码的默认强制风格。AI 必须遵守下列规则；目标树 `Documentation/process/coding-style.rst` 和子系统规则中的明确例外也必须遵守。官方原文用“preferred”等措辞时，按其真实含义保留可读性例外，不得把偏好改写成无条件硬门槛；有目标约束冲突时，说明具体冲突和采用的例外。源码目录、Kconfig、kernel-doc、日志设施等仅用于内核时，不能错误套用到用户态。来源和任务路由见 [官方覆盖映射](../sources/official-docs.md#风格文档与贡献)。

### C 与 C 风格 C++ 的强制风格

- **缩进、空白与行宽**：代码缩进使用 8 列 tab，不用空格代替缩进；注释、文档和 Kconfig help 按各自格式处理。删除行尾空白。80 列是默认可读性目标；只有保持语义清楚或完整用户可见字符串更重要时才超出，不拆碎日志字符串以迁就列宽。长语句拆成语义清楚的块，续行明显缩进并按目标树对齐风格排列；长函数参数列表也按相同原则处理。
- **大括号、switch 与语句**：函数左大括号另起一行，控制语句的左大括号同行；`} else` 和 `} while (...)` 按目标树格式衔接。`switch` 与 `case` 标签对齐，标签下的语句缩进一级。单条简单语句可省略大括号；多语句必须加括号，`if/else` 两侧保持一致。不得将多个语句、赋值或逗号表达式压成一行来隐藏控制流。
- **运算符空格**：关键字后通常留空格；`sizeof`、`typeof`、`alignof`、`__attribute__` 按函数式形式书写。括号内部不加空格；指针 `*` 按目标树偏好贴近变量名或函数名。二元、三元运算符两侧留空格，一元运算符、前后缀自增/自减及 `.`、`->` 周围不加空格。格式检查辅助发现问题，不替代人工审查。
- **命名**：函数和变量使用小写下划线风格；全局符号要能说明职责，局部变量在上下文明确时保持简短。不得以类型信息重复编码名字、制造无意义缩写或为短函数臆造泛化包装。新术语使用清楚且包容的表述；只有为保持既有 ABI/API 或硬件、协议原文而确有必要时才保留旧称。
- **typedef**：不为可直接访问的结构体或指针引入 typedef。只有不透明抽象、确有语义价值的精确类型、Sparse 类型区分或 ABI 明确需要时使用；类型别名必须说明实际目的。
- **函数和声明**：函数围绕一个职责组织，长度按复杂度、缩进和局部状态判断；“一到两屏”及约 5–10 个局部变量只是复杂度警示，不作机械阈值。原型写参数名，不添加无意义 `extern`；声明和定义中的存储类、section 属性、返回类型、函数名、参数及行为属性按目标树规定排序。注意声明与定义中参数属性位置可能不同，不能用一条固定模板改写所有原型。函数之间留一个空行；导出符号宏紧跟函数定义的右大括号。多个失败出口有共同清理时使用语义化标签汇合，并检查各资源获取阶段的释放顺序；可行时用故障注入或针对性测试覆盖失败路径。
- **清理路径**：多个退出点需要相同清理时用语义明确的 `goto out_*` 汇合；没有共同清理时直接返回。不同资源取得阶段使用准确的清理标签，避免空指针释放或遗漏。目标内核若采用 `__free()`/guard 等作用域清理，必须遵循其声明、逆序释放、移交和退出限制；不得与同函数的 goto 清理随意混用。用户态沿用项目可用的显式清理方式。
- **注释**：注释说明代码做什么、为什么这样做、外部无法看出的限制和不变量，不逐行复述实现如何运行；复杂注释优先改进代码结构，函数用途说明通常放在函数开头，函数体内只为隐晦或脆弱约束保留必要注释。长注释采用一致的 C 注释排版；声明各变量独占一行，必要时可逐项说明。公共内核接口使用精确 kernel-doc，避免模板化复述签名；用户态按项目文档格式记录同类契约。
- **整理与格式化**：修复时保持局部 diff，不顺手重排无关文件。格式工具只能按目标树配置辅助检查，不能取代人工审查；不在源文件添加编辑器 modeline、私有编译命令或缩进指令。
- **Kconfig**：仅内核配置文件适用。`config` 下选项缩进使用 tab，help 正文额外缩进两个空格；危险功能在提示中显著说明。依赖、默认值、可见性及 `select`/`imply` 等语义另按目标树 Kconfig 文档核实。
- **结构体与存活**：结构布局和字段应体现真实职责、同步与 ABI 约束。任何可被其他执行上下文发现的对象都必须有显式生命周期证明；存在可独立保留指针的并发使用者时，引用计数通常是默认方案。只有独占移交、访问与销毁严格由同一锁覆盖、RCU/epoch 等方案确实能证明没有悬空访问时，才采用相应替代方案。锁保护一致性，单独的锁不保证解锁后的对象存活；引用计数也不自动保证字段一致性。不得盲目加引用计数，也不得以“有锁”代替生命周期证明。
- **宏、枚举与 RTL**：一组相关常量优先用 enum；常量宏名与 enum 标签使用大写，函数式宏可按目标风格小写。函数式逻辑优先用可类型检查的函数或 `static inline`；未使用参数的宏应改用静态内联函数，不用 `(void)(arg)` 掩盖问题。多语句宏用 `do { ... } while (0)`，参数和表达式正确括号化，避免多次求值、调用者局部变量捕获、隐式控制流、左值宏及常见局部名碰撞。宏常量表达式整体加括号；不要自行重造目标树已有 helpers。RTL（GCC Register Transfer Language）仅在编译器/汇编相关工作触及时按 GCC 专门资料核对。
- **内核日志**：仅内核适用。设备上下文优先使用正确设备和级别的 `dev_*`，无设备上下文使用适当 `pr_*`；驱动正常运行保持安静，调试信息使用动态调试/调试宏。消息拼写正确、准确、简短、可搜索，通常不加句点或无意义括号数字；不无端输出重复错误、地址或用户数据，保留可 grep 的完整消息字符串。
- **分配表达式**：仅内核分配器规则适用。优先采用目标树提供的结构体/数组分配 helpers 和溢出检查；不要重复写 `sizeof(*p)` 以外的脆弱类型名模式，不把 `void *` 强制转换成目标指针，不在分配失败时重复输出已有的栈转储。具体 helper、GFP 与失败处理必须符合目标版本和调用上下文。
- **inline**：不得把 `inline` 当作默认性能优化或为了“更快”普遍添加。宏替换、编译期常量折叠等有明确作用时才使用；其余让编译器决定，需优化收益时提供测量依据。
- **返回语义与名字**：动作/命令函数通常返回错误码，谓词通常返回 bool；计算结果、计数和指针按各自契约定义失败值。名称、类型和调用方判断必须一致；目标 API 的既有语义优先，不能为迎合规则机械改写公共函数。
- **bool**：逻辑布尔值用 `bool`、`true` 和 `false`，不需要用 `!!` 转换。若 ABI、布局、对齐、位宽或 cache line 占用有要求，采用明确的位域/固定宽度类型；多个布尔参数使调用点难读时评估 flags。
- **复用公共宏**：长度、最小/最大值、结构成员大小及数组/柔性数组计算优先使用目标树类型安全 helpers。使用前核对 helper 的溢出、类型、版本及上下文契约，不另造不完全等价的宏。
- **内联汇编**：只有 C 或现有抽象无法表达 CPU/平台操作时才使用；常用片段封装为 helper，较大汇编放 `.S` 并声明匹配的 C 原型及目标 ABI 所需属性（如适用的 `asmlinkage`）。明确输入、输出、clobber、内存/控制效果及 `volatile` 必要性；多指令按目标汇编格式分行。架构特定代码必须读取对应架构规则。
- **条件编译**：优先隔离完整函数并提供契约一致的 stub，避免在函数表达式和深层控制流里散布 `#ifdef`。目标符号存在时优先用 `IS_ENABLED()` 表达普通条件；符号不存在、类型无法编译或代码必须被预处理移除时才使用条件编译。仅在某些配置下未使用的定义按目标规则标注；始终未使用的定义应删除。较长条件块用匹配的 `#endif` 注释。
- **断言与崩溃**：不得用 `BUG*()` 逃避错误处理；仅对无法恢复的重大内部损坏且有充分理由的特殊情形考虑新增使用。`panic()` 仅用于无法继续的特殊启动等场景。`WARN_ON_ONCE()` 通常优先于重复告警，但只用于真正意外、非普通输入可触发的违约，并尽可能提供恢复路径；不能把 WARN 当作常规校验器或前后置条件检查。编译期不变量使用 `BUILD_BUG_ON()` 等编译期断言。

### 内核专属文档和接口要求

- 内核 C 导出 API、模块可见公开头接口及应公开的全局类型按目标树要求写 kernel-doc，准确记录参数、上下文、返回值和成员约束；内存屏障注释说明配对与成立理由。
- 新 ABI/用户接口按接口类型更新对应文档：`Documentation/ABI/`、ioctl 号码表、`/proc`、启动参数、模块参数说明和用户可见文档。先确认目标树既有接口和兼容规则。
- 内核 Rust 使用目标树 Rust 风格和 rustfmt；`unsafe` 块前的 `// SAFETY:` 证明该调用点前提，unsafe 函数/trait 的公开 `# Safety` 契约说明调用方责任，两者不能互相代替。适用时补充 `# Panics`、`# Examples` 和正确链接；C/C++ 风格规则不覆盖 Rust 的语法约定。
- 检查项按 [目标树验证规则](../workflows/validation.md#内核构建与文档检查) 执行；新增/修改文档也要使用目标树相应 Sphinx/kernel-doc 构建入口。

## 图示与验证

所有权转移、状态机、锁依赖、设备停止或数据布局用文字难以审查时，可增加简短图示。标签使用真实状态、函数、字段或业务概念中最准确的一种；包含相关失败/取消/退出路径。不按步骤数强制配图，不为画图重构代码，也不假定源码中的 Mermaid 会被自动渲染。

性能结论按 [性能证据与交付](../workflows/validation.md#性能证据与交付) 区分结构变化、推导和实测；源码中不写一次性调试流水账。

检查注释是否仍准确、公开声明与实现是否一致，以及改动是否误触代码、宏续行、编译指令或文档生成格式。中文项目/专门中文补注任务另按 [可选中文约定](project-conventions.md) 采用相关部分。
