# 共同工程原则

本文件将内核经验迁移到系统开发；不是声称所有用户态项目都必须采用内核实现。官方依据见 [资料索引](../sources/official-docs.md)。

## 从优点到具体决策

| 内核工程经验 | 在当前改动中落实 | 需要避免的机械移植 |
| --- | --- | --- |
| 简洁、可局部理解 | 函数职责集中、少嵌套、命名说明角色、注释解释约束与原因 | 函数行数硬门槛、为缩短函数拆出无意义包装 |
| 子系统与机制复用 | 使用项目或平台已有接口，以 ops/回调隔离真实变化点 | 只有一个实现却提前造通用框架、复制内核容器到所有项目 |
| 明确生命周期 | 创建、发布、借用、转移、回收各有契约，释放与取得成对 | 引用计数替代同步、依赖“调用者应该不会并发” |
| 并发可推理 | 每份共享状态指定锁或原子协议，约定锁顺序及退出过程 | 仅加 volatile、每字段加原子但缺少整体一致性 |
| 外部接口长期可用 | API/ABI、格式、错误码、时序、旧客户端有回归证据 | 为内部重构改变公开布局、把内部内核 API 当稳定 ABI |
| 架构与配置可移植 | 处理端序、对齐、位宽、溢出、不同 CPU 内存序及配置 | 仅在 x86/64 位/单配置成功就声称通用正确 |
| 数据驱动性能 | 先测热点，再评估批处理、局部性、锁粒度及数据结构 | 无基准的自旋、RCU、内联、分支提示和零拷贝 |
| 故障可诊断 | 有界等待、可恢复错误、关联上下文、适度日志及追踪点 | 热路径刷日志、失败被吞、用户输入触发断言崩溃 |
| 可审查的小改动 | 单个逻辑目的，修复与无关重排分离，保留可二分定位能力 | 无授权提交/推送、顺手大规模重构 |

## 资源、状态与错误

- 为 fd、内存、映射、锁、队列项、线程、设备请求标明 owned/borrowed/transferred。接口成功及失败分别说明所有权；返回错误不等于没有产生副作用。
- 初始化对象完成后才发布；移交异步执行者前取得有效引用，或明确转移唯一所有权。从共享表取得对象时，查找与取引用必须受到存活保护。
- 资源按依赖逆序清理。C 与 C 风格 C++ 采用项目已有的显式清理方式；多项资源共享退出路径时可用有语义的 `goto out_*`，单资源失败可以直接返回。目标内核 C 已采用作用域清理时遵守其声明/释放顺序和所有权转移机制，见 [源码与规范比对](../sources/mainline-reading.md)，不要机械改回手动 unwind。C++ 的跳转不能越过不允许跨越的初始化。
- 保存原始错误，清理操作不能覆盖它。区分可恢复失败、超时、取消、部分完成、永久失败；重试需要截止时间、次数/预算和幂等性依据。
- 异步对象退出采用依赖顺序：阻止新工作 → 同步仍可生产工作的来源 → 取消或等待在途活动 → 收敛引用 → 释放。具体中断、定时器、工作项和设备停止的顺序由依赖图确定；不能只 flush 一次便假定永远不会再入队。
- 队列和重试有上界，约定背压、满队列策略与丢弃责任。超时后不能释放仍被后台使用的参数；取消成功的定义须区分“已请求”和“不会再回调”。

## 并发证明

对变更涉及的共享对象回答：

1. 哪些执行者读写它？中断、回调、取消、析构是否也包含在内？
2. 什么保护状态一致性，什么保证内存可见性，什么保证对象存活？三者可由不同机制承担。
3. 锁的顺序及范围是什么？持锁期间哪些操作可能阻塞、回调或重入？是否等待一个同样需要该锁的执行者？
4. 使用原子时，指出发布者、接收者及 release/acquire 配对；复用数据还需反向交接。引用计数不能保护对象内部可变字段。
5. 停止/超时如何唤醒等待者？最后一个读者或回调何时结束，之后才可以回收什么？

默认选择能证明正确的简单同步。RCU、seqlock、无锁结构要补充适用工作负载、内存序、重试/饥饿、回收及 ABA 分析。内核 LKMM 与用户态语言内存模型分别核对，不能逐行替换宏来移植。

## 数据边界、安全与可移植性

- 每个边界先验证长度、计数、偏移、权限及允许的状态。先检查加乘溢出再分配/访问，限制总量与并发量，覆盖零值和最大值。
- 区分本机内部类型与外部表示。外部二进制格式明确位宽、端序、填充和版本/能力机制；不要直接将含指针的内部结构写到磁盘或网络。
- 不依赖未对齐强转、违反别名规则的访问、未定义的移位/溢出或编译器恰好生成的指令。地址空间、CPU 地址和设备地址不能互换。
- 配置禁用、可选功能不存在、硬件能力不足都是正常分支。敏感信息不进日志，权限在真正使用资源的边界执行；与本次改动无关的安全机制不扩展实现。
- 解释“不支持/未验证”与“不可能”之间的区别；不要将旧文档中的历史规则当作当前子系统事实。

## 编码、文档与协作

- 遵循已有命名和组织方式。注释与公开接口文档按 [编码与文档](coding-and-documentation.md) 说明本次必要的契约；不强制前缀、配图或保留已失真的说明。
- 使用可读控制流和现有容器/算法；宏仅用于有必要的编译期能力，避免隐藏控制流与参数多次求值。内联和缓存行填充需要测量依据。
- 改动及补丁描述说明问题、原因、方案和验证，准备 Git 提交按需使用 [提交与变更说明](../workflows/git-commit.md)。上游内核提交再核对 MAINTAINERS、补丁格式、DCO 和子系统流程；不得代用户声明未确认的签署或自动向外发送内容。
