# 内存与锁设计

设计、实现或只读审查涉及分配、缓冲区、异步对象、共享状态或同步路径时使用。本页维护资源生命周期、预算与同步设计的详细规则；接口错误语义见 [共同原则](engineering.md)，具体原语遵守 [用户态](../environments/userspace.md) 或 [内核态](../environments/kernelspace.md) 的约束。

## 从工作负载主动选方案

从调用者、数据流和现有指标确认对象大小/频率、并发数、谁持有多久、延迟和内存要求、允许阻塞的上下文。未知的容量/负载参数写成待确认的配置或推导条件，不捏造项目数值。先修生命周期与资源失控，再依据瓶颈选择性能优化。

## 生命周期与退出协议

画出或简述对象流转：创建 → 构造/校验 → 发布/入队 → 执行/借用 → 完成/取消 → 回收。为 fd、内存、映射、锁、队列项、线程和设备请求标明 owned/borrowed/transferred，说明成功、失败及部分完成后由谁释放。

- 完成初始化后才发布。移交异步执行者前取得有效引用或转移唯一所有权；异步边界不能借用调用者随时可改写或释放的 buffer。从共享集合查找到取得引用期间必须保护对象存活。
- 能证明独占、唯一所有权移交，或统一所有者在全部使用者结束后回收时，不因跨线程可见就新增共享引用计数。确需共享引用才采用相应机制；移交已经持有的引用也不必先增后减。前提是移交者不再访问，失败/借用/退出路径均有明确责任，目标 API 的强制引用规则仍须遵守。
- 资源按依赖逆序清理。C 与 C 风格 C++ 沿用项目显式清理方式；多项资源共享退出路径时可用有语义的 `goto out_*`，单资源失败可直接返回。C++ 跳转不能越过不允许跨越的初始化。目标内核 C 的作用域清理按 [内核规则](../environments/kernelspace.md#c-作用域清理)，不机械改回手动 unwind。
- 停止采用依赖顺序：阻止新工作 → 同步仍可生产工作的来源 → 取消或等待在途活动 → 收敛引用 → 释放。中断、定时器、工作项和设备的具体顺序由依赖图确定；一次 flush 不能保证以后不再入队。
- 区分“取消已请求”和“不会再回调”。超时后仍被后台访问的参数不能释放；明确最后使用者结束的条件，再回收其依赖对象。

## 内存：先所有权和预算，再分配器

| 当前需求或现象 | 优先评估的方案 | 选择前要证明的条件 |
| --- | --- | --- |
| 对象只属于当前调用/父对象 | 自动存储、内嵌或一次分配容纳头与数据 | 栈/父对象生命周期和容量允许；总大小、对齐、溢出检查正确 |
| 已有清晰单一消费者 | 转移所有权、借用不可变视图或批次独占 | 所有失败/取消路径明确；引用不超出有效期；不为了少一次复制制造悬空指针 |
| 一批对象一起结束 | 现有批量分配/arena 等生命周期分组 | 没有对象越过整批回收点；峰值、对齐、部分失败和释放时机可控 |
| 高频固定大小对象或不可睡眠路径 | 预分配、有界池、目标树适用的对象缓存 | 有测量或上下文/进展要求；容量、耗尽、跨线程回收、退出及闲置保留可解释 |
| 低频变长对象 | 普通可失败分配，必要时合并头/数据 | 通常更易维护；不能仅因“内核有 slab”就自建用户态 slab |
| 多执行者确需同时持有 | 引用计数或受锁保护的共享对象 | 无更简单的唯一所有权；取得引用时尚存活，内部可变状态另行同步 |

有界队列同时评估条数和字节，约定背压、满队列策略与丢弃责任；预算覆盖**构造中的生产者、排队项、在途项、外借/延迟回收项和缓存保留**，不能只算链表长度。区分逻辑有效字节、分配容量/元数据与实际 allocator/RSS 高水位；不要把逻辑额度声称为精确 RSS 保证。

需要严格限制并发分配时，在分配之前预留额度；用互斥或等效协议使“检查 + 预留”不可竞态。锁外分配后重新检查停止/状态并提交；失败、停止或取消时，已分配对象真正释放后才退还额度，尚未分配的预留可直接退还。对象从排队移到在途只是所有权迁移，不能提前退还仍占用内存的额度；同一对象也不能在预留与实际占用中重复计费。等待容量者必须能因停止/超时醒来。

资源不越界与业务能继续前进分别验证。替换、扩容或回收可能同时保留新旧对象；明确满额后能否更新、需要多少临时余量，以及何时能恢复准入。按业务选择复用、预留余量、串行化或明确拒绝，不默认要求所有满额替换成功，也不能只用峰值合格证明长期运行可用。

检查分配/复制热路径，评估合并分配、复用现有缓冲和批处理。只有确认内容稳定、接收者存活、完成/取消均可追踪时才考虑零拷贝。池化、缓存和分片需评估碎片、闲置内存、缓存行争用、NUMA 及复杂度；没有相关需求时保留简单分配。

## 锁：先减少共享，再缩小临界区

为每份相关共享状态列出全部执行者，包括中断、回调、取消和析构；分别说明状态一致性、内存可见性和对象存活的保证，再确定上下文、持锁允许操作、锁顺序及退出。能独占或通过消息转移的状态优先减少共享。

| 情形 | 设计选择 |
| --- | --- |
| 多生产者提交、单消费者处理 | 简单队列锁保护链接、计数和停止状态；出队后由消费者独占处理 |
| 慢 I/O、分配、复制、外部回调延长持锁时间 | 评估锁外准备/执行 + 锁内校验提交；移出前补齐引用/独占、状态复查及提交一致性 |
| 合法的可睡眠 mutex 路径 | 核对回收、fault、回调和反向锁依赖；持 mutex 时睡眠本身不是正确性错误 |
| 锁等待已被证实是瓶颈 | 再评估批量摘取、按对象/键分片、读写锁；比较单锁成本和新增顺序、饥饿及内存代价 |
| 必须原子操作或拟用无锁/RCU/seqlock | 先说明简单同步为何不足，再证明下述发布、回收和进展协议 |

`volatile` 不提供同步，引用计数不保护内部可变字段，普通原子变量也不自动组成安全算法。原子承担发布或所有权交接时，明确一致性单位、线性化/发布点及发布者与接收者的 release/acquire 等实际排序协议；复用数据还需反向交接。独立统计计数按可观察契约可采用 relaxed 等较弱排序，不能用它发布其他数据或把多个独立读取当作一致快照。无锁、RCU、seqlock 另分析工作负载、重试/饥饿、回收及 ABA。内核用法进一步核对 [复杂读侧同步](../environments/kernelspace.md#复杂读侧同步)；LKMM 与用户态语言内存模型分别验证，不能逐行替换宏移植。

任何锁外操作都要回答：解锁后对象会被谁释放/替换，结果提交前哪些状态会变化？以有效引用、所有权交接等保证对象存活，另用所需的锁或原子提交协议保持操作一致性；提交时复查真正依赖的停止、版本等状态。顺序服从接口的线性化点或业务版本契约：相互重叠的无条件全量替换可按原子发布点排序，不能仅因构造开始较早就强加代际检查；确有过期拒绝要求时才建立相应校验协议。

区分互斥与等待：条件变量/waitqueue/completion 等等待完整状态谓词，覆盖停止、超时和取消。join/cancel/flush/回调若依赖同一锁，要调整等待点或协议；不要通过盲目换成自旋锁、recursive mutex 或 raw 锁掩盖设计错误。

## 联合示例：变长消息发送队列

场景：多个生产者、一个发送者，消息发送期间必须有效，停止要与在途操作收敛。一个可优先评估的基础设计是：

1. 模块具有固定配置的消息大小上限、条数/字节额度及停止策略。提交者先登记在途提交并在状态锁下检查状态、预留额度，再锁外分配“头 + payload”并复制；分配失败释放预留，停止后不再提交新消息。
2. 准备完成后锁内复核停止状态；成功则将所有权和额度记账责任转给队列，失败则由提交者释放并退还额度。唤醒消费者/容量等待者时遵守同一谓词协议。
3. 消费者锁内摘取，锁外处理 I/O；消息在其独占期间仍计入预算。移交异步后端仅转移所有权及记账责任，同一模块预算内须到消息真正释放后才归还额度；跨预算转移要先由接收侧成功预留并承接，再归还发送侧额度。短操作、失败及取消均只完成一次消息，不重复释放或重复记账。
4. stop 关闭入口并唤醒等待者；按排空或丢弃契约处理队列及在途提交，向可能永久阻塞的 I/O 提供有效中止机制或有界等待，等待所有执行者结束后销毁共享状态。调用方也须遵守模块句柄存活契约。

这解决锁内阻塞、异步 buffer 存活、并发分配失控和提前释放，性能收益另行测量。基线不足时保留普通分配和单把队列 mutex；不自动加入内存池、分片或无锁队列。

## 将设计落实为验证

- 暂停生产者于“已预留未分配”和“已分配未提交”，并发触发容量耗尽/stop，检查额度、所有权和唤醒均收敛。
- 暂停消费者于“已摘取未完成”，检查该消息仍计入预算且不会被 stop 提前释放；测试真正阻塞时能否停止。
- 注入取得资源/提交失败；检查不重复释放、额度不泄漏、共享对象不比使用者先销毁。
- 缩小锁范围时安排并发替换/取消/重入交错，验证状态复查和提交契约；保留合法 mutex 路径作为避免误报的反例。
- 性能候选按 [改动验证](../workflows/validation.md) 对比分配次数、峰值内存、锁等待/持有时间及业务吞吐/尾延迟，区分结构性改进和已测得的收益。
