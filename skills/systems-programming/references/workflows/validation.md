# 改动验证与性能证据

先找项目已有构建和测试入口，只运行与改动和风险相关的检查。不能将格式检查等同于语义正确，也不能把压力测试无报告当作并发证明。

本页回答“当前改动应运行什么检查、如何取得和记录证据”。完整测试策略、框架与覆盖规划使用 [测试策略](testing-strategy.md)，通用 diff/PR 审查流程使用 [代码审查](code-review.md)；普通资源改动不因此自动展开完整策略或通用审查流程。

## 输出目录约束

编写或运行测试时，**不要在 `/tmp` 创建或写入测试文件、临时目录、日志、构建产物或缓存**。优先使用当前项目已有输出目录。

运行前确认构建器、编译器、测试框架、UML/QEMU、sanitizer 和子进程的临时文件行为。可配置时，将 TMPDIR/TMP/TEMP、缓存、日志和显式输出参数指向工作区的已有目录或专用验证目录。不能仅因设置 TMPDIR 就假定所有工具均遵守；已知硬编码 `/tmp` 且无法重定向的测试不运行，说明原因。不要为了验证该限制而先让测试往 `/tmp` 写一次。

## 选择验证

| 变更风险 | 用户态 | 内核态 |
| --- | --- | --- |
| 风格/编译问题 | 目标 C/C++ 模式、现有告警与静态分析；Rust fmt/clippy 按项目配置 | 目标 Kbuild、变更相关 W=1 告警、checkpatch；C=1 sparse（工具可用时） |
| 越界、释放、未定义行为 | 针对性测试及适用 ASan/UBSan/LSan | KUnit/集成场景及适用 KASAN/UBSAN/KFENCE |
| 数据竞争/锁 | 并发回归和适用 TSan；核对同步证明 | lockdep、KCSAN、相关上下文/锁调试配置 |
| 内核内部逻辑 | 可复用纯逻辑在其真实环境测 | KUnit 适合内部单元/白盒路径 |
| 系统接口与设备行为 | 客户端行为、协议和错误约定 | kselftest/既有集成测试，真实 UAPI 和设备路径 |
| 资源耗尽与回滚 | 分配/I/O 失败注入、容量和退出测试 | fault injection、probe 失败、热拔插/解绑、队列取消 |
| 性能 | 同一条件下对比代表性工作负载 | 同配置/硬件/负载下对比，按需 perf/追踪和锁竞争分析 |

这是可选工具映射，不要求每次全部启用。不同 sanitizer/config 可能需要分别构建运行；支持程度以目标工具链/架构为准，不强行组合全部开关。

## 内核构建与文档检查

内核变更按目标树提交检查表和子系统 CI 要求列出适用矩阵，声明满足上游流程前逐项对照 [官方检查表](../sources/official-docs.md#构建与配置)。普通用户态或无关文档修改不启动该矩阵。

- 新增/修改配置覆盖相关 n/m/y、依赖启闭、built-in/module 组合；核对实际 `.config`、编译、链接和 modpost。按检查表要求评估 `allnoconfig`、`allmodconfig`、独立 `O=` 输出及相关架构/字长/端序；不将一个模块配置通过推广到全部组合。
- 编译器、SMP、抢占、RT 和调试配置按目标树支持情况及清单执行；包括要求的 lockdep、RCU/对象/原子上下文等检查。区分可合并与冲突配置，未具备工具、硬件或运行条件的项列为未验证，不能改写为不适用来声称全通过。
- kernel-doc 校验公开源文件和头文件；额外编译告警检查未必覆盖头文件文档。Documentation 改动按目标树构建相应 `htmldocs`/其他要求的输出，修正本次新增的告警。Rust 格式、文档和测试使用树内入口，不另建普通 Cargo 应用。
- 同步执行本次行为相关的 KUnit、kselftest、设备/ABI 或故障注入场景。静态配置、构建成功、工具无报告与运行行为各有证明范围。

以上命令也受 [输出目录约束](#输出目录约束) 限制；运行前核对子工具，不能取得的证据如实报告。

## 有意义的场景

从本次改动选择适用项，不为纯格式或低风险文档改动新增业务测试。设计新用例时按 [单项测试的质量](testing-strategy.md#单项测试的质量) 核对断言与交错；使用既有检查不因此重做完整测试规划。

- 正常输入与最小/最大/越界输入；长度加乘溢出、无效标志、权限和坏地址。
- 每个相关资源取得失败时的回滚；验证错误码、剩余所有权和资源平衡。
- 额度与锁范围改动的针对性交错和断言见 [将设计落实为验证](../principles/memory-and-locks.md#将设计落实为验证)；在候选实现上执行并记录结果。
- 并发生产/消费、重复使用、关闭/取消/超时、回调与释放竞争。
- 重试期间维持原截止时间；部分完成不重复提交具有副作用的操作；超时后后台访问仍受生命周期保护。
- 内核改动涉及上下文时覆盖相关 RT/非 RT、SMP、抢占及实际支持配置；不要为无关变更盲目跑完整矩阵。
- ABI 变化覆盖旧应用/新内核、相关新应用/旧内核的探测/降级、32 位 compat、布局及保留字段；架构与硬件不足以验证的项列为未验证。
- 设备相关覆盖 probe 失败、解绑/卸载、IRQ/work/timer/DMA 在途和相关 suspend/resume 生命周期。
- 采用容器、事件通知或可复用句柄时安排相关交错：查找后删除、遍历时修改、旧 ID 完成落到新请求、登记前后就绪、completion 超时/复用及 timer/work 重新生产。普通正确用法和 API 已有引用保证也作为避免误报的对照。
- 文件/映射变更按实际契约检查非阻塞、dup/fork、关闭 fd 后继续映射和最终解除映射；VFS 生命周期不能仅靠直接调用 `.release` 的替身证明。DMA、总线顺序和真实设备停止的结论需要相应平台证据，纯软件测试不能单独证明。

## 性能证据与交付

区分可由实现证明的结构变化、带条件的推导与实际性能测量；没有数据时给出前提和验证方法，不将候选优化写成已测收益。记录同等条件下的基线与候选值，包括负载、并发、运行次数和波动；按目标报告吞吐、p95/p99 延迟、CPU、内存或锁竞争。诊断开关导致的开销与正式测量区分；优化收益与饥饿、复杂度、内存和尾延迟代价一起评估。

交付说明包含实际命令或可定位的测试入口、结果、配置/环境及未覆盖项。失败和未运行都如实记录。提交/推送/邮件发送仍取决于用户授权，不由此技能自动触发。
