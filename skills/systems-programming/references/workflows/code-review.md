# 代码变更审查

用于明确的 diff、PR 或代码审查任务。审查只输出发现和建议；修改代码需要相应授权。普通实现自检与当前风险相称，不自动展开全仓审查。

## 先固定对象

确认需求、基线/候选版本、差异范围及目标项目规则，从允许的文件与调用链获取必要上下文。区分本次引入、原有问题和范围外建议；不因 diff 中出现一个关键词就加载所有领域资料。

审查面向 Linux 上游的贡献时，同时采用 [内核贡献流程](kernel-contribution.md) 的原文和政策要求；目标内核的格式与文档、配置及验证分别由对应专题维护，不把通用审查通过等同于已满足上游提交条件。

## 审查路径

1. 核对行为：需求是否满足，公开 API/ABI、错误、副作用、顺序和兼容契约是否保持；实现是否含未经授权的扩展。
2. 沿实际调用者和状态转换检查正常、失败、取消及清理路径，跨文件核对声明、布局、配置和消费者。
3. 根据可触发风险深入：资源与并发读 [共同原则](../principles/engineering.md) 和 [内存与锁设计](../principles/memory-and-locks.md)；攻击面读 [安全边界](security-review.md)；构建读 [构建与依赖](build-and-dependencies.md)；测试证据读 [改动验证](validation.md)。
4. 检查测试是否观察真实行为、是否触达目标分支；已有通过结果能支持什么、仍缺什么。压力测试或工具无报告不替代生命周期和同步证明。
5. 先报告有证据的正确性、生命周期、安全和兼容问题；性能结论需要负载及数据，再按项目要求处理风格与维护性。

## 应用项目实际使用的设施

语言清单用于识别风险，不要求引入新设施。C 风格 C++ 禁库路径检查显式资源责任和现有 C 同步，不因未使用智能指针、异常或模板而判错，也不建议新增 C++ 库。已有其他项目设施按用户和目标项目约束处理，不附带全仓迁移。

内核及 no_std Rust 使用目标树类型，不强制用户态 std::error::Error、异步运行库或独立 Cargo 构建。Go/Python 等沿用项目错误、取消、资源和测试约定；不把语言习惯当作已经发生的缺陷。

## 形成可执行发现

每项发现给出具体位置、触发条件、失败机制、影响、证据及修复方向。严重度依据影响与可达性：数据破坏/越权/崩溃等实质后果优先，纯风格单独标明。

无法证实的担忧写清成立条件和待验证项，不将关键词命中、可能优化或个人偏好写成确定 bug；不编造行号、运行结果或性能收益。

没有发现时说明审查范围、实际验证与重要缺口，不将其表述为整个项目无缺陷。输出长度随实际发现决定，不按固定分钟数、检查项数或预设模板扩张。
