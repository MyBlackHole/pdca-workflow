# 根因调查与验证

用于实际 bug、构建失败、测试失败或异常行为；不是普通开发的固定前置审批。本页提供独立完整的方法，不依赖其他调试技能或插件。

## 从症状形成证据链

1. 固定症状、期望行为、输入、版本、配置和观察条件。沿错误码、日志、调用链和最近相关改动寻找发生边界，先区分事实、推测与信息缺口。
2. 优先使用项目既有入口得到最小、能观察精确症状的复现。先检查测试输出、临时目录、日志及缓存行为；不向 `/tmp` 写入，能重定向时使用工作区目录，不能避免时不运行并说明限制。
3. 无设备、生产专属或偶发问题不能本机复现时，继续分析已获准读取的 trace、正常/异常样本及状态机；明确结论尚未验证，不把复现命令作为开始分析的硬门槛。
4. 用事件、请求标识、状态和资源归属重建时间线。时间上相邻、某次变更后出现或一次压力测试没复现，都不足以单独证明因果关系。

## 假设与实验

- 根据已有证据选择当前最值得检验的假设，写明支持/反驳证据、预期观察和最小实验；假设数量由问题决定。
- 一次实验改变一个可辨别因素，优先消除替代解释。负例要实际触达目标条件，不能被前面的参数检查拦住。
- 已授权范围内的常规实验继续推进，无需为每个假设或既有测试边界重复请求确认。设备操作、生产变更、外部发送和破坏性动作仍须具备对应授权。
- 诊断只收集必要数据，隐藏凭证和个人信息；不要整包输出环境变量、请求体或密钥材料。临时诊断改动需有范围，结束时只清理自己产生的产物。

## 修复与可信程度

根因与故障路径有足够证据关联后，修复导致错误的条件，优先补上能区分修复前后的回归检查。缺少执行条件时，可以提出带前提的修复建议，但不得将它写成已确认根因或已验证修复。

验证复现入口、相关回归及受影响契约；无需无差别运行全部测试。保留已有代码、用户修改和有用证据，不为重演测试顺序删除业务实现，也不制造红灯。

输出说明症状、因果证据、修改或建议、实际检查和未覆盖项。静态分析、条件推断、复现成功及验证通过分别标注。

涉及所有权、内存预算、锁和异步退出时读取 [内存与锁设计](memory-and-lock-design.md)，按实际环境核对用户态/内核态契约；需要重新设计测试体系时读取 [测试策略](testing-strategy.md)。只按具体任务读取。
