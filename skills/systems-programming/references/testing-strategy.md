# 测试策略与覆盖规划

用于测试体系、框架、覆盖范围及 CI 成本规划。当前改动的回归和诊断工具选择见 [验证与审查](verification.md)；不因每次普通实现重新设计整套测试体系。

## 从风险到可观察行为

列出本次需要保证的行为、外部契约和失败代价，再选择能观察它们的最小有效边界。优先项目已有测试入口和确定性断言；覆盖正常、错误、边界及相关并发/退出路径，不把测试数量或行覆盖率当作质量证明。

| 要验证的行为 | 候选方式与成立条件 |
| --- | --- |
| 纯逻辑、解析、算法 | 单元/示例/属性测试；独立预期值或不变量，随机测试保存种子及最小失败样本 |
| 组件交互、文件/网络/设备接口 | 集成或契约测试；关键行为需使用真实实现核对，替身不能证明真实协议兼容 |
| 用户关键流程 | 少量端到端场景，覆盖无法在更低层证明的链路；没有用户流程的组件不硬加 E2E |
| 资源、并发、取消和故障恢复 | 明确屏障/事件控制交错，失败注入及收敛检查；不能只靠 sleep 或一次压力测试 |
| 工具可检测的未定义行为/竞争 | 支持平台上的 sanitizer、race、内核诊断配置，区分构建组合和检测能力 |
| 吞吐、尾延迟和占用 | 同条件基线、代表性负载、波动及取舍；诊断模式不直接作为发布性能 |

单元/集成/契约/E2E 比例由系统结构决定，不给所有项目套固定百分比。覆盖率用来寻找重要行为缺口；目标应有风险和维护依据，不设统一下限或上限。变异测试用于评估关键断言的辨别力，按成本选择，不要求每版本全量运行。

## 真实依赖与替身

- 使用 Stub 控制外部结果、Spy 记录观察、Mock 验证确实属于契约的交互、Fake 提供轻量行为；按要证明的事实选择，不要求每个外部输入都做 Stub。
- 不 mock 正在测试的实现或内部细节来重演同一算法。真实依赖关键语义由契约/集成场景补充，不能以 Fake 通过证明真实存储、网络或设备行为。
- 为时间、随机、调度或故障设置可控入口时沿用已有公共边界，不仅为测试暴露所有静态函数或扩张产品 API。已授权实现/测试且边界明确时无需逐项确认。

## 语言、目标与工具

| 项目环境 | 选择依据 |
| --- | --- |
| C / C 风格 C++ | 现有 C 测试入口或驱动；禁 C++ 库时不加入依赖 STL 的测试框架。资源清理遵守真实生命周期，不为测试默认引入 setjmp/longjmp |
| Rust 用户态 | 项目现有 test/doctest/integration 入口；属性、fuzz 和基准只在有相应目标时配置 |
| Rust 内核 / no_std | 目标树支持的测试和错误类型，不照搬普通应用 Cargo、用户态运行时或 std 框架 |
| Go | 既有 testing、表驱动和接口场景；race 需目标/工具链支持，不能支持时记录缺口并选择可行补验 |
| Python | 沿用项目现有框架、异步模型及 fixture 生命周期；不因通用偏好迁移框架或安装整套插件 |

先确认编译器、架构和工具的可用性及组合限制，不能无差别同时开启所有 sanitizer。不能执行的配置如实列为未验证；替代场景的证明范围单独说明。

## CI、稳定性与证据

按失败反馈速度和风险安排快速检查、相关集成、平台矩阵及周期性高成本检查。若跨组件变化需要集成证据，应在作出合并/交付结论前取得，不能仅因模板写了“合并后运行”就延后必要验证。

偶发失败先保存最小输入、环境、种子、日志和事件顺序，按 [根因调查](debugging.md) 分析。使用状态屏障、可注入时钟和适当隔离修复原因；不能仅重试至绿或以固定“连续一百次通过”宣称修复。是否隔离某项测试由项目策略和风险决定，保留原始失败及后续跟踪。

每项计划说明行为/风险、测试层次、真实依赖或替身、运行入口、环境、输出目录、预期证据及暂不能覆盖的条件。测试与子进程的临时文件、缓存、构建和日志必须可落在工作区；不写入 `/tmp`，无法重定向的命令不运行。

需要测试先行方法时读取 [TDD](tdd.md)；构建运行器和依赖配置见 [构建与依赖](build-and-dependencies.md)。
