# 源码与规范比对

用于从本地 Linux 主线/目标树提炼工程方法，或判断一个新写法能否用于当前项目。结合 [内存与锁设计](memory-and-lock-design.md)、[内核约束](kernelspace.md) 和 [资料索引](sources.md)，不要仅凭出现次数或某个驱动的写法建立规则。

## 固定真实来源

- 记录源码根、实际远端、分支、完整提交、Makefile 版本及所读文件的本地差异。主线、稳定版和 linux-next 分开识别；发布日期、分支名或“目录叫 linux”不能证明是最新主线。
- “最新”只表示某个核验时刻的远端/本地状态。记录该时刻与实际取得的提交，不能把之后移动的 master 链接当作永久证据。
- 遵守项目允许的读取范围，先选择明确文件；不为找例子扫描无关工作区。浅克隆足以读固定快照，不能据此宣称已调查完整历史。

## 每条结论的证据链

| 证据层 | 要回答的问题 |
| --- | --- |
| 同提交 Documentation | 它是要求、推荐、历史说明，还是专为演示错误的反例？ |
| 声明与实现 | 配置、执行上下文、返回值、排序、取得/释放后的对象存活约束是什么？ |
| 具体调用者 | 为什么选该分配器、锁或清理方式？发布、失败、取消和回收是否完整？ |
| 当前任务 | 上述成立条件是否在目标版本、架构、工具链和用户态/内核态仍成立？ |

优先对比同提交树内文档，再比官方在线资料。发现差异先核对版本、实现与调用路径；不能自动以“代码存在”否定规范，也不能以最新文档要求旧树调用不存在的 API。注明差异、适用条件和未决问题，避免将历史代码的缺陷、特殊上下文或调试用法推广为最佳实践。

文档若仅包含 kernel-doc/include 指令，沿已获准的精确路径读取被引用的正文或 API 注释；不能只读这个入口文件就认定已核对完整规范。

记录“规范位置 → 源码文件/符号/提交 → 观察 → 可迁移原则 → 限制”。保持引用简短，不把内核源码大段复制进技能，也不让技能依赖某台机器上的绝对路径。

学习“锁外遍历”要逐把确认实际释放与继续持有的锁，并追踪并发删除、回调新增项和重新合并协议；不能把释放队列锁概括为完全无锁。学习内存记账则追踪分配容量、在途持有和析构回收，区分流控阈值与严格配额；源码中的一次阈值检查不自动证明并发硬上限。

## 值得核对的现代 C 机制

目标树支持、子系统接受且工具链满足时，评估内核 C 的作用域清理：`__free()`、`guard()`/`scoped_guard()`、`return_ptr()` 等。它们是 C 的清理抽象，不依赖 C++ 库。旧树或普通用户态工程继续采用其现有清理机制，不为模仿主线强行移植宏。

- 清理按声明逆序发生，变量应在真正取得资源的位置定义并初始化；需要持锁的对象清理必须在锁释放之前发生。
- guard 持锁持续到对应作用域结束，不能只看源码中“最后一次使用锁”的位置；用清晰作用域控制范围。
- 成功返回或移交对象时用目标树适用的所有权释放标记，避免自动清理释放已经交付的对象；失败路径仍正确清理。
- 按该机制的官方要求选择函数内一致的退出方式，避免在同一函数混用跨作用域 goto 清理与自动清理造成重叠释放或错误顺序。
- 自动释放只解决当前作用域的清理，不替代异步引用、取消、IRQ/work/DMA 收敛或对象退出协议。

## 核对锁和内存的隐藏契约

- mutex 解锁的内部发布点不代表 `mutex_unlock()` 已结束访问锁结构。对象和其中的 mutex 必须至少存活到解锁调用返回，并收敛其他使用者；观察到锁空闲不构成回收证明。
- 用户可触发的内核分配要核对已有 memcg/kmem 归属及子系统计量；服务自己的字节预算不能替代系统资源计量。按上下文和目标树选择适用的 `__GFP_ACCOUNT`/`GFP_KERNEL_ACCOUNT` 等机制，不重复计量或破坏不可睡眠约束。
- 非睡眠分配区分可失败的 NOWAIT 路径和确需消耗保留资源的 ATOMIC 路径；“不睡眠”不代表 NMI、PREEMPT_RT 下持 raw 锁/禁抢占等上下文均可调用分配器，需核对其内部锁与具体上下文限制。
- PREEMPT_RT 下释放内存也可能涉及分配器内部锁；分配与释放都核对调用上下文，必要时将实际回收延后到允许的执行环境。
- mempool 的 `min_nr` 是保留元素数，不是最大活跃分配数；常规分配先尝试底层分配器，失败再使用保留。硬字节上限仍需独立预算；进展取决于资源需求、并发和等待依赖，不能仅看“用了 mempool”。
- 涉及回收的工作依赖，要核对 NOFS/NOIO 作用域、workqueue 的回收进展保证与相互等待；内存池、rescuer 或 `WQ_MEM_RECLAIM` 各自不能自动消除所有资源/锁循环。

看到 `kmalloc_obj`、数组/柔性数组等类型化分配 helper 时，核对目标树实现、默认 GFP、溢出和计数字段规则；不能只因调用变短就默认适合原子路径，或要求旧树增加该 API。

这些是需要核对的决策点，具体机制以目标树契约为准。源码阅读证明的是已读路径的设计与约束；构建、故障注入、并发及性能结论仍需要对应运行证据。
