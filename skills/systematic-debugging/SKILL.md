# 系统性调试

## 概述

**核心原则：** 必须找到根因再尝试修复。修复症状就是失败。

## 铁律

```
无根因调查则无修复
```

如果你还没完成 Phase 1，你不能提出修复方案。

## 四阶段

### Phase 1：根因调查
1. 仔细阅读错误信息（不要跳过）
2. 稳定复现（不能稳定复现→收集更多数据，不要猜）
3. 检查最近改动
4. 构建 tight loop：一个命令能复现 + 能捕获症状

**完成标准：** 你能命名一个已经运行过的命令，它驱动了实际的 bug 代码路径并断言了用户的精确症状。

### Phase 2：模式识别
1. 错误分类（编译时/运行时/逻辑/集成）
2. 搜索已知模式（竞态条件、空值传播、状态损坏、集成失败、配置漂移、缓存过期）
3. 检查相关代码

### Phase 3：假设
1. 生成 3-5 个排名假设
2. 每个假设必须可证伪
3. 格式："如果 <X> 是原因，那么 <Y> 会..."
4. **在测试任何假设前，先向用户展示排名列表**

### Phase 4：实现修复
1. 每次只改一个变量
2. 修复后重新运行 Phase 1 tight loop
3. 写回归测试
4. 清理：移除调试产物

## 10 种反馈循环构建法

按成本递增排列：

| # | 方法 | 适用场景 |
|---|------|---------|
| 1 | 失败测试 | 有明确接缝可测试 |
| 2 | Curl/HTTP 脚本 | Web 服务问题 |
| 3 | CLI 调用 + fixture | 命令行工具问题 |
| 4 | 无头浏览器脚本 | UI 相关问题 |
| 5 | 重放捕获的 trace | 难以稳定复现的问题 |
| 6 | 临时测试工具 | 需要特殊环境的问题 |
| 7 | 属性/模糊测试 | 边界条件问题 |
| 8 | 二分法（git bisect） | 回归问题 |
| 9 | 差分循环 | 行为不一致问题 |
| 10 | HITL bash 脚本 | 最后手段 |

## 压力测试场景

| 场景 | 压力来源 | 容易犯的错 |
|------|---------|-----------|
| 紧急生产修复 | 时间压力 | 跳过根因直接修复 |
| 沉没成本+疲劳 | 已投入大量时间 | 不愿承认方向错误 |
| 权威+社交压力 | 上级/同事催促 | 盲目执行不合理的修复方案 |

遇到这些场景时，显式提醒自己遵守铁律。
