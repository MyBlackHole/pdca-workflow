# U12：串行发布仍必须比较候选基准

## 固定前置与被测对象

A/B候选均基于r1；A发布r2后B才取得锁；B的目录代数可能已刷新但base仍旧。

模型中的LIB/D、DIGEST-*、FIX-*和授权标志仅为符号fixture；不是实际生产ID、摘要、用户消息或发布证据。宿主验收必须在授权沙箱绑定真实值。每个向量独立重置，不继承前一例状态。

## 执行动作

在提交边界同时比较catalog和definition base三元组；测试head revision相同但digest/manifest不同的异常。

## 正例、反例与oracle

正例：base/head/catalog全匹配且其余门禁成立才提交。

反例：目录变动后沿用旧检查；只更新目录代数掩盖旧base；同revision字节变动。

逐字段比较model_vectors的固定expected；预期来自上述契约，在运行之前保存。正确拒绝错误资料是测试通过；测试器/环境坏了记error，不是有效拒绝。仅参考模型通过不能写host_result=PASS。

## 错误实现／错误规则控制

`SERIAL_LOCK_MEANS_NO_BASE_CHECK`：故意省略 `base` 检查，对 `stale_base` 运行原断言应出现差异。另跑全部正向控制，防止用“始终拒绝”取得假通过。变体未执行或构建失败是invalid，不计killed。

## 必须观测与证据

两候选原始base、实际head与提交先后、单写者回执。锁试验不能代替语义版本检查。

分别保存规则/数据版本、原始输入、expected/actual、断言位置、真实动作、环境、清理及局限。真实身份和授权不能由本案例自己生成；示例有意错误只能在隔离副本注入。
