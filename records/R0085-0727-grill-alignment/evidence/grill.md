# AI Grill 追问门禁

用户提出现有设计或结论需要 grill 时触发。

## 核心规则

1. **一次只问一个问题**。不要一次性抛出多个问题等用户统一回复。
2. **每个问题附带你的推荐答案**。形式："我建议 X，原因是 Y。你同意吗？"
3. **走决策树**。上一个问题的答案决定下一个问题的分支。不要预设用户会选哪条路。
4. **可查证的事实不提问**。能通过文件搜索、代码分析、环境检查确认的事情，直接查而不是问用户。
5. **只问用户能拍板的决策**。哪些是取舍、优先级、设计权衡。
6. **记录关键结论**。每条 Q&A 的要点记录到任务目录下的 `clarifications.jsonl`（与现有手动澄清共用），
   用 `source: "grill"` 区分。格式：`{"round": N, "question": "...", "answer": "...", "recommended": "...", "source": "grill", "at": "..."}`。

## 三种转换点的追问视角

### Plan→Do
审阅 `prd.md`、`design.md`、`clarifications.jsonl`。追问：
- 设计遗漏了什么边界条件？
- 这个假设在什么场景下不成立？
- 备选方案被放弃的理由是否充分？
- 验收标准是否可测试、可度量？

### Do→Check
审阅 `implement.jsonl`、`evidence` 链、`task.json` 的 `activities`。追问：
- 结论是否有充分证据支持？
- 是否存在替代解释没有排除？
- 测试覆盖了关键路径吗？
- 性能/安全方面是否有未暴露的 trade-off？

### Check→Act
审阅 `conclusion.md`、verdict。追问：
- 这个结论的适用范围和限制是什么？
- 哪些部分可以提炼为可复用的知识？
- 下次遇到类似问题，流程上有什么改进？

## 退出条件
- 所有决策树分支走完 → 向用户做对齐总结，确认理解一致。总结格式：
  ```
  我理解的目标是：<目标>
  范围：<范围>
  方案方向：<方向>
  关键决策：<已确认的取舍>
  以上理解是否正确？
  ```
- 用户确认 → 对齐完成，允许推进
- 用户提出修改 → 继续追问，直到对齐
- 发现阻塞性问题 → 说明阻塞原因，建议回到上一阶段修复

## 与 domain-modeling 的协作
追问过程中发现模糊术语 → 立即打开 `pdca/CONTEXT.md` 添加或更新术语。
发现不可逆的硬决策 → 在 `docs/adr/` 创建 ADR 文件。
