# 场景10 限流/带宽控制（动态窗口 vs 令牌桶）

## 技术原理

备份引擎全速传输会挤占业务带宽，调度子系统需要**节流**原语。两种经典
带宽控制算法：

1. **动态阈值窗口限流**（镜像产品 `bwlimit` 模块思路）：以 `thresh` 字节
   为一个窗口，窗口内累计写入量，到达阈值时按目标速率计算应耗时并睡眠
   `(已传字节×8/rate − 实际耗时)`；根据实际等待时长自适应调整窗口大小——
   等待过长（≥1s）缩小窗口以更细粒度校准，等待过短（<10ms）扩大窗口以
   减少唤醒开销。
2. **令牌桶限流（next_free 时间推进模型）**：每次写入 `need bit` 后，把
   "允许写入的下一个时刻"推进 `need/rate`；允许提前消费 `burst_us` 的带宽
   作为突发上限。无累积误差，速率精度高。

多线程共享同一全局限流器时，总速率由内部互斥锁保护，**并发不超上限**。

## 并发模型图（共享全局限流器）

```
   线程0 ─┐
   线程1 ─┼─▶ poc_bw_wait(nbytes) ──▶ [内部锁 + 动态窗口/令牌桶] ──▶ 放行/睡眠
   线程2 ─┤         │                                                     │
   线程3 ─┘         └── 单实例全局状态: rate/burst/thresh/next_free ───────┘
                      总速率 ≤ 上限(锁串行化各线程推进), 各线程竞争锁 → 公平性取决于调度
```

图例：`──▶` 数据流，`锁` 全局互斥，`next_free` 令牌桶推进时刻。

## 逻辑原理图（动态窗口自适应）

```
   窗口: |---thresh 字节---|
   写入达到 thresh → 计算 wait = 目标耗时 − 实际耗时
     wait ≥ 1s  → thresh /= 2   (等待过长, 细化窗口)
     wait <10ms → thresh *= 2   (等待过短, 扩大窗口减少唤醒)
   sleep(wait) 后重置窗口
```

```
   令牌桶: next_free(允许写入时刻) ──need/rate──▶ next_free'
           突发: 允许时刻最多提前 burst_us (=burst/rate)
```

图例：`thresh` 动态窗口阈值，`need` 本次写入位数，`burst` 桶容量。

## 实测结论（字节流计时模拟发送；机器写速上界 ≈9.8 GB/s）

| 算法 | 4 MB/s 偏差 | 32 MB/s 偏差 | 抖动(分窗标准差率) |
|------|------------|-------------|-------------------|
| 动态窗口 | -0.77% | -3.42% | 0.07% / 0.18% |
| 令牌桶 | +0.03% | +0.06% | 0.10% / 0.01% |

- V1 速率精度：两算法、两档速率均落在 ±5% 内，**令牌桶精度显著更高**
  （next_free 模型无累积误差，偏差 <0.1%）。
- V2 平稳性：两算法抖动均 <0.2%（分窗速率标准差），动态窗口 32MB/s 档
  0.18% 略高（自适应窗口收敛期），无吞吐锯齿。
- V3 并发公平性：4 线程共享限流器，总速率 = 32MB/s（不超上限），
  公平指数 0.76~0.82。公平性受限流器锁串行化（先到线程占满窗口）影响，
  属可接受的实现取舍。
- 设计结论：需要**高精度平滑限流**选令牌桶；需要**随实际传输速率自适应**
  且接受 ~3% 偏差选动态窗口（产品 bwlimit 采用后者，换取对突发/慢链路
  的自适应能力）。
