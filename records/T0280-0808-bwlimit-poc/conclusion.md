# 场景10 限流/带宽控制实证 — 结论

## 上下文

备份引擎全速传输挤占业务带宽，调度子系统需节流原语。POC 仓库已实证
网络时序/增量/去重分块/加密压缩/并行分块/事件模型+流式，但缺限流对照
数据。本任务自研两种带宽控制算法并实测对照（字节流计时模拟发送，
机器写速上界 ≈9.8 GB/s）。

## 假设与结果

假设：动态窗口限流（产品 bwlimit 思路）与令牌桶均能满足备份节流需求，
且可量化精度/抖动/并发公平性，给出选型依据。

| 假设 | 结果 |
|------|------|
| 两算法单线程速率偏差 ≤ ±5% | 通过。令牌桶 +0.03%/+0.06%，动态窗口 -0.81%/-3.21% |
| 抖动可量化 | 通过。分窗速率标准差 <0.2%，令牌桶 0.01% 最优 |
| 多线程共享不超上限 | 通过。4 线程总速率 = 目标值（32MB/s），无超速 |
| 并发公平性可测 | 通过。Jain 公平指数 0.73~0.82 |
| 纳入聚合回归 | 通过。make test PASS: 10  FAIL: 0 |

## 分析

1. **令牌桶（next_free 时间推进模型）精度显著高于动态窗口**：偏差 <0.1%
   vs ~3%。next_free 模型无累积误差，是毫秒级平滑限流的首选。
2. **动态窗口的自适应代价**：32MB/s 档偏差 -3.2%（自适应窗口收敛期），
   换取对突发/慢链路的自适应能力——这正是产品 bwlimit 选它的原因。
3. **并发公平性受锁串行化限制**（~0.8 而非 1.0）：全局互斥锁使先到线程
   占满当前窗口/令牌后其他线程才推进。此为"总速率不超上限"的必然取舍；
   若业务需要更公平，可按线程均分速率建独立限流器。
4. **设计结论**：高精度平滑节流选令牌桶；需自适应真实传输速率（慢链路、
   突发容忍）选动态窗口。

## 适用边界

- 字节流计时模拟发送，非真机 socket；未覆盖网络抖动与内核发送缓冲。
- 固定速率档位，未测运行时动态调速。
- 公平指数受机器调度影响，同档多次运行略有波动（0.73~0.82）。

## 下一轮建议

- 场景11 候选：断点续传/分块重传（调度子系统下一缺口），或令牌桶
  动态调速（运行中调整速率）验证。
- 若产品接入限流，建议默认令牌桶（精度优先），保留动态窗口为自适应
  降级路径。
