# rdb-tools-design:迭代需求 → 代码路径定位

## 1. 这个 skill 解决什么问题

项目代码的**知识地图已经建好**(references/ 内 6 份文档),但 agent 的常见失败模式是:不查地图直接 grep,找到代码也不知道是现行还是孤岛,拼错协议常量(method 字符串/MT 消息号/ioctl 字)而不自知。本 skill 强制「**先路由定位,再代码验证,最后输出定位结论**」,把 agent 引导到正确的阅读路径上——具体方案由 agent 读完代码后自行形成。

**孤岛模块并存是最大的坑**:本仓库有多个对第三方开放、但仓内零引用的交付模块(xbsa/libobk/dmsbtex/s3-tool，见 §4)。引用了孤岛实现 = 定位失败。

> **适用分支**：6.2.0.0（目录 `aio-tools/6200/release`），实证 commit `fe9d4364`。他分支以各分册头标注为准，差异见分册「分支差异」章节。

## 3. 核心流程(强制五步)

### 3.1 需求拆解(先读 00,不读代码)

读 `references/00-index.md` 全部,再按需读相关分册的对应段,回答三个问题:

1. **哪个子系统?** fs-backup(文件备份)/ rpc+rdbcomm(传输通道)/ libs(公共库)/ 介质扩展(S3/XBSA/SBT)/ 构建装配——00 §1 能力总表
2. **哪条任务链?** 备份 / 恢复 / 快照合并 / 监控增删 / 远端传输 / 鉴权握手 / 介质备份——各分册任务链章节
3. **涉及哪些模块?** 00 §2(客户端改 fsclient;服务端改 fsdeamon;通道改 rpc;原子能力改 libs;新介质先查 04 孤岛清单;构建改动看 05)

无法判定子系统/任务链时,明确写出「无法确认」并说明缺什么信息,不猜测。

### 3.2 路由加载(按行号 Read,不全量)

按 00-index 的「需求类型 → 文档路由」选必读分册,再按「能力 × 任务链」的行号用 `Read` 读**指定 offset 段**。规则:

- 分册是大文档,**只读路由表指定的段**(如 01 §3 备份链),禁止全量读
- 每份文档读到的结论,记录「文档出处(文档 + 章节)」,作为定位结论的引用依据
- 涉及传输通道时,必读 02 §4(协议常量表)+ 02 §3(握手鉴权链)

### 3.3 代码验证(文档是地图,代码是事实)

文档可能滞后于代码。定位完成前,对**每一个计划呈现的代码路径**做实证:

1. 路径存在(`ls` / `Read` 确认)
2. 链路现行(该文件是否被现行调用链引用——grep 调用方,参考 §4 的裁决速查)
3. 与文档描述一致(函数名/method 字符串/MT 常量/ioctl 字逐字核对)

**文档说「存在」≠ 现行链路**。发现文档与代码不符时,以代码为准,并在定位结论中记录差异。

### 3.4 契约核对(跨模块隐式契约,无共享常量)

涉及传输/备份链路时逐项核对:

| 契约 | 核对方式 |
|---|---|
| fs-cli method 字符串 = fsdeamon 分发分支 | 01 §4 method 表,两侧逐字一致,拼错即无响应 |
| FS_ 命令字:cli 发送值 = daemon switch 分支 | 01 §4 命令字表(`fs_service_proto.h`) |
| MT_ 消息号:client 发送 = server 分发 | 02 §4(`rpc-protocol.h`),拼错即走 default |
| ioctl 字:用户态 = 内核 driver 分发 | 01 §4(`dev_ioctl.h` 三份拷贝一致性) |
| rdbcomm 消息号/握手字段 | 02 §4(`rdbcomm.h`) |
| 端口约定(fsdeamon 8901 / rpc 6611 / dm-ftp 1255 / FileTransferAgent 12000) | 01 §4 + 02 §4 + 04 对应章节 |

### 3.5 输出定位结果

向用户呈现:需求对应的子系统与任务链、涉及的模块、**已定位的代码路径清单**(每个路径注明「文档依据 + 代码实证」)、复用/扩展判断、契约核对结果。格式自由,重点是让用户看到**准确的代码位置**,方案由此自然展开。

## 4. 孤岛与废弃裁决速查(定位涉及的代码必须过这一关)

**落码原则**:新代码只能落三处——备份业务逻辑 → `fs-backup/fsdeamon` 或 `fs-backup/fsclient`;传输通道 → `rpc/`;公共能力 → `libs/`。其余目录视为禁区(新介质除外,见 04)。

| 状态 | 内容 |
|---|---|
| 现行 | 01–03 各分册标注的现行链路;`bwlimit/`(被 rpc 反向依赖的限速库) |
| ⚠️ 孤岛,禁止引用/禁止写新代码 | `xbsa/`(XBSA 库,仓内零引用,仅自带 demo 消费)· `libobk/`(OB SBT 库,仓内零引用)· `dmsbtex/`(达梦 SBT 库,仓内零引用)· `s3-tool/`(S3 二进制,仓内零链接)· `huanweicloun-sdk-s3-data-backup/`(半孤岛,仅帮助文本提及)——详 04 §6 |
| 冗余拷贝,认准权威份 | `fs-backup/kernel/device/dev_ioctl.h` = `fsbackup_kernel_4.x/device/dev_ioctl.h` = `rpc/dev_ioctl.h`(三份同内容);`rpc/crc32.c` vs `libs/crc32.c`;`public/json.hpp` vs `rpc/json.hpp`;`xbsa` 内独立 `thread_pool` 非 `libs` 版 |
| 疑似废弃,先实证再引用 | `FS_BITMAP=5`(handlers 无分支,仅 help 残留)· `rpc/connect_server2`(旧 ioctl 路径)· `MT_GET_TIME` 对时(无业务调用)· `libs/timed_net_key.c`(C 仓零调用)· `libs/anet.c tcp_*`(业务零调用) |
| 运维附属,非业务链 | `fs-backup/tools/`(手动调试二进制)· 各 `tests/` · `*.o/*.ko` 入库残留(构建污染) |

## 5. 铁律

1. **先路由,再验证,后输出**——禁止跳过文档直接凭印象给结论
2. **文档是地图,代码是事实**——每个路径过实证,不符以代码为准并记录差异
3. **不引用孤岛模块**——§4 清单之外,凡文档标注「孤岛/废弃/冗余」的一律避开
4. **无法确认就标记**——不猜、不编,写明缺失信息
5. **不把业务逻辑放公共库**——`libs/` 是纯能力库,业务决策归 fsdeamon、通道编排归 rpc(03 §5 边界)
6. **输出必须落到具体代码路径**——只给「读了哪里、结论是什么」,不给「相关服务」这类模糊表述
