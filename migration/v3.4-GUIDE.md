# 3.4使用指南：本体入库、工作实例与递归子本体

本指南是规范导航，不是另一个权威流程；具体规则以根rule_authorities为准。本版是文件维护交付，没有将用户records转成真实成功任务。

## 1. 这次改变的工作方式

输入“使用ontology_modeling发起本体项目审查任务”时，先保存原始审查目标及被审版本，不把它变为构建同名系统。派发前准备只封装已知目标、来源和控制事实；TASK/CAP确认真实新Agent、独立交互和写权后，该Agent自行Plan。没有能力则只保持未执行准备，draft不是正式Do准入例外。

建模要形成可跨场景理解的业务定义/采用结果与当前工作实例：前者回答“这个审查实体是什么”；后者回答“本次审哪些对象、采用哪个定义、怎样组合”。记录工具动作/用户确认/actual的task不承担共享知识定义角色。

## 2. 已交付到ontology的业务定义

| 路径 | 职责 |
|---|---|
| ontology/concept/audit/project-review.md | 固定审查目标、跨分片覆盖和整体结论 |
| ontology/concept/audit/rule-consistency-review.md | 规则前置、状态、类型及交叉冲突 |
| ontology/concept/audit/source-claim-review.md | 主张原文、来源、版本和证据强度 |
| ontology/concept/audit/test-contract-review.md | 测试规范、实际反例、错误判定器和返工 |
| ontology/pattern/audit/project-review-composition.md | 角色复用、递归展开和父组合义务 |

这些是按用户设计形成的规定性契约，不是对本项目全部资料已核验的报告。仓库中存在active文件不代表EVOLVE线上发布发生；首次采用按授权baseline_snapshot固定。旧领域资料证据状态没有被提升。

五份实体/模式各有三场景套件，共75个固定结构案例；它们验证模型化约束，真实自然语言/源码审查仍需逐事实证据和独立任务。模式有自己的CP套件，不借根套件名称充数。

## 3. 一次建模的分时点产物

| 时点 | 必需 | 允许尚不存在 |
|---|---|---|
| 派发前准备 | 原目标、所选协议、能力/权限的实际事实；未知不填假ID | 正式task/Agent尚未创建时应明确未知 |
| 当前Plan确认 | 当前通用建模suite、既有输入、复用决定、分解评估计划、有限预算和真实来源 | 自己即将生成的最终节点、后代产物 |
| 当前节点交付 | 定义/采用与当前实例、分解结论、直接seed、三个scene的测试语义和当前建模actual | 未来projection/verification的实际运行、后代最终产物 |
| 整树冻结 | 所有真实节点本地建模可用、完整tree-spec/manifest及对应真实确认 | 不要求未来十个或更多场景任务提前执行 |
| 知识目标完成 | 所有声明必需的共享义务有匹配发布或已有定义采用证据 | 其他未声明范围的全部工作迁移，不反向阻塞本工作 |

区分not_defined和not_run：没有期望就谈不上已设计的测试。正确草稿没犯错与检查器能拒绝错误也是两回事，后者必须实际输入错误样本并保存结果。

## 4. 复用和入库决定

实例总要有本次自己的work/node身份；知识decision独立选reuse/local_extension/revise_shared/create。records为空只代表新工作，不意味着ontology没有可用定义。先检索业务语义、适用条件和证据，再选最小变化；名称相似不是充分匹配。

existing_reuse：合格定义已足够，固定采用即可，仍完整PDCA。

local_only：当前参数/差异或受权限限制的一次性定义，给出原因，不声称已入共享库。

shared_required：用户明确需要可复用新知识，记录目标库/ID、责任、完成条件和授权范围。候选暂留records可结束本地节点，但工作知识目标仍未完成；candidate_only不能取消这项义务。

shared_deferred：明确获准的延期、原因、后续责任和触发条件，不得用“以后处理”当已发布。

发布时先固定语义、案例和闭包，再独立审查、精确授权、base/catalog比较及真实提交。不能把旧task日志、私有会话和actual一并搬进ontology。两个候选同基于r1，后提交者即使取得锁仍要检查当前head，不最后写入覆盖。

## 5. 递归建模不是只拆一次

父先固定直接角色seed，默认assess_recursively；孩子用全新Agent在自己的PDCA内判leaf/composite/blocked。children为空是判叶的结果，不能作为理由。严格原子边界必须有证据，遇反证提交设计问题。

评估对象是实体全部建模/实施/审查职责，不是当前草稿字数。可按需读取、分批测试，但必须同时处理的约束不能超预算；父的直接子接口组合也要有界。拆分应减少单任务最大负担，不把同一个大目标换名再交给孩子无限递归。

在父已确认允许范围内增加孙节点，不必重新启动父Agent；改变父接口或必需义务则对应父新attempt；已冻结目标改变则新tree_revision。以最终节点集合核对逐scene覆盖，不用最初五节点锁死后续拆分。

父主要交付责任可以唯一，但多个节点可以验证相同约束、只读相同知识；这与物理双写不同。孩子全部PASS也不能证明父义务无人遗漏。

## 6. 固定闭包不再签认tree.md视图

工作视图tree.md会更新state/确认/回执指针，不进入目标闭包。tree-spec固定目标、角色实例与节点结构；manifest固定所有节点、三个suite/case/fixture/oracle、图/check、定义闭包、实际建模delivery和独立终态证明。

对象字节先固定，manifest后固定，真实确认和freeze receipt最后单向引用。完整闭包核对不只看外层digest；旧对象变更要新提案，不能修改旧用户回应中的摘要。冻结后更新视图不会改spec；图或节点被改则应阻断。

## 7. 对用户已有records的处理

本版没有改动records.tar.gz、records.tar(1).gz或records.tar(2).gz。完整包中的旧冻结摘要不匹配、未来suite未定义和attempt混用以只读来源负例记录。真实Agent/确认来源须向原宿主核验，不因缺包内回执就断言不存在，也不能倒填证明。

未执行草稿可按真实范围重建；有运行记录先按CONTROL/RESOURCE结清状态与写权，已有冻结问题保留历史并新proposal/必要树版本。不要将本版范例复制为用户实际24个成功任务。

## 8. 实际验收范围

K01—K20含76个固定结构输入与20个错误规则控制；五个审查契约含75个结构样本；四条中文样本只作有限句式检查。还运行了真实本地文件摘要/闭包反例及原版复用发布兼容检查。结果详见本版VALIDATION。

结构模型中的fact为真不等于真实来源为真；metadata齐全不等于Agent有授权。真实多Agent、独立交互、共享库发布与完整业务审查仍NOT_RUN。所有验证工具在外部附件，不进入Markdown工作流依赖。
