# 大提交审查的归属验证与测试盲区

## 模式一：git log -L 逐项验证引入点

审查 squash 大提交时，「本次引入 vs 既有债务」必须逐条机器验证，不可凭 diff 直觉：

```bash
git log -L<起>,<止>:<文件> --oneline   # 追溯指定行的引入提交
git show <提交> --stat -- <路径>       # 确认文件是 new file 还是修改
```

价值：修复排期分级（新引入必修 vs 存量择机）、避免把历史债务错记为新回归。

## 模式二：测试全绿 ≠ 无 Blocking

实证案例（T3975，0ec03d3d）：44/44 测试通过，但深审发现 CRITICAL×4、HIGH×21。全部集中于同一批盲区：

- **新建文件的全新功能**：单测只测了作者写用例时想到的路径（如 Copy 场景完全未覆盖）
- **负路径注入**：短包/畸形长度字段/脏配置值无一进入用例
- **跨构建目标差异**：ARM 目标不在本机执行，缺依赖静默通过
- **协议契约双侧一致性**：单侧测试固化了错误预期（4 字节拒绝帧）

对策：审查报告的 Blocking 清单应反向驱动补充测试——每条确定性发现对应一个缺失用例。
