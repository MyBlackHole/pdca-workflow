# 合并提交版本号与信息规范（单需求视角）

## 适用场景
将多个提交（含跨子任务 / 关联需求的提交）squash 为单个需求提交时。

## 规则
1. **版本号归一**：合并后各组件版本号应相对「上一个提交」（squash 前的父）仅递升一个版本（+1）。
   - 不要累加被合子提交的版本增量——子提交各 +1 会导致合并后 +N 超幅跳版。
   - 若父版本为 X，合并后应为 X+1；原始合并中误跳版（如 `1.0.0.0 -> 1.0.1.7`）必须修正回 `X+1`。
2. **提交信息保持单需求语义**：以主需求单号（如 `【F-139】`）概括，子任务要点融入需求描述，不把 `T`/`B` 等子任务作为独立需求标签逐条罗列。
3. **版本变化节**逐组件列出「父 -> 父+1」，明确标注被修正的误跳版。

## 失败案例（本次 T3993 踩坑）
- libobk 误从 `1.0.0.0` 改为 `1.0.1.7`（跳版），应 `1.0.0.1`。
- rpc 误累加 `3.6.4.19 -> 3.6.4.27`（+8），应 `3.6.4.20`。
- 初期把 F-139/T3985/B-3988 多需求提交 squash 成一个却罗列各需求标签，用户判定「提交内容不对」——应归并为单需求实现描述。

## 复用触发
下次执行 `git squash` / 版本号 bump / 提交信息规范化时参考本规范。
