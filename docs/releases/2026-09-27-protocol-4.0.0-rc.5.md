# Release candidate: protocol 4.0.0-rc.5 / Skill bundle 5.0.0-rc.3

Date: 2026-09-27

This release candidate adds a normative project-ontology construction contract after the ontology-construction audit.

## Version identity

| Domain | Version |
|---|---|
| PDCA protocol | `4.0.0-rc.5` |
| Runtime Skill bundle | `5.0.0-rc.3` |
| Record schema major | `pdca.* /v4` |
| Host acceptance | `H1–H18 = NOT_RUN` |

The Skill bundle is unchanged because no runtime entry name/path/metadata surface changed. The protocol changes because Modeling semantics changed materially.

## Main semantic change

Every project/work ontology revision now has a unique **model root ref**. From that root, the fixed revision payload must be able to resolve:

- project/work identity;
- adopted semantic units;
- requirement coverage;
- object definitions;
- current work instances;
- relation definitions and relation instances;
- constraints/invariants;
- provenance/source refs;
- unknown/limitations.

The model can still be Markdown, multiple files, a database object, or an external fixed model. rc.5 does not introduce an OntologyManifest schema.

## Definition / instance / node / task separation

rc.5 makes the ontology chain explicit:

```text
reusable definition
  -> adopted fixed definition
  -> current work instance
  -> semantic relations / constraints
  -> TREE / DEPENDENCY projection
  -> qualified work node
  -> task seed
  -> task
```

Reference entities, work instances, work nodes and tasks must not be treated as aliases of one another.

## Relation contract

A project-ontology relation used for reasoning must define enough semantics to interpret:

- relation identity/type;
- meaning;
- source/target endpoints and roles;
- direction;
- endpoint kind/domain-range;
- cardinality/order when materially relevant;
- provenance;
- explicit composition/dependency implications.

Generic `relates_to` does not imply composition, dependency, ownership, data flow or task decomposition.

## Constraint contract

Important constraints/invariants now distinguish:

```text
semantic property
relation
constraint/invariant
observation/test signal
task acceptance criterion
```

A shell command, grep pattern or test recipe is not itself an ontology property.

## Requirement coverage

Each in-scope requirement must be explicitly `covered`, `partial`, `uncovered` or `not_applicable`, with links to the model semantics that carry it.

Mentioning a requirement in prose is not coverage.

## Provenance and unknowns

Portable provenance should prefer fixed repository commit/path/symbol, stable external document versions or PDCA record refs.

Environment-local absolute paths are only local clues unless an explicit environment identity and fixed content basis are recorded.

Material unknowns now need subject, unresolved claim/question, missing evidence/source, impact and resolution condition.

## Modeling semantic closure

Modeling Check now explicitly reviews:

1. identity closure;
2. definition/instance consistency;
3. relation endpoint and role closure;
4. constraint observability;
5. requirement coverage;
6. provenance validity;
7. unknown completeness;
8. composition/dependency separation;
9. adoption scope.

This remains an AI semantic review. No project-specific semantic validator is added.

## Reference reuse/adoption

REUSE now returns semantic-unit candidates rather than implying whole-file reuse.

ADOPT fixes only selected definitions/relation definitions/constraints/claims and records explicit exclusions. Historical validation recipes, local paths, retired-rule references and unrelated claims do not become current model inputs merely because they share the same source file.

## Record compatibility

Record schema remains `/v4`.

`pdca.ontology-revision/v4` keeps the same fields. Its existing `payload_ref` is now normatively interpreted as the project ontology model root ref; `payload_digest` fixes the complete revision payload, not merely the root file bytes.

All active current contracts/templates declare protocol `4.0.0-rc.5`.

Historical rc.4 records are not rewritten. Existing tasks remain bound to their original protocol/Git/ref context and recover through RECOVERY-01.

## What is still unverified

The current repository still does not contain a real `ontology/projects/...` project ontology generated by a host-executed Modeling task.

Therefore rc.5 defines the construction contract, but real construction/recovery equivalence remains unverified until host-smoke produces a bounded-counter project ontology and another Agent can recover the same semantics from the fixed model root.

Mechanical CI success does not change H1–H18 from NOT_RUN.
