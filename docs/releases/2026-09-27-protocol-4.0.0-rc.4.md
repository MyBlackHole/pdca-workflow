# Release candidate: protocol 4.0.0-rc.4 / Skill bundle 5.0.0-rc.3

Date: 2026-09-27

This release candidate closes the semantic refactor carried by PRs #17–#27.

## Version identity

| Domain | Version |
|---|---|
| PDCA protocol | `4.0.0-rc.4` |
| Runtime Skill bundle | `5.0.0-rc.3` |
| Record schema major | `pdca.* /v4` |
| Host acceptance | `H1–H18 = NOT_RUN` |

These are separate version axes. A schema `/v4` record is not tied to protocol `rc.3`; current active contracts/templates now declare protocol `4.0.0-rc.4`.

## Why the protocol revision changed

Since `4.0.0-rc.3`, normative semantics changed materially even though the record field sets and authority IDs stayed stable.

The main changes are:

1. **Thin runtime surface**
   - `pdca`, `pdca-assist`, four phase Skills and three scene Skills are routing/entry surfaces.
   - Phase/scene/recovery semantics live in their existing authorities instead of being copied into Skills.

2. **Formal task creation pipeline**
   - `TASK -> CONTEXT -> CAP -> CONFIRM -> agent-dispatch`.
   - Dispatch is a one-shot native create transaction, not a task lifecycle manager.

3. **Phase control split**
   - `CONFIRM authorization -> GATE readiness -> TRANSITION event -> STATE projection`.
   - `confirmed != ready != running`.
   - State fields never create permission.

4. **Recovery/control/resource/dependency split**
   - RECOVERY only proves continuation of the original task/attempt/Agent.
   - CONTROL only expresses pause/cancel/revoke/stop facts.
   - RESOURCE owns acquisition/settlement facts.
   - DEPENDENCY owns ready/stale facts.

5. **Evidence pipeline**
   - CASE fixes oracle before actual.
   - TEST records observations.
   - EVIDENCE binds a claim to observations/counterevidence.
   - REVIEW yields review claims/findings.
   - VERDICT aggregates Check acceptance results and subject conformance.
   - `delivery_usable` is decided by actual Act disposition, not by Check.

6. **Ontology lifecycle**
   - `ONTOLOGY -> REUSE candidate -> ADOPT fixed input -> EVOLVE M1→M2 -> TREE candidate -> NODE qualification -> Modeling Check/Act fixed node -> DECOMP task seed`.
   - Draft responsibilities and candidate nodes cannot bypass Modeling Act and go straight to DECOMP.

7. **Rework / Act terminal semantics**
   - Same-attempt rework happens before Act and requires a new Do phase_start.
   - Act is terminal disposition for the current attempt.
   - After `archived`, that attempt never returns to Do.

8. **Scheduling and learning boundaries**
   - SCHED only presents creation candidates for existing fixed task seeds.
   - LEARN only produces/persists/publishes learning candidates when explicitly included in Act scope.
   - Shared knowledge becomes a REUSE candidate; other tasks still need REUSE→ADOPT.

9. **Global consistency audit**
   - 28/28 authority mappings match INDEX and actual frontmatter.
   - 9/9 Skill catalog entries match Skill names/paths/version.
   - Central relative navigation was checked.
   - Known stale semantic paths were removed.

## Compatibility and migration

### Existing records

Existing task/attempt records keep their original bytes and original `protocol_revision`.
This release does **not** rewrite historical rc.3 records to rc.4.

Recovery of an existing task still uses its fixed Git source, refs, original Agent identity and RECOVERY-01.
A current template version bump does not re-authorize, re-adopt or silently upgrade an active task.

### Record schema

There is no schema-major migration in this release:

```text
pdca.* /v4  -> remains /v4
```

The protocol bump reflects changed control semantics, not a field-layout break.

### Skill discovery

The runtime surface remains exactly nine Skills. No new entry names were added and no existing entry name was removed.

## What remains unverified

The repository's Mechanical Checks only verify low-level syntax/whitespace properties.
They do not certify native Agent identity, continuation, isolation, user-source authenticity, resource fencing or event semantics.

Therefore:

```text
H1–H18 = NOT_RUN
```

until executed against a real supported host/configuration.

See:

- `tests/host-acceptance.md`
- `tests/host-smoke.md`

## Upgrade guidance

For a centralized checkout:

1. Review local changes and records before updating.
2. Update the Git working copy using the user's normal Git workflow.
3. Restart/reload Skill discovery if the host requires it.
4. Resume existing tasks only through their original refs/Agent and RECOVERY-01.
5. Use current rc.4 templates for newly written current-format records; do not batch-rewrite historical records.

No automatic task migration, Git commit, adoption, phase start or scene start is implied by updating the repository.
