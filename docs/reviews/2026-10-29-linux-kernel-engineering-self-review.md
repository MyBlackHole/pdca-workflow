## 结论与发现

原版已经能引导基础设计改进；不能断言它只会被动检查。独立基线在普通模块实现请求中主动提出合并分配、有界队列、消费者独占和锁外发送。不过，技能对主动设计的触发、方案取舍与交付要求不够明确，文档还存在一处锁规则错误。

| 发现 | 位置（1.0.0） | 影响与修订 |
| --- | --- | --- |
| 持锁禁止睡眠被泛化到所有锁 | `references/kernelspace.md:17` | 原文“持锁区域不调用可能 fault/睡眠的 uaccess、分配或阻塞等待”会误导合法 mutex 路径。区分禁止睡眠的上下文/锁和可睡眠 mutex，按回收、fault、回调及锁顺序判断；锁外移是需要证明一致性的设计选择。 |
| 主动设计缺少明确产物 | `SKILL.md:40`、`:59` | 原文有原则，但未要求在相关改动中交付内存与锁的具体决定。新增按代码路径触发的设计要求，包含所有权、分配/复制选择、容量、锁范围、退出及方案保留理由。 |
| 内存预算和缩锁方案缺少细化 | `references/engineering-principles.md:19`、`:28` | 队列上界未展开到构造/在途/缓存对象，也没有分配前并发预留或锁外状态提交的选择方法。新增 `memory-and-lock-design.md` 并加入针对性交错验证要求。 |

新增指引将内嵌/合并分配、唯一所有权、批量生命周期、预分配/池、共享引用作为条件选择；将减少共享、简单队列锁、锁外准备与提交、基准后分片作为条件选择。保留简单设计同样满足要求，避免把“主动”解释为强推内存池、无锁或范围外重构。

复验 agent：`/root/kernel_skill_review_retest`。

以下保留实际题设和可定位的响应摘录，结果为文档情境应用证据，不是系统实现验证，也不是重复采样的统计保证。

### A：没有点名优化的异步发送模块

题设：实现 C 用户态模块；8 个生产线程、1 个发送线程；变长消息 1～64 KiB，发送期间数据必须有效。原型 producer 分别 malloc 描述符和 payload 后复制，mutex 入队；worker 持同一锁阻塞 send；stop 置位后立即 free 队列。用户要求可靠实现，没有基准，也未要求内存池或无锁。

基线实际主动提出：“消息可用一次分配容纳描述符与 payload”；“worker 出队后解锁，独占消息直到发送结束”；按条数/字节限额，并等待提交者与 worker 后释放。该输出没有明确分配前额度预留、额度跨在途阶段保留及逻辑预算/RSS 的区别；不能据此推出所有基线运行都不会考虑它们。

复验实际提出：“在锁内先预留，锁外分配，入队前复查停止状态”；预算覆盖构造、排队、发送及元数据，不能等同精确 RSS；“消息实际释放才退额度”。继续采用普通分配和单 mutex，锁外发送并处理停止，池化和无锁待基准决定。

判断：本次修订输出落实了更具体的内存上界与锁管理决定，且没有依赖用户显式要求优化。

### B：合法的 mutex 内分配与 uaccess

题设：普通可睡眠进程上下文的低频 ioctl；struct mutex 保护配置更新；锁内小块 `kmalloc(..., GFP_KERNEL)` 与 `copy_from_user`。已确认没有回收重入、反向锁序、原子上下文或同锁 fault 依赖。判断是否构成必须修复的正确性错误。

基线实际回答：“两处均不构成必须修复的正确性错误”，并主动指出 skill 表述过宽；它借助技术判断修正了文档歧义。本次没有观察到 agent 因旧规则而实际误报，错误是通过文档与给定合法反例的冲突确认的。

复验实际回答：“普通可睡眠进程上下文允许持 mutex 睡眠”；可以保留当前范围；锁外移动需要重新证明存活、状态复查与提交一致性。另行检查 NULL、未复制字节数和部分数据提交。

判断：修订版明确表达正确边界，不要求 agent 自行推翻泛化规则，也没有强迫重构合法路径。

### C：小改动不能触发过度设计

题设：单线程离线工具，启动分配 64 KiB、退出释放，固定工作集且无热循环分配；已有库边界内低频 mutex。用户只要求长度边界修复。

基线和复验均保留现有分配与锁，只改校验及相关错误路径。复验明确不需要池、arena、把大 buffer 移上栈或新增同步。

判断：主动设计允许有依据地保留原方案，不自动扩大成资源框架重构。

### D：语言与执行上下文边界

题设：Rust 内核不可睡眠 callback 补齐分配失败处理；C++ 用户态仅采用 C 风格且不用 C++ 库。提出 `std::vector` 缓存与内核 `std::sync::Mutex` 两项建议。

基线和复验均不采纳两项库建议，保留 C 资源接口与 Rust 内核 no_std/目标树抽象。复验明确不可睡眠 callback 不能取得可睡眠 mutex，分配可失败且必须按回调契约回滚/降级，不猜目标树具体 API。

判断：新增设计要求没有破坏 C++ 无库与内核上下文约束。

- Scope：改动仅用于本技能设计指导和一处错误规则修正，没有业务实现或其他仓库规则变更。
- Consistency：主入口把内存/锁设计参考置于相关代码路径的读取条件下；原有用户态/内核态差异、目标树优先、C++ 无库、Rust 适配与禁止测试写 `/tmp` 保留。
- Adversarial：测试既包含明显需要改进的队列，也包含合法 mutex 和应保留原分配的反例，避免只测“应该优化”的正例。另行安排一次只读反例审查，核对预算、对象流转、锁外操作及授权边界。
- Evidence：本轮应用测试实际输出如上。机械检查包括 skill-creator `quick_validate.py`、相对链接检查及 `git diff --check`；这些只证明格式/链接/差异检查结果，不代替设计或内核行为验证。

独立反例 reviewer `/root/kernel_skill_design_adversarial` 在第一版修订中指出两处可达歧义：设计资料的路由只写“新增或修改”，可能让只读审查跳过它；队列示例的“释放/移交后更新额度”可能被解释为异步后端仍持有消息时就归还额度。后者反例为不断摘取并移交消息、重用已归还额度，实际在途内存持续增长。

当前修订已将路由明确扩展为设计、实现或只读审查，并规定同预算内移交只转移记账责任，实际释放后才归还；跨预算先成功承接额度再转移。还明确失败/停止/取消只有释放已分配对象后才能退还额度。

同一 reviewer 重新读取最终两份文件，复验了两个反例：

- 仅审查现有队列、明确禁止修改：正确选择设计资料，交付所有权、预算、锁与退出协议的审查决定，并明确不能修改业务代码。
- 同模块预算 128 KiB，两个各计 64 KiB 的消息已交异步后端但均未释放：回答已用 128 KiB、可用 0，第三条不能预留或先行分配；停止/取消本身不退还前两条额度，没有成功预留的第三条也无额度可退。

reviewer 最终结论为“两处问题均已解决；本轮未发现新增矛盾”。这是待根审查核验的结论；上述最终文本、预算算例及路由条件经根审查逐项复核一致，仍不代表实际并发程序已实现或测试通过。
