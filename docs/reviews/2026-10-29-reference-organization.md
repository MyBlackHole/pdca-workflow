其中测试相关边界明确为：

- testing-strategy：规划测试体系、边界、框架、覆盖和 CI 成本。

- validation：为当前已确定改动选择检查、故障注入、并发交错和性能证据。
- code-review：对明确的 diff/PR 追踪行为、调用链及可执行发现。

技术规则、内存预算、锁协议、异步退出及目标版本要求保留。正文只收紧两处表述：验证页的职责说明，以及明确“专门中文补注”才采用中文项目资料；其余变化是目录、文件名、相对链接和验证资料的引用名称。

## Adversarial Review

修改前独立读取基线覆盖六组场景：有界用户态队列；局部回归/全项目策略/TDD 的区别；不可信跨边界 ioctl；主线与旧目标树比对；普通注释与中文补注；既有构建及局部提交。

基线能正确区分资料，未遇缺失文件，不能声称原分类导致六项读取失败。但它发现“专门补注”可能仅凭入口措辞多加载中文资料，现已明确为“专门中文补注”。基线为建立整体判断实际读了全部十六份资料，不能将其记录为每个场景只读取了最小集合。

重组后独立读取复测得到六组正确路由：

1. 用户态队列从 principles 取得生命周期与预算方案，从 environments 取得 pthread/I/O 约定，从 workflows/validation 选择交错证据；不默认读内核、安全全审或完整测试策略。
2. 局部回归使用 validation，体系规划使用 testing-strategy，实现切片使用 test-driven-development；已有实现不删除重演红灯，只有实际故障才补 debugging。
3. ioctl 同时核对两侧 environments、security-review、资源原则与改动验证；不把用户页 pin、一次校验或引用计数当成完整安全证明。
4. 主线学习区分 sources 中的官方定位和版本比对方法，结合目标内核环境；不将新 helper 直接移植到旧树。
5. 普通注释使用编码资料，明确中文补注才采用可选项目约定；普通英文注释不触发中文化。
6. CMake 修复与局部提交使用构建、改动验证及 Git 流程，根因未知时补调试；不因此启动完整代码审查、测试体系或项目翻译。

复测为整体评估实际读了十六份资料，未遇缺失文件或妨碍路由的分类含糊；它验证了六组应读集合和职责判断，不是单任务最小读取成本的测量。未读取范围外的迁移索引或联网核验来源。
