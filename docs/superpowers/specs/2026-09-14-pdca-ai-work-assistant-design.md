# PDCA AI 工作辅助设计

## 状态与目标

本设计为 PDCA 4.0.0-rc.2 定义一个经用户显式调用的 AI 工作辅助层。它帮助用户从已获授权的项目与集中记录中看见任务、上下文、质量证据和协作状态，并提出可选下一步；它不替用户决定、派发 Agent 或推进阶段。

目标是让 AI 能同时辅助：

- 任务拆解、关系表达与跟踪；
- 上下文及共享术语/决策的沉淀和检索；
- 质量验证、结论和证据的组织；
- 跨 Agent 的交接、阻塞与协作建议；
- 安装、首次使用和发布包内容的清晰性。

本设计不引入常驻服务、独立界面或业务项目中的隐式状态目录。首版由一个 `$pdca-assist` 入口同时给出四类建议；不为尚未稳定边界的能力预先增加多个入口。

## 约束

- 继续以 Agent Skills 形式发布，并由 `setup` 导出到宿主发现目录（默认 `~/.agents/skills`）。
- `PDCA_ROOT` 是本体、records、资源预约、决策和证据的集中写域；`TARGET_ROOT` 只承载已获用户批准的产品产物。
- 除集中记录外，`$pdca-assist` 可在当前已绑定的 `TARGET_ROOT` 内只读分析源码、文档和 Git 状态，并受宿主权限限制；不得遍历其他项目、未关联目录或集中根中无关的历史内容。
- 已有八个入口的含义、原 Agent 连续性和“每个阶段由用户启动”的规则不得改变。
- AI 只提出选项；用户选择、补充并对写入或阶段变化作明确授权。
- 安装器不是 Agent Runtime，不承担调度、后台观察或业务锁职责。

## 入口与能力组织

新增 `$pdca-assist` 作为用户显式调用的工作台入口：

1. 核验集中根、规则快照及项目绑定；
2. 读取已获授权的任务、阶段、资源预约、证据索引和可读项目上下文；
3. 以“现状、候选动作、影响、所需授权”呈现少量建议；
4. 接收用户的选择、拒绝或补充；
5. 仅在适当确认后路由到既有阶段入口或专项方法。

`$pdca` 保持只读定位和分流：回答当前在哪个中心、项目绑定了什么、哪些任务或确认待处理。它不承担工作建议，以免改变已有调用的预期。

首版的候选动作覆盖任务地图、项目上下文、证据审阅和协作交接四个视角，但均由 `$pdca-assist` 呈现。只有某一视角形成稳定的输入、输出、写入边界及独立用户调用价值时，才拆成专项方法 Skill；任何专项 Skill 都不互相隐式串联，也不替代 Plan、Do、Check、Act。

这采用“用户调用的编排入口 + 可组合的专项方法”的组织方式。参考 mattpocock/skills 的分层与首次配置方式，但不复制其代码、安装机制或外部任务跟踪假设。

## 数据与交互流

默认调用是只读的：

`用户调用 → 绑定核验 → 记录/上下文汇总 → 候选动作 → 用户选择或补充`

涉及创建任务草案、写入上下文、记录评审结论、建立交接或进入阶段的动作，必须在候选动作之后再次获得明确确认。确认后的记录写入集中根，并包含选择理由、关联对象和可核验证据；业务项目仅在对应产品工作获得授权后才写入。

无法安全判断时，入口只报告缺失信息、冲突或可选的人工核对路径。它不得猜测项目身份、覆盖记录、创建隐式 Agent，或把建议表述为已批准动作。

## 安装、使用与发布结构收敛

发布根只保留面向人的 `README.md` 和 `INSTALL.md`、实际 Skills/本体/模板/脚本/测试，以及一个机器可读的 `release.json`。根 `SKILL.md`、`USE-PDCA.md`、`protocol-release.md`、`release-manifest.md` 和整个 `bootstrap/` 在迁移完成后移除。

`release.json` 是唯一的发布控制对象，并同时承担当前清单和协议基线职责。它包含版本、完整文件摘要、当前任务采用的 active 集合、Skill 索引、PDCA 控制元数据（包括用户显式推进、集中 records 根、规则权威索引、资源范围和 legacy 政策）。它不自哈希；项目绑定固定其字节摘要。安装校验、发布构建、项目绑定和任务快照都从该对象读取。新绑定使用 `release_ref` 与 `release_digest`；已有任务继续使用其已固定的旧 `protocol-release.md` 与 `release-manifest.md` 快照，不回写或重签历史记录。

`skills/catalog.json` 是入口集合的唯一来源；`setup`、`release.json`、安装预览/校验/更新/卸载结果和用户文档中的入口数量均从它派生，不能再把“八个入口”写死。新增入口必须与现有入口同样具有可检查的导出、来源快照和冲突保护。

对 `bootstrap/`、安装及校验脚本、模板、旧文档和未被入口引用的内容做职责审计，而非基于目录名称删除。原 `bootstrap/entry-check.md` 与 `dispatch-guide.md` 的规范内容迁入 `ontology/contracts/`；全局引导和安装来源迁入 `INSTALL.md`；宿主能力说明迁入 `ontology/concept/capability-protocol.md`；无独有职责的工作方法说明删除。每项内容分为：

- 发布必需：安装、运行、测试或用户使用当前版本必需；
- 维护参考：仅维护/设计时需要，应有明确索引和不参与运行的说明；
- 可删除或迁移：没有当前职责，或已有唯一替代路径。

`USE-PDCA.md` 的用户使用说明合并进 `README.md` 与 `INSTALL.md`，根 `SKILL.md` 的兼容跳转由 `skills/pdca/SKILL.md` 取代。删除前必须证明没有 `release.json`、安装器读取路径、Skill 引用、测试、迁移或用户文档链接依赖。重叠逻辑先收敛调用方至一个实现，再删除旧实现。不得删除已有任务快照、records、本体历史或用户资产。

## 失败处理与验证

项目未登记、规则快照不匹配、技能发现目录冲突或证据不足时保持只读并提供恢复/人工核对指引。

实现计划至少覆盖：

1. 安装器、`release.json` 构建/校验及旧快照兼容的单元测试；
2. `$pdca-assist` 场景：建议不写入、用户选择后才写入或路由、阶段不自动推进；
3. 宿主验收：发现新增入口，安装/更新/卸载不重复，且现有八个入口不受影响；
4. 迁移后根 `SKILL.md`、`USE-PDCA.md`、`protocol-release.md`、`release-manifest.md` 和 `bootstrap/` 均不存在，且没有活动规则、文档、测试或脚本链接指向它们；
5. 每个清理项的引用扫描与相关回归测试。

## 非目标

- 不自动创建或管理后台 Agent；
- 不把资源预约伪装成沙箱、锁或调度器；
- 不在目标项目创建 `.pdca/` 或改写项目指令；
- 不用静态测试宣称宿主已发现技能或 Agent 已具备交互能力。
