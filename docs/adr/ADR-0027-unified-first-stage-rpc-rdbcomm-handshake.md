# ADR-0027: rpc 与 rdbcomm 共用第一阶段明文握手
日期: 2026-08-18
状态: Accepted

## 背景

rpc 与 rdbcomm 都需要在连接建立后区分获取时间、明文业务和 mTLS 业务。若分别在各自 APP 帧中扩展，容易产生协议分叉，并且无法在 TLS 前可靠识别连接意图。

## 候选方案

1. 分别扩展 rpc/rdbcomm 的业务帧：改动局部，但 wire 协议不一致，时间能力难以复用。
2. 共用独立第一阶段明文协议：增加共享协议组件，但可以统一 TIME、mTLS、明文继续和错误处理。

## 决策

选择方案 2。第一阶段使用版本化固定头和 operation 字段；TIME 返回后关闭；NEGOTIATE 根据客户端请求、服务端允许和算法能力交集决定明文继续或 mTLS 升级。服务端算法类型可配置，证书选择沿用按 `ca_cn` 匹配，并在升级响应中返回选定 `ca_cn`；客户端按 `cert_dir/<ca_cn>/` 显式加载本地证书。TLS 阶段不再通过回调猜测证书，仅执行证书链、签名和 CN 校验。未知/直接 APP 帧或证书不存在时返回明确错误并关闭。

## 影响

rpc 与 rdbcomm 获得一致的 wire 语义，现有 APP 数据帧可以保持不变；旧客户端直发 APP 不再静默兼容，需要升级客户端。默认模式为明文，显式 mTLS 才进入加密升级。mTLS 成功后必须保留 TLS 数据面，禁止 detach 后使用原始 fd。证书选择增加了客户端证书配置/映射维护成本，但消除了多证书场景下的猜测和错误证书尝试。
