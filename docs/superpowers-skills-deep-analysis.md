## 1. Test-Driven Development (TDD)

### 1.1 核心原则

```
先写测试。观察失败。写最小代码通过。
```

**铁律：**
```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

### 1.2 详细流程

#### RED - 写失败测试

写一个最小测试，展示应该发生什么。

**好的示例：**
```typescript
test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```
清晰的名称，测试真实行为，一件事

**坏的示例：**
```typescript
test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```
模糊的名称，测试mock而不是代码

**要求：**
- 一个行为
- 清晰的名称
- 真实代码（除非不可避免，不使用mock）

#### 验证 RED - 观察失败

**强制性。永不跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（不是错误）
- 失败消息是预期的
- 因为功能缺失而失败（不是拼写错误）

**测试通过？** 你在测试现有行为。修复测试。

**测试错误？** 修复错误，重新运行直到正确失败。

#### GREEN - 最小代码

写最简单的代码通过测试。

**好的示例：**
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```
刚好通过

**坏的示例：**
```typescript
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // YAGNI
}
```
过度设计

不要添加功能、重构其他代码或"改进"超出测试的内容。

#### 验证 GREEN - 观察通过

**强制性。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、警告）

**测试失败？** 修复代码，不是测试。

**其他测试失败？** 现在修复。

#### REFACTOR - 清理

只有在绿色之后：
- 移除重复
- 改进名称
- 提取帮助函数

保持测试绿色。不要添加行为。

#### 重复

下一个失败测试用于下一个功能。

### 1.3 好的测试

| 质量 | 好 | 坏 |
|------|-----|-----|
| **最小** | 一件事。名称中有"和"？拆分它。 | `test('validates email and domain and whitespace')` |
| **清晰** | 名称描述行为 | `test('test1')` |
| **显示意图** | 展示期望的API | 模糊代码应该做什么 |

### 1.4 常见借口与现实

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会出错。测试只需30秒。 |
| "我之后再测试" | 之后写的测试会立即通过——这证明不了什么。它们可能测试错误的东西，测试实现而不是行为，或错过你忘记的边缘情况。你从未观察失败，所以从未证明它能捕获bug。测试前写强制失败。 |
| "测试后写达到相同目标（精神不是仪式）" | 测试后回答"这做什么？"；测试前回答"这应该做什么？"之后写的测试偏向你已经写的代码——你验证记住的案例，而不是你会发现的案例。没有证明测试工作的覆盖率。 |
| "已经手动测试过了" | 手动测试是临时的：没有覆盖记录，无法重新运行。"我试的时候工作了" ≠ 全面。自动化测试每次运行方式相同。 |
| "删除X小时是浪费" | 沉没成本谬误——时间已经花了。真正选择：用TDD重写（高信心）vs 保留并加测试（低信心，可能有bug）。保留不可信代码是浪费。 |
| "保留作为参考，先写测试" | 你会适配它。那是之后写测试。删除意味着删除。 |
| "需要先探索" | 好的。丢弃探索，用TDD开始。 |
| "测试难 = 设计不清楚" | 听测试。难以测试 = 难以使用。 |
| "TDD会让我变慢" | TDD是实用路径：在提交前捕获bug，防止回归，让你无畏重构。"实用"快捷方式意味着在生产中调试——更慢，不是更快。 |
| "手动测试更快" | 手动不证明边缘情况。你会重新测试每个更改。 |
| "现有代码没有测试" | 你在改进它。为现有代码添加测试。 |

### 1.5 红旗 - 停止并重新开始

- 代码在测试之前
- 实现后测试
- 测试立即通过
- 无法解释为什么测试失败
- 测试"之后"添加
- 合理化"就这一次"
- "我已经手动测试过了"
- "测试后达到相同目的"
- "这是关于精神不是仪式"
- "保留作为参考"或"适配现有代码"
- "已经花了X小时，删除是浪费"
- "TDD是教条的，我在实用"
- "这不同因为..."

**所有这些都意味着：删除代码。用TDD重新开始。**

### 1.6 示例：Bug修复

**Bug：** 空邮箱被接受

**RED**
```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**验证 RED**
```bash
$ npm test
FAIL: expected 'Email required', got undefined
```

**GREEN**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**验证 GREEN**
```bash
$ npm test
PASS
```

**REFACTOR**
如有需要，为多个字段提取验证。

### 1.7 验证检查清单

标记工作完成前：

- [ ] 每个新函数/方法都有测试
- [ ] 实现前观察每个测试失败
- [ ] 每个测试因预期原因失败（功能缺失，不是拼写错误）
- [ ] 写了最小代码通过每个测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、警告）
- [ ] 测试使用真实代码（仅在不可避免时使用mock）
- [ ] 覆盖边缘情况和错误

不能检查所有框？你跳过了TDD。重新开始。

## 2. Subagent-Driven Development

### 2.1 核心原则

```
每个任务一个新子代理 + 任务审查（规格合规 + 代码质量）+ 最终全分支审查 = 高质量，快速迭代
```

**为什么使用子代理：** 你将任务委派给具有隔离上下文的专业代理。通过精确制作它们的指令和上下文，你确保它们保持专注并成功完成任务。它们永远不应该继承你会话的上下文或历史——你构造它们需要的确切内容。这也为你自己的上下文保留了协调工作。

**叙述：** 在工具调用之间，最多叙述一行——账本和工具结果承载记录。

**连续执行：** 不要在任务之间暂停与你的伙伴签到。不停止地执行计划中的所有任务。停止的唯一原因是下面命名的四个，或所有任务完成。"我应该继续吗？"提示和进度摘要浪费他们的时间——他们要求你执行计划，所以执行它。

**裁决，不是停滞。** 运行中的计划不等待人类。冲突、歧义、计划缺陷、你本会要求超过的上限——决定它们。规格是约束权威，计划是其参数，你的判断解决两者都不回答的问题。在账本中记录每个决定为`裁决：<你决定了什么> — <为什么> — <如果错了付出什么代价>`，然后继续。错误的裁决代价是重做你的伙伴可以看到和撤销；会话停在一个问题上代价是他们的一整天，什么也没买。

四件事阻止你，只有这些：不可逆或破坏性操作；安全敏感操作；规范说你先询问的此工作树外的副作用（合并、推送到共享分支、发布）；以及计划如此破碎，每条前进路径都是猜测。对于这些，停止并询问。

### 2.2 何时使用

```
有实现计划？ → 任务大多独立？ → 留在此会话？ → subagent-driven-development
                ↓                      ↓
            手动执行或先头脑风暴    executing-plans（并行会话）
```

**vs. Executing Plans（并行会话）：**
- 同一会话（无上下文切换）
- 每个任务新子代理（无上下文污染）
- 每个任务后审查（规格合规 + 代码质量），最后全审查
- 更快迭代（任务间无人在循环）

### 2.3 设置

确保工作在隔离的工作区进行：使用 superpowers:using-git-worktrees 创建一个或验证现有的。永远不要在主分支上开始实现，没有你伙伴的明确同意。

对话记忆在压缩后不存活。在真实会话中，丢失位置的控制器已经重新分派了整个完成的任务序列——观察到的最昂贵失败。在账本文件中跟踪进度，而不仅仅在待办事项中。

- 每个计划拥有一个工作区：在技能开始时，运行此技能的`scripts/sdd-workspace PLAN_FILE`——它打印计划的git忽略目录（`<repo-root>/.superpowers/sdd/<plan-basename>/`），用于此计划的所有工件：账本、简报、报告、审查包。另一个计划的目录永远不是你读或写的。
- 检查此计划的账本在`<workspace>/progress.md`。如果其第一行命名你的计划文件，带有`Task <N>: complete`行的任务已完成——不要重新分派它们；在没有此行的第一个任务恢复。任务的最后一行是修复循环：在下一轮恢复循环。第一行命名不同计划文件的账本——或在旧平面路径`.superpowers/sdd/progress.md`的 stray 账本——是另一个计划的进度：将其留在原地并开始你自己的，全新的。
- 用其标识作为第一行创建账本：`# SDD ledger — plan: <plan file path>`。
- 账本是你的恢复地图：它命名的提交存在于git中，即使你的上下文不再记得创建它们。压缩后，信任账本和`git log`而不是你自己的回忆。
- `git clean -fdx`会销毁工作区（它是git忽略的临时文件）；如果发生，从`git log`恢复。

读取计划一次，注意其上下文和全局约束，并为每个任务创建一个待办事项。如果计划命名规格，也读取该规格：规格是计划论证的权威，计划内的冲突解决对抗它。没有可访问规格的计划得到一个账本注释说明如此——没有规格做出的裁决是临时的。

在分派任务1之前，扫描计划一次查找冲突，记下你检查的内容：

- 互相矛盾或与计划全局约束矛盾的任务
- 计划明确强制但审查标准视为缺陷的任何内容（一个断言无内容的测试，逻辑块的逐字重复）

扫描的输出是一个表，不是判决。每个共享文件或接口的任务对一行：两个任务，一个生产什么对抗另一个消费什么，以及你发现的内容。每个任务一行：其自己的文本是否与自身一致——它指定的测试对抗它指定的代码，它创建的文件对抗它稍后接触的文件。"扫描干净"没有那些行不是你运行的扫描。

将表写入账本。在执行开始前裁决你发现的每个内容——每个发现对抗强制它的计划文本——并在账本中记录每个裁决。如果扫描干净，不加评论继续。裁决它表面的每个冲突——规格是约束权威，计划是其参数——在行旁边记录裁决，然后分派任务1。审查循环仍然是仅从实现出现的冲突的网。

### 2.4 模型选择

使用能处理每个角色的最不强大模型以节省成本并增加速度。

**机械实现任务**（隔离函数、清晰规格、1-2文件）：使用快速、便宜的模型。大多数实现任务在计划良好指定时是机械的。

**集成和判断任务**（多文件协调、模式匹配、调试）：使用标准模型。

**架构和设计任务**：使用最强大的可用模型。最终全分支审查是其中之一——在最强大的可用模型上分派它，而不是会话默认。

**审查任务**：选择具有相同判断的模型，按diff的大小、复杂性和风险缩放。小的机械diff不需要最强大的模型；微妙的并发变化需要。小修复diff的范围重审采用便宜到中等层。

**修复循环升级（第4-5轮）**：使用至少比陷入困境的实现者高一级的模型。

**当分派子代理时总是明确指定模型。** 省略的模型继承你会话的模型——通常是最强大和最昂贵的——这无声地击败了本节。

**轮次计数胜过令牌价格。** 墙钟和上下文成本与子代理采取的轮次数量成比例，最便宜的模型在多步工作上通常采用2-3倍轮次——总体成本更高。使用中等层作为审查者和从散文描述工作的实现者的底线。当任务的计划文本包含要写的完整代码时，实现是转录加测试：为该实现者使用最便宜层。单文件机械修复也采用最便宜层。

**任务复杂性信号（实现任务）：**
- 接触1-2个文件，完整规格 → 便宜模型
- 接触多个文件，有集成问题 → 标准模型
- 需要设计判断或广泛代码库理解 → 最强大模型

### 2.5 任务循环

**批量小型相同形状工作。** 当计划列出多个任务，每个都是相同类型的小独立编辑——相同的单行修复、常量更改或跨文件的字段添加——不要每个任务分派一个子代理。组合一个分派简报列出每个文件及其更改，将整个批次发送给单个子代理，并作为单个单元审查其diff。将每个任务一个分派保留给需要自己判断、自己测试或自己审查表面的工作。

你粘贴到分派提示中的所有内容——以及子代理打印回的所有内容——在会话的其余时间驻留在你的上下文中，并在每个后续回合重新读取。将工件作为文件传递。

**等待已分派的子代理：** 永远不要用短超时轮询等待接口，也永远不要坐在一个沉默的、开放-ended的等待中。当你有本地工作——账本更新、打包下一个审查、读取报告——继续工作；子结果自己到达。当你真正空闲时，在有界拉伸中等待（五到十分钟，你的平台允许），并在拉伸之间发布一行状态并协调你的活动孩子：列出它们，并追赶任何完成但没有报告的。有界拉伸几乎保持长等待的所有效率，同时保证卡住或丢失的孩子在几分钟内被注意到，而不是在会话结束时。

#### 1. 分派实现者

在分派前记录BASE（`git rev-parse HEAD`）——审查包和修复轮次diff需要它。

- **任务简报：** 在分派实现者之前，运行此技能的`scripts/task-brief PLAN_FILE N`——它将任务的完整文本提取到唯一命名的文件并打印路径。组合分派，使简报保持需求的单一来源。你的分派应包含：(1) 此任务在项目中适合的一行；(2) 简报路径，介绍为"先读这个——它是你的需求，使用确切的值逐字"；(3) 早期任务的接口和决策，简报无法知道；(4) 你在简报中注意到的任何歧义的解决方案；(5) 报告文件路径和报告合同。确切值（数字、魔术字符串、签名、测试用例）仅出现在简报中。永远不要让子代理读取整个计划文件。
- **报告文件：** 以简报命名实现者的报告文件（简报`…/task-N-brief.md` → 报告`…/task-N-report.md`）并将其放入分派提示中。实现者在其中写入完整报告并仅返回状态、提交、一行测试摘要和关注。
- 分派提示描述一个任务，不是会话的历史。不要将累积的先前任务摘要（"任务1-3后的状态"）粘贴到后来的分派中——真实会话的分派达到42k字符，其中99%是粘贴的历史。新子代理需要它的任务、它接触的接口和全局约束。没有其他。
- 分派携带无子代理合同（它在实现者模板中）：实现者永远不派发子代理——不是帮助者，永远不是审查者。审查从你来，在报告之后。在真实会话中，工人生成的每个审查者都复制了控制器分派的任务审查——每个任务一个完整的额外审查席位。
- 如果先前任务在此任务接触的区域停放了发现，在分派中携带指向该账本条目的指针。
- 从分派结果记录实现者的代理标识——修复循环轮次1-3恢复此代理。
- 永远不要并行分派多个实现子代理（冲突）。

#### 2. 处理报告

实现者子代理报告四种状态之一。适当处理每个：

**DONE：** 生成审查包（`scripts/review-package PLAN_FILE BASE HEAD`，从此技能目录——它打印写的唯一文件路径；BASE是你在分派实现者前记录的提交——永远不是`HEAD~1`，它默默地丢弃多提交任务的所有但最后一个提交），然后用打印的路径分派任务审查者。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。在继续前阅读关注。如果关注关于正确性或范围，在审查前解决它们。如果它们是观察（例如，"这个文件变得很大"），记下它们并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文并重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞者：
1. 如果是上下文问题，提供更多上下文并用相同模型重新分派
2. 如果任务需要更多推理，用更强大的模型重新分派
3. 如果任务太大，将其分解为更小的部分
4. 如果计划本身错误，裁决更正，记录它，并携带裁决重新分派

**永远不要**忽略升级或强迫相同模型重试而没有更改。如果实现者说它卡住了，需要改变什么。

如果实现者问问题——开始前或任务中——清晰完整地回答，如果需要提供额外上下文，不要急于实现。

#### 3. 审查任务

每个任务审查是任务范围的门。全审查发生一次，在最终全分支审查。永远不要跳过任务审查，永远不要接受缺少任一判决的报告——规格合规和任务质量都需要。实现者自我审查永远不替代任务审查；两者都需要。

- 将diff作为文件交给审查者：运行此技能的`scripts/review-package PLAN_FILE BASE HEAD`并将打印的文件路径传递给审查者（或没有bash：`git log --oneline`，`git diff --stat`，和`git diff -U10`对于范围，重定向到一个唯一命名的文件）。输出永远不进入你自己的上下文，审查者在一个读取调用中读取提交列表、stat摘要和完整diff与上下文。使用你在分派实现者前记录的BASE——永远不是`HEAD~1`，它静默地截断多提交任务。永远不要在没有diff文件的情况下分派任务审查者。
- **审查者输入：** 任务审查者获得三个路径——相同的简报文件、报告文件和审查包——加上约束任务的全局约束。
- 你交给审查者的全局约束块是其注意力镜头。从计划的全局约束部分或规格逐字复制约束要求——确切值、确切格式和组件之间的声明关系（"与X相同的布局"、"匹配Y"）。审查者的模板已经携带过程规则（YAGNI、测试卫生、审查方法）——约束块用于此项目的规格要求。
- 不要添加开放指令如"检查所有用法"或"运行竞争测试如果有用"而没有具体的、特定任务的原因
- 不要要求审查者重新运行实现者已经在相同代码上运行的测试——实现者的报告携带测试证据
- 不要为审查者预判发现——永远不要指示审查者忽略或不标记特定问题。如果你相信发现会是假阳性，让审查者提出它并在审查循环中裁决它。如果你写的提示包含"不要标记"、"不要将X视为缺陷"、"最多Minor"或"计划选择了"——停止：你在预判，通常是为了让自己省去审查循环。

任务审查者可能报告"⚠️ 无法从diff验证"项——存在于未更改代码中或跨任务的需求。这些不阻止审查的其余部分，但你必须在标记任务完成前自己解决每个：你持有计划和审查者缺乏的跨任务上下文。如果你确认项目是真实差距，将其视为失败的规格审查——它进入修复循环与其他发现一起。

模板：[task-reviewer-prompt.md](task-reviewer-prompt.md)

#### 4. 修复循环

当审查报告规格❌、任何Critical或Important发现、或你确认为真实差距的⚠️项时，循环触发。

在循环开始前，两条路线立即离开它：

- 将Minor发现记录在进度账本中（`Task <N>: minor (deferred): <one-liner>`），并将最终全分支审查指向该列表，以便它可以分类哪些必须在合并前修复。没人读的汇总表是静默丢弃。Minor发现永远不进入循环。
- 标记为计划强制的发现——或与计划文本要求冲突的任何发现——是你的裁决：权衡发现与计划文本，决定规格为约束权威，并在对其采取行动前记录裁决。不要因为计划强制它而丢弃发现，也不要分派与计划矛盾的修复而没有记录的裁决。

其他一切进入循环。修复轮是一次修复分派加一次范围重审。每个任务最多五轮：

**轮次1-3 — 恢复原始实现者。** 将其发送为开放发现逐字。其上下文完整：它知道任务、代码和它自己的选择。如果你的线束无法向活动子代理发送另一条消息，分派新实现者携带简报路径、报告文件路径和发现——报告文件是持久内存无论哪种方式。

**轮次4-5 — 分派新实现者在更强大的模型上**（按模型选择），携带简报路径、报告文件路径、开放发现和此框架："先前实现者尝试此任务[N]次；你现在拥有它。阅读报告文件了解尝试了什么。"存活三次恢复的循环通常意味着实现者无法看到自己的问题——新鲜眼光和能力提升在一个动作中。

**每轮，无论哪种方式：** 实现者修复，重新运行覆盖修改代码的测试，将其修复报告附加到相同报告文件，并返回短合同。在重新分派审查者前，确认修复报告包含覆盖测试、运行的命令和输出；一旦三个都存在，分派重审。在修复消息中命名覆盖测试文件——单行修复不需要整个套件。

**重审是范围的。** 运行`scripts/review-package PLAN_FILE FIX_BASE HEAD`其中FIX_BASE是先前审查看到的HEAD，并用发现列表、简报、报告文件和打印的diff路径分派[re-review-prompt.md](re-review-prompt.md)。重审者判决每个发现ADDRESSED或NOT ADDRESSED并仅在修复diff中标记新破坏。修复diff中的新Critical/Important破坏加入开放发现列表。范围外观察进入账本作为延迟minor——它们永远不扩展循环。

**每轮后，** 附加到账本：
`Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <finding one-liners>; commits <a7>..<b7>)`

永远不要在控制器会话中自己修复发现——你的上下文保持干净用于协调，控制器修复跳过审查。

**断路器。** 当第5轮重审仍留下发现开放时，停止分派。自己裁决每个开放发现——你持有计划和审查者缺乏的跨任务上下文：

- **审查者错了，或点可争议：** 停放它——`Task <N>: parked — <finding> — Ruling: <why the code stands>`。最终审查看到双方。
- **真实的，但下游没有构建于它：** 以相同方式停放，裁决它是真实的并延迟。
- **真实且承载——** 后续任务构建于它，或它揭示计划缺陷：裁决最小更改以解锁依赖工作，记录它为`Task <N>: Ruling: <finding> — <what you decided and why>`，并携带它到下一个任务的分派。静默停放结构失败让每个依赖任务构建于它。仅当缺陷留下每条前进路径都是猜测时停止。

仅在上限裁决。提前裁决以结束循环是不同名称的预判。每个裁决是账本条目——静默丢弃被禁止。

#### 5. 完成任务

当审查返回干净——或每个开放发现以裁决在上限停放——在同一消息中附加完成行到账本与其他簿记：

- `Task <N>: complete (commits <base7>..<head7>, review clean)`
- `Task <N>: complete (commits <base7>..<head7>, <K> parked)` 后断路器跳闸

然后标记待办完成并继续。永远不要在审查有既未修复也未停放以裁决在上限的开放Critical/Important问题时移动到下一个任务。

### 2.6 最终审查

最终全分支审查也获得一个包：运行`scripts/review-package PLAN_FILE MERGE_BASE HEAD`（MERGE_BASE = 分支开始的提交，例如`git merge-base main HEAD`）并在最终审查分派中包含打印的路径，以便最终审查者读取一个文件而不是用git命令重新派生分支diff。在最强大的可用模型上分派（见模型选择），使用 superpowers:requesting-code-review的[code-reviewer.md](../requesting-code-review/code-reviewer.md)。将其指向账本的延迟minor和停放行以便它可以分类哪些必须在合并前修复。

如果最终全分支审查返回发现，分派一个修复子代理，携带完整发现列表——不是每个发现一个修复器。每个发现修复器各自重建上下文并重新运行套件；真实会话的最终审查修复波成本超过其所有任务的总和。然后恰好运行一次修复波的范围重审（`scripts/review-package PLAN_FILE FIX_BASE HEAD`超过修复范围，[re-review-prompt.md](re-review-prompt.md)）。裁决任何残余发现在任务循环的断路器中：停放以裁决，或裁决承载的并记录你决定的。只有上面四类在此阻止你。没有第二次修复波——残余承载发现在你的伙伴在完成开发分支呈现选项时浮现。

### 2.7 完成

在删除任何内容前，收集每个包含`Ruling:`的账本行——预飞行裁决、停放发现、断路器裁决、所有——在你的最终消息下"我做的裁决"，按你做的顺序，每个附带如果错了付出什么代价。列表是详尽的：如果账本持有裁决，列表持有它。该列表是你代替伙伴做的决定唯一到达他们的地方——他们阅读并重做你弄错的任何内容。随工作区死亡的裁决是秘密做的决定。

当最终全分支审查干净且其修复已合并，删除此计划的工作区（`rm -rf <workspace>`）——git历史现在是记录。兄弟目录属于其他计划；让它们 alone。

使用 superpowers:finishing-a-development-branch。

### 2.8 常见借口

| 借口 | 现实 |
|------|------|
| "接近规格合规" | 审查者发现规格差距 = 未完成。修复或达到上限并裁决——那些是唯二出口。 |
| "我自己修复，分派是开销" | 控制器修复污染你的上下文并跳过审查。恢复实现者。 |
| "再一轮会收敛" | 超过上限，轮次不收敛——失败是结构性的。裁决并路由。 |
| "审查者只会找到新东西" | 范围重审验证修复；它们不能漫游。未触及代码的新发现进入账本，不是循环。 |
| "这个发现显然错，我会丢弃" | 你仅在上限裁决，每个裁决是账本条目。静默丢弃被禁止。 |
| "修复很小，跳过重审" | 未审查的修复是回归着陆的方式。每轮以范围重审结束。 |
| "审查减慢循环" | 没有审查的循环只是未验证的搅拌。审查是循环的刹车和转向。 |
| "账本簿记是开销" | 账本是压缩后存活的东西。没有一个的控制器已经重新分派了整个完成的任务序列。 |
| "实现者生成了自己的审查者——免费额外保证" | 它是审查相同diff的重复席位；任务审查是门。工人生成的审查者是要标记的缺陷，不是严格。 |

## 3. Writing Plans

### 3.1 核心原则

```
假设工程师对我们的代码库零上下文，判断力有问题。
文档化他们需要知道的一切：每个任务接触哪些文件、代码、测试、
他们可能需要检查的文档、如何测试它。给他们整个计划作为小任务。
DRY。YAGNI。TDD。频繁提交。
```

假设他们是熟练的开发者，但对我们的工具集或问题域几乎一无所知。假设他们不太了解好的测试设计。

### 3.2 计划文档头部

**每个计划必须以此头部开始：**

```markdown
# [功能名称] 实现计划

> **对于代理工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话描述构建什么]

**架构：** [2-3句话描述方法]

**技术栈：** [关键技术/库]

**规格：** [此计划实现的规格/设计文档路径——计划从规格论证，所以规格随它一起；执行者读取两者]

## 全局约束

[规格的项目级要求——版本下限、依赖限制、命名和复制规则、平台要求——每行一个，从规格逐字复制。每个任务的需求隐式包含此部分。]

---
```

### 3.3 任务结构

```markdown
### Task N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[此任务使用早期任务的内容——确切签名]
- 生产：[后续任务依赖的内容——确切函数名、参数和返回类型。任务的实现者只看到他们自己的任务；这个块是他们如何学习相邻任务使用的名称和类型。]

- [ ] **步骤1：写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤2：运行测试验证失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL with "function not defined"

- [ ] **步骤3：写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤4：运行测试验证通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
```

### 3.4 禁止占位符

每个步骤必须包含工程师需要的实际内容。这些是**计划失败**——永远不要写它们：
- "TBD"、"TODO"、"之后实现"、"填写细节"
- "添加适当的错误处理" / "添加验证" / "处理边缘情况"
- "为上述编写测试"（没有实际测试代码）
- "类似于任务N"（重复代码——工程师可能按顺序读取任务）
- 描述做什么但不展示如何的步骤（代码步骤需要代码块）
- 引用未在任何任务中定义的类型、函数或方法

### 3.5 自我审查

编写完整计划后，用新鲜眼光查看规格并检查计划对照它。这是你自己运行的检查清单——不是子代理分派。

**1. 规格覆盖：** 浏览规格的每个部分/需求。你能指出实现它的任务吗？列出任何差距。

**2. 占位符扫描：** 搜索你的计划中的红旗——"禁止占位符"部分中的任何模式。修复它们。

**3. 类型一致性：** 你在后期任务中使用的类型、方法签名和属性名称是否与你在早期任务中定义的匹配？在任务3中称为`clearLayers()`但在任务7中称为`clearFullLayers()`的函数是bug。

如果发现问题，就地修复。不需要重新审查——只需修复并继续。如果发现没有任务的规格需求，添加任务。

### 3.6 执行交接

保存计划后，提供执行选择：

**"计划完成并保存到`docs/superpowers/plans/<filename>.md`。两种执行选项：**

**1. 子代理驱动（推荐）** - 我每个任务分派一个新子代理，任务间审查，快速迭代

**2. 内联执行** - 在此会话中使用executing-plans执行任务，带检查点的批量执行

**哪种方法？"**

## 4. Verification Before Completion

### 4.1 核心原则

```
证据优先于声明，总是如此。
```

**铁律：**
```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

如果你没有在此消息中运行验证命令，你不能声称它通过。

### 4.2 门控功能

```
在声称任何状态或表达满意之前：

1. 识别：什么命令证明这个声明？
2. 运行：执行完整命令（新鲜、完整）
3. 读取：完整输出，检查退出码，计算失败数
4. 验证：输出是否确认声明？
   - 否：陈述实际状态并附证据
   - 是：陈述声明并附证据
5. 只有然后：做出声明

跳过任何步骤 = 撒谎，不是验证
```

### 4.3 常见失败

| 声明 | 需要 | 不足够 |
|------|------|--------|
| 测试通过 | 测试命令输出：0失败 | 之前的运行，"应该通过" |
| Linter干净 | Linter输出：0错误 | 部分检查，推断 |
| 构建成功 | 构建命令：退出0 | Linter通过，日志看起来好 |
| Bug修复 | 测试原始症状：通过 | 代码更改，假设修复 |
| 回归测试工作 | RED-GREEN循环验证 | 测试通过一次 |
| 代理完成 | VCS diff显示更改 | 代理报告"成功" |
| 需求满足 | 逐行检查清单 | 测试通过 |

### 4.4 红旗 - 停止

- 使用"应该"、"可能"、"似乎"
- 在验证前表达满意（"很好！"、"完美！"、"完成！"等）
- 即将提交/推送/PR而没有验证
- 信任代理成功报告
- 依赖部分验证
- 想"就这一次"
- 疲惫并希望工作结束
- **任何暗示成功而没有运行验证的措辞**

### 4.5 合理化预防

| 借口 | 现实 |
|------|------|
| "现在应该工作了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter通过了" | Linter ≠ 编译器 |
| "代理说成功" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查足够" | 部分证明不了什么 |
| "不同措辞所以规则不适用" | 精神胜于字母 |

### 4.6 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34通过] "所有测试通过"
❌ "现在应该通过了" / "看起来正确"
```

**回归测试（TDD RED-GREEN）：**
```
✅ 写 → 运行（通过） → 恢复修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ "我已经写了回归测试"（没有RED-GREEN验证）
```

**构建：**
```
✅ [运行构建] [看到：退出0] "构建通过"
❌ "Linter通过了"（Linter不检查编译）
```

**需求：**
```
✅ 重新读取计划 → 创建检查清单 → 验证每个 → 报告差距或完成
❌ "测试通过，阶段完成"
```

**代理委派：**
```
✅ 代理报告成功 → 检查VCS diff → 验证更改 → 报告实际状态
❌ 信任代理报告
```

### 4.7 何时应用

**在以下之前总是应用：**
- 任何成功/完成声明的变体
- 任何满意的表达
- 关于工作状态的任何肯定陈述
- 提交、PR创建、任务完成
- 移动到下一个任务
- 委派给代理

**规则适用于：**
- 确切短语
- 意译和同义词
- 成功的暗示
- 建议完成/正确的任何通信

### 4.8 PDCA 借鉴点

| 借鉴实践 | 实现位置 | 具体实现 |
|---------|---------|---------|
| 验证门控 | pdca-check 技能 | 在任务完成声明前强制执行验证 |
| 证据优先 | pdca-check 技能 | 创建验证检查清单和模板 |
| 红旗列表 | pdca-check 技能 | 添加到任务验证指南中 |
| 关键模式 | pdca-check 技能 | 添加测试、构建、需求验证模式 |

## 5. Systematic Debugging

### 5.1 核心原则

```
永远先找根因，再尝试修复。症状修复是失败。
```

**铁律：**
```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你没有完成阶段1，你不能提议修复。

### 5.2 何时使用

用于任何技术问题：
- 测试失败
- 生产中的bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下情况使用：**
- 时间压力下（紧急情况让猜测诱人）
- "只是一个快速修复"似乎明显
- 你已经尝试多个修复
- 先前修复不起作用
- 你不完全理解问题

**不要跳过当：**
- 问题似乎简单（简单bug也有根因）
- 你匆忙（匆忙保证重做）
- 经理想要立即修复（系统化比折腾快）

### 5.3 四个阶段

你必须完成每个阶段然后才能进行到下一个。

#### 阶段1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **一致地重现**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 如果不可重现 → 收集更多数据，不要猜测

3. **检查最近更改**
   - 什么更改可能导致这个？
   - Git diff、最近提交
   - 新依赖、配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提议修复之前，添加诊断工具：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录退出组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次以收集证据显示它在哪里断裂
   然后分析证据以识别失败的组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 层1：工作流
   echo "=== 工作流中可用的密钥：==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 层2：构建脚本
   echo "=== 构建脚本中的环境变量：==="
   env | grep IDENTITY || echo "IDENTITY 不在环境中"

   # 层3：签名脚本
   echo "=== 钥匙串状态：==="
   security list-keychains
   security find-identity -v

   # 层4：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪层失败（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误在调用栈深处时：**

   参见此目录中的`root-cause-tracing.md`了解完整的向后追踪技术。

   **快速版本：**
   - 坏值来自哪里？
   - 谁用坏值调用这个？
   - 继续追踪直到找到源头
   - 在源头修复，不是在症状

#### 阶段2：模式分析

**在修复前找到模式：**

1. **找到工作示例**
   - 在相同代码库中定位类似的工作代码
   - 什么工作类似于什么坏了？

2. **与参考比较**
   - 如果实现模式，完整阅读参考实现
   - 不要略读 - 逐行阅读
   - 在应用前完全理解模式

3. **识别差异**
   - 工作和坏的之间有什么不同？
   - 列出每个差异，无论多小
   - 不要假设"那不重要"

4. **理解依赖**
   - 这需要什么其他组件？
   - 什么设置、配置、环境？
   - 它做什么假设？

#### 阶段3：假设和测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为X是根因因为Y"
   - 写下来
   - 具体，不模糊

2. **最小化测试**
   - 做最小可能的更改来测试假设
   - 一次一个变量
   - 不要一次修复多个东西

3. **继续前验证**
   - 它工作了吗？是 → 阶段4
   - 没有工作？形成新假设
   - 不要在上面添加更多修复

4. **当你不知道时**
   - 说"我不理解X"
   - 不要假装知道
   - 寻求帮助
   - 研究更多

#### 阶段4：实现

**修复根因，不是症状：**

1. **创建失败测试用例**
   - 最简单的重现
   - 如果可能，自动化测试
   - 如果没有框架，一次性测试脚本
   - 修复前必须有
   - 使用`superpowers:test-driven-development`技能编写正确的失败测试

2. **实现单一修复**
   - 解决识别的根因
   - 一次一个更改
   - 没有"我在这里"的改进
   - 没有捆绑重构

3. **验证修复**
   - 测试现在通过？
   - 没有其他测试被破坏？
   - 问题实际解决？
   - 在声称成功前使用`superpowers:verification-before-completion`技能

4. **如果修复不起作用**
   - 停止
   - 计数：你尝试了多少修复？
   - 如果<3：返回阶段1，用新信息重新分析
   - **如果≥3：停止并质疑架构（下面的步骤5）**
   - 不要在没有架构讨论的情况下尝试修复#4

5. **如果3+修复失败：质疑架构**

   **指示架构问题的模式：**
   - 每个修复在不同地方揭示新共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每个修复在其他地方创建新症状

   **停止并质疑基础：**
   - 这个模式从根本上合理吗？
   - 我们是"仅凭惯性坚持"吗？
   - 我们应该重构架构 vs 继续修复症状？

   **在尝试更多修复前与你的伙伴讨论**

   这不是失败的假设——这是错误的架构。

### 5.4 红旗 - 停止并遵循流程

如果你发现自己在想：
- "现在快速修复，之后调查"
- "只是尝试改变X看看它是否工作"
- "添加多个更改，运行测试"
- "跳过测试，我会手动验证"
- "可能是X，让我修复那个"
- "我不完全理解但这可能工作"
- "模式说X但我会不同地适配它"
- "这是主要问题：[列出修复而没有调查]"
- 在追踪数据流之前提议解决方案
- **"再一个修复尝试"（当已经尝试2+时）**
- **每个修复在不同地方揭示新问题**

**所有这些都意味着：停止。返回阶段1。**

**如果3+修复失败：** 质疑架构（见阶段4.5）

### 5.5 你的伙伴信号你做错了

**观察这些重定向：**
- "那不是发生吗？" - 你假设没有验证
- "它会显示我们...？" - 你本应该添加证据收集
- "停止猜测" - 你在没有理解的情况下提议修复
- "超想这个" - 质疑基础，不仅仅是症状
- "我们卡住了？"（沮丧） - 你的方法不起作用

**当你看到这些：** 停止。返回阶段1。

### 5.6 常见借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单bug很快。 |
| "紧急情况，没有时间流程" | 系统化调试比猜测-检查折腾更快。 |
| "先尝试这个，然后调查" | 第一个修复设置模式。从一开始做对。 |
| "确认修复工作后我会写测试" | 未测试的修复不持久。先测试证明它。 |
| "一次多个修复节省时间" | 无法隔离什么工作了。导致新bug。 |
| "参考太长，我会适配模式" | 部分理解保证bug。完整阅读它。 |
| "我看到问题，让我修复" | 看到症状 ≠ 理解根因。 |
| "再一个修复尝试"（2+失败后） | 3+失败 = 架构问题。质疑模式，不要再修复。 |

### 5.7 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 阅读错误、重现、检查更改、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找到工作示例、比较 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug解决，测试通过 |

### 5.8 当流程揭示"无根因"时

如果系统化调查揭示问题确实是环境的、时间依赖的或外部的：

1. 你已经完成流程
2. 文档化你调查的内容
3. 实现适当的处理（重试、超时、错误消息）
4. 添加监控/日志以供未来调查

**但是：** 95%的"无根因"案例是不完整的调查。

| 借鉴实践 | 实现位置 | 具体实现 |
|---------|---------|---------|
| 四阶段调试 | pdca-check 技能 | 集成根因调查 → 模式分析 → 假设测试 → 实现流程 |
| 证据收集 | pdca-check 技能 | 在修复前强制执行证据收集 |
| 3次修复规则 | pdca-check 技能 | 3+修复失败后质疑架构 |
| 红旗列表 | pdca-check 技能 | 添加到调试检查清单中 |
| 快速参考表 | pdca-check 技能 | 创建调试快速参考表 |

## 6. Brainstorming

### 6.1 核心原则

```
在任何创意工作之前，你必须探索用户意图、需求和设计。
```

**硬门控：**
```
不要调用任何实现技能、编写任何代码、搭建任何项目，
或采取任何实现操作，直到你告诉你的伙伴你打算做什么
并且他们批准了它。
这适用于下面每个路径上的每个任务——仪式随任务缩放；审批门不会。
```

### 6.2 三条路径

在你的第一个问题之前，分类请求并大声说出分类——"这看起来是有范围的，所以我会在这里呈现一个简短的设计而不是写规格"——以便你的伙伴可以覆盖它：

- **Spike** — 可行性问题（"我们能..."，"是否可能..."，"快速脏的可以"）其输出是答案，不是你保留的代码。呈现问题和你将在2-3句话中尝试的内容，获得点头，然后尽可能便宜地正确找出。没有设计文档，没有规格文件。将发现报告为建议；你构建的任何内容保持标记为一次性。

- **Bounded** — 对此仓库中已经存在的代码的良好范围更改：新标志、小端点、单文件修复。理解应用程序的种类不够——范围意味着你正在更改的流程已经在这里可以读取。如果没有现有流程可更改，任务不是范围的。询问重要的澄清问题，在聊天中呈现简短设计（几句话到几个短段落），然后停止。实现仅在你的伙伴说对该设计同意后开始——范围任务的审批与架构任务一样是硬门控。没有规格文件，没有实现计划文档。

- **Architectural** — 新项目、新子系统、重构组件如何组合或改变其他依赖的接口的更改。遵循完整流程：问题、方法、分段设计、写规格，然后writing-plans技能。

当两个路径之间有疑问时，取更重的。棘轮是单向的：任务中发现的隐藏复杂性升级路径——停止，这么说，并升级。没有什么在任务中降级。

### 6.3 反模式："太简单不需要审批"

每个路径以你的伙伴在实现前审批你的意图结束。待办事项列表、单函数工具、配置更改——设计可能是在聊天中的两句话，但你必须呈现它并获得同意。"简单"任务是未检查假设导致最多浪费工作的地方。随简单性缩放的是工件，永远不是审批。

### 6.4 红旗

| 想法 | 现实 |
|------|------|
| "这太简单不需要设计" | 简单意味着简短设计，不是没有设计。聊天中两句话，然后审批。 |
| "我会称它为范围的并跳过规格" | 伸手拿标签以跳过工作就是怀疑——取更重的路径。 |
| "它是范围的，设计明显——我会在他们阅读时开始" | 门是审批，不是设计的长度。呈现，然后停止直到听到同意。 |
| "我理解这种应用程序，所以它是范围的" | 范围衡量仓库，不是你的熟悉度。新项目没有现有流程——它是架构的。 |
| "Spike工作了，所以我会保留代码" | Spike的输出是答案。保留代码是新请求——分类它。 |
| "它增长了，但我快完成了——不需要重新分类" | 隐藏复杂性在任务中升级路径。停止并这么说。 |
| "他们批准了Spike，所以后续更改也批准了" | 每个任务获得自己的分类和自己的审批。 |

### 6.5 检查清单

分类后，宣布路径，然后为路径上的每个项目创建任务并按顺序完成它们。

**Spike：**
1. **探索项目上下文** — 足够以框架探测
2. **呈现问题+探测计划** — 2-3句话
3. **获得审批** — 点头足够
4. **调查** — 尽可能便宜地正确
5. **报告发现** — 建议；标记任何构建的内容为一次性

**Bounded：**
1. **探索项目上下文** — 检查文件、文档、最近提交
2. **询问澄清问题** — 一次一个，重要的那些
3. **在聊天中呈现简短设计** — 方法、接触的文件、测试
4. **获得审批** — 停止并等待明确同意；在同一呼吸中呈现设计和开始是跳过门
5. **实现** — 继续正常开发工作流（TDD适用）；没有计划文档

**Architectural：**
1. **探索项目上下文** — 检查文件、文档、最近提交
2. **提供可视化伴侣** — 不是预先。第一次问题如果显示会比描述更清晰时，然后提供它（它自己的消息）；批准后，其浏览器标签为你打开。如果没有视觉问题出现，永远不提供。见下面的可视化伴侣部分。
3. **询问澄清问题** — 一次一个，理解目的/约束/成功标准
4. **提议2-3种方法** — 附带权衡和你的推荐
5. **呈现设计** — 按其复杂性缩放的部分，每个部分后获得用户批准
6. **写设计文档** — 保存到`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`并提交
7. **规格自我审查** — 快速内联检查占位符、矛盾、歧义、范围（见下面）
8. **用户审查书面规格** — 要求用户在继续前审查规格文件
9. **转换到实现** — 调用writing-plans技能创建实现计划

### 6.6 过程流程

```
分类: spike / bounded / architectural
  ↓
Spike: 呈现问题+探测(2-3句话) → 人类批准？ → 调查；报告建议
  ↓
Bounded: 询问澄清问题 → 在聊天中呈现简短设计 → 人类批准？ → 实现（无计划文档）
  ↓
Architectural: 探索项目上下文 → 询问澄清问题 → 提议2-3种方法 → 呈现设计部分 → 
  用户批准设计？ → 写设计文档 → 规格自我审查 → 用户审查规格？ → 调用writing-plans技能
```

**终端状态是路径绑定的。** Architectural：你在头脑风暴后调用的唯一技能是writing-plans——永远不是frontend-design、mcp-builder或任何其他实现技能。Bounded：批准后，实现直接通过正常开发工作流进行；没有计划文档。Spike：终端状态是报告的建议。

### 6.7 过程

下面的子部分服务于范围和架构路径（Spike在"呈现探测，获得点头"处停止）。从**探索方法**开始的部分是架构路径深度——对于范围工作，上下文加几个问题加聊天中的简短设计是整个过程。

**理解想法：**

- 首先检查当前项目状态（文件、文档、最近提交）
- 在询问详细问题之前，评估范围：如果请求描述多个独立子系统（例如，"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记这个。不要花问题来完善需要分解的项目的细节。
- 如果项目太大无法单个规格，帮助用户分解为子项目：独立的部分是什么，它们如何相关，应该按什么顺序构建？然后通过正常设计流程头脑风暴第一个子项目。每个子项目获得自己的规格 → 计划 → 实现周期。
- 对于适当范围的项目，一次询问一个问题以完善想法
- 尽可能使用多选问题，但开放式也可以
- 每条消息一个问题——如果主题需要更多探索，将其分解为多个问题
- 专注于理解：目的、约束、成功标准

**探索方法：**

- 提议2-3种不同方法，附带权衡
- 以对话方式呈现选项，附带你的推荐和推理
- 以你的推荐选项开始并解释原因
- YAGNI无情地——从每个方法和设计中移除不必要的功能

**呈现设计：**

- 一旦你相信你理解你在构建什么，呈现设计
- 按其复杂性缩放每个部分：如果简单，几句话；如果细致，最多200-300字
- 每个部分后询问是否到目前为止看起来正确
- 覆盖：架构、组件、数据流、错误处理、测试
- 准备回去澄清如果有不理解的内容

**为隔离和清晰设计：**

- 将系统分解为更小的单元，每个有一个清晰目的，通过明确定义的接口通信，可以独立理解和测试
- 对于每个单元，你应该能够回答：它做什么，如何使用它，以及它依赖什么？
- 某人可以在不阅读其内部的情况下理解单元做什么吗？你可以在不破坏消费者的情况下更改内部吗？如果不是，边界需要工作。
- 更小、良好绑定的单元也更容易与你一起工作——你更好地推理你可以一次放在上下文中的代码，并且当文件集中时你的编辑更可靠。当文件变大时，那通常是它做太多事情的信号。

**在现有代码库中工作：**

- 在提议更改之前探索当前结构。遵循现有模式。
- 其中现有代码有影响工作的质量问题（例如，增长太大的文件、不清晰的边界、纠缠的职责），将有针对性的改进作为设计的一部分——就像一个好的开发人员改进他们正在工作的代码一样。
- 不要提议不相关的重构。专注于服务当前目标的内容。

### 6.8 设计之后（架构路径）

**文档化：**

- 将验证的设计（规格）写入`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
  - （用户对规格位置的偏好覆盖此默认）
- 使用elements-of-style:writing-clearly-and-concisely技能如果可用
- 将设计文档提交到git

**规格自我审查：**
编写规格文档后，用新鲜眼光查看它：

1. **占位符扫描：** 任何"TBD"、"TODO"、不完整部分或模糊需求？修复它们。
2. **内部一致性：** 任何部分矛盾吗？架构匹配功能描述吗？
3. **范围检查：** 这是否足够集中于单个实现计划，或者需要分解？
4. **歧义检查：** 任何需求可以被解释为两种不同方式？如果是，选择一个并使其明确。

就地修复任何问题。不需要重新审查——只需修复并继续。

**用户审查门控：**
规格审查循环通过后，要求用户在继续前审查书面规格：

> "规格已写入并提交到`<path>`。请审查它并在我们开始编写实现计划之前告诉我是否要进行任何更改。"

等待用户的响应。如果他们请求更改，进行更改并重新运行规格审查循环。只有用户批准后才继续。

**实现：**

- 调用writing-plans技能创建详细的实现计划
- 不要调用任何其他技能。writing-plans是下一步。

| 硬门控 | pdca-plan 技能 | 在实现前强制执行设计审批 |

## 7. Receiving Code Review

### 7.1 核心原则

```
代码审查需要技术评估，而不是情感表演。
```

**验证后再实现。先问后假设。技术正确性胜过社交舒适。**

### 7.2 响应模式

```
当接收代码审查反馈时：

1. 阅读：完整反馈不反应
2. 理解：用自己的话重述需求（或询问）
3. 验证：对照代码库现实检查
4. 评估：对THIS代码库技术上健全？
5. 响应：技术确认或有理由的反驳
6. 实现：一次一个，测试每个
```

### 7.3 禁止响应

**永远不要：**
- "你完全正确！"（显式指令文件违规）
- "好观点！" / "优秀反馈！"（表演性）
- "让我现在实现那个"（验证前）

**改为：**
- 重述技术需求
- 询问澄清问题
- 如果错误，用技术推理反驳
- 只是开始工作（行动 > 言语）

### 7.4 处理不清晰反馈

```
如果任何项目不清晰：
  停止 - 不要现在实现任何东西
  询问不清晰项目的澄清

为什么：项目可能相关。部分理解 = 错误实现。
```

**示例：**
```
你的伙伴："修复1-6"
你理解1,2,3,6。不清楚4,5。

❌ 错误：现在实现1,2,3,6，之后询问4,5
✅ 正确："我理解项目1,2,3,6。需要澄清4和5才能继续。"
```

### 7.5 来源特定处理

#### 来自你的伙伴
- **可信** — 理解后实现
- **仍然询问** 如果范围不清晰
- **没有表演性同意**
- **跳到行动** 或技术确认

#### 来自外部审查者
```
实现前：
  1. 检查：对THIS代码库技术上正确？
  2. 检查：破坏现有功能？
  3. 检查：当前实现的原因？
  4. 检查：在所有平台/版本上工作？
  5. 检查：审查者理解完整上下文？

如果建议似乎错误：
  用技术推理反驳

如果无法轻松验证：
  说："我无法在没有[X]的情况下验证这个。我应该[调查/询问/继续]吗？"

如果与你的伙伴先前决策冲突：
  停止并与你的伙伴讨论
```

**你的伙伴规则：** "外部反馈 - 怀疑，但仔细检查"

### 7.6 "专业"功能的YAGNI检查

```
如果审查者建议"正确实现"：
  grep代码库以实际使用

  如果未使用："此端点未被调用。移除它（YAGNI）？"
  如果使用：那么正确实现
```

**你的伙伴规则：** "你和审查者都向我报告。如果我们不需要此功能，不要添加它。"

### 7.7 实现顺序

```
对于多项目反馈：
  1. 首先澄清任何不清晰的
  2. 然后按此顺序实现：
     - 阻塞问题（崩溃、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 测试每个修复单独
  4. 验证无回归
```

### 7.8 何时反驳

反驳当：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反YAGNI（未使用功能）
- 对此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的伙伴的架构决策冲突

**如何反驳：**
- 使用技术推理，不是防御性
- 询问具体问题
- 引用工作测试/代码
- 如果是架构的，涉及你的伙伴

**如果你不舒服大声反驳：** 命名该紧张，然后告诉你的伙伴你看到的问题。他们会感谢你的诚实。

### 7.9 确认正确反馈

当反馈确实是正确的：
```
✅ "已修复。[描述更改内容]"
✅ "好发现 - [具体问题]。在[位置]修复。"
✅ [只是修复它并在代码中显示]

❌ "你完全正确！"
❌ "好观点！"
❌ "谢谢你发现那个！"
❌ "谢谢[任何东西]"
❌ 任何感激表达

为什么没有感谢：行动说话。只是修复它。代码本身显示你听到了反馈。
```

**如果你发现自己要写"谢谢"：** 删除它。陈述修复。

### 7.10 优雅纠正你的反驳

如果你反驳且你错了：
```
✅ "你是对的 - 我检查了[X]它做[Y]。现在实现。"
✅ "已验证这是正确的。我最初的理解错误因为[原因]。修复。"

❌ 长道歉
❌ 为为什么你反驳辩护
❌ 过度解释
```

事实陈述纠正并继续。

### 7.11 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 陈述需求或只是行动 |
| 盲目实现 | 对照代码库验证 |
| 批量没有测试 | 一次一个，测试每个 |
| 假设审查者正确 | 检查是否破坏东西 |
| 避免反驳 | 技术正确性 > 舒适 |
| 部分实现 | 首先澄清所有项目 |
| 无法验证，继续 | 陈述限制，询问方向 |

### 7.12 PDCA 借鉴点

| 借鉴实践 | 实现位置 | 具体实现 |
|---------|---------|---------|
| 响应模式 | pdca-check 技能 | 集成代码审查接收流程 |
| 禁止响应列表 | pdca-check 技能 | 添加到代码审查指南中 |
| 来源特定处理 | pdca-check 技能 | 区分伙伴和外部审查者反馈 |
| 实现顺序 | pdca-check 技能 | 添加到代码审查检查清单中 |

## 8. Requesting Code Review

### 8.1 核心原则

```
早期审查，频繁审查。
```

### 8.2 何时请求审查

**强制性：**
- 子代理驱动开发中每个任务后
- 完成主要功能后
- 合并到主分支前

**可选但有价值：**
- 卡住时（新鲜视角）
- 重构前（基线检查）
- 修复复杂bug后

### 8.3 如何请求

**1. 获取git SHA：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
HEAD_SHA=$(git rev-parse HEAD)
```

**2. 分派代码审查者子代理：**

分派`general-purpose`子代理，填充[code-reviewer.md](code-reviewer.md)中的模板

**占位符：**
- `{DESCRIPTION}` - 你构建的内容简要总结
- `{PLAN_OR_REQUIREMENTS}` - 它应该做什么
- `{BASE_SHA}` - 起始提交
- `{HEAD_SHA}` - 结束提交

**3. 处理反馈：**
- 立即修复Critical问题
- 继续前修复Important问题
- 注意Minor问题供以后
- 如果审查者错了则反驳（附推理）

### 8.4 示例

```
[刚完成任务2：添加验证函数]

你：在继续前请求代码审查。

BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | awk '{print $1}')
HEAD_SHA=$(git rev-parse HEAD)

[分派代码审查者子代理]
  DESCRIPTION: 添加了 verifyIndex() 和 repairIndex()，4种问题类型
  PLAN_OR_REQUIREMENTS: 部署计划中的任务2
  BASE_SHA: a7981ec
  HEAD_SHA: 3df7661

[子代理返回]：
  优势：清晰架构，真实测试
  问题：
    Important: 缺少进度指示器
    Minor: 魔术数字(100)用于报告间隔
  评估：准备继续

你：[修复进度指示器]
[继续任务3]
```

### 8.5 常见借口

| 借口 | 现实 |
|------|------|
| "我会自己审查diff而不是分派审查者" | 你是协调者——内联审查diff会燃烧你需要保持驱动工作的上下文窗口。分派审查者子代理：diff和评估在其上下文中，只有发现回到你。 |
| "审查者需要我的整个会话历史来理解更改" | 将其精确制作的上下文，永远不是你的会话历史。这保持审查者在工作产品上，而不是你的思考过程。 |

### 8.6 红旗

**永远不要：**
- 因为"它很简单"跳过审查
- 忽略Critical问题
- 继续有未修复的Important问题
- 与有效技术反馈争论

**如果审查者错了：**
- 用技术推理反驳
- 展示证明它工作的测试/代码
- 请求澄清

见[code-reviewer.md](code-reviewer.md)中的模板。

| 借鉴实践 | 实现位置 | 具体实现 |
|---------|---------|---------|
| 审查时机 | pdca-check 技能 | 集成代码审查请求流程 |
| 分派模板 | pdca-check 技能 | 创建代码审查分派模板 |
| 反馈处理 | pdca-check 技能 | 集成审查反馈处理流程 |

## 9. Writing Skills

### 9.1 核心原则

```
编写技能就是应用于流程文档的测试驱动开发。
```

你编写测试用例（带子代理的压力场景），观察它们失败（基线行为），编写技能（文档），观察测试通过（代理遵守），并重构（关闭漏洞）。

**核心原则：** 如果你没有观察代理在没有技能的情况下失败，你不知道技能是否教授正确的内容。

**必需背景：** 你必须理解superpowers:test-driven-development才能使用此技能。该技能定义了基本的RED-GREEN-REFACTOR循环。此技能将TDD应用于文档。

### 9.2 TDD映射到技能

| TDD概念 | 技能创建 |
|---------|---------|
| **测试用例** | 带子代理的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 代理在没有技能时违反规则（基线） |
| **测试通过（GREEN）** | 代理在有技能时遵守 |
| **重构** | 关闭漏洞同时保持遵守 |
| **先写测试** | 编写技能前运行基线场景 |
| **观察失败** | 记录代理使用的确切合理化 |
| **最小代码** | 编写针对这些特定违规的技能 |
| **观察通过** | 验证代理现在遵守 |
| **重构循环** | 找到新合理化 → 堵塞 → 重新验证 |

整个技能创建过程遵循RED-GREEN-REFACTOR。

### 9.3 何时创建技能

**创建当：**
- 技术对你来说不是直观明显的
- 你会跨项目再次引用这个
- 模式广泛适用（不是项目特定的）
- 其他人会受益

**不创建当：**
- 一次性解决方案
- 其他地方文档良好的标准实践
- 项目特定约定（放在你的指令文件中）
- 机械约束（如果可以用正则表达式/验证强制执行，自动化——为判断调用保存文档）

### 9.4 技能类型

**技术：** 要遵循的具体方法步骤（基于条件的等待、根因追踪）

**模式：** 思考问题的方式（带标志扁平化、测试不变量）

**参考：** API文档、语法指南、工具文档（办公室文档）

### 9.5 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主参考（必需）
    supporting-file.*     # 仅在需要时
```

**扁平命名空间** - 所有技能在一个可搜索命名空间

**单独文件用于：**
1. **重度参考**（100+行） - API文档、综合语法
2. **可重用工具** - 脚本、实用程序、模板

**保持内联：**
- 原则和概念
- 代码模式（< 50行）
- 其他所有内容

### 9.6 SKILL.md 结构

**前置元数据（YAML）：**
- 两个必需字段：`name`和`description`
- 总计最多1024字符
- `name`：仅使用字母、数字和连字符（无括号、特殊字符）
- `description`：第三人称，仅描述何时使用（不是它做什么）
  - 以"Use when..."开始以专注于触发条件
  - 包括具体症状、情况和上下文
  - **永远不要总结技能的过程或工作流**
  - 如果可能，保持在500字符以下

```markdown
---
name: Skill-Name-With-Hyphens
description: Use when [specific triggering conditions and symptoms]
---

# 技能名称

## 概述
这是什么？核心原则1-2句话。

## 何时使用
[小型内联流程图 IF 决策不明显]

带症状和用例的项目符号列表
何时不使用

## 核心模式（对于技术/模式）
前后代码比较

## 快速参考
用于扫描常见操作的表或项目符号

## 实现
简单模式的内联代码
重度参考或可重用工具的文件链接

## 常见错误
什么出错 + 修复

## 真实影响（可选）
具体结果
```

### 9.7 技能发现优化（SDO）

**对发现至关重要：** 未来的代理需要找到你的技能

#### 1. 丰富的描述字段

**目的：** 你的代理读取描述以决定对于给定任务加载哪些技能。使其回答："我现在应该读这个技能吗？"

**格式：** 以"Use when..."开始以专注于触发条件

**关键：描述 = 何时使用，不是技能做什么**

描述应仅描述触发条件。不要在描述中总结技能的过程或工作流。

**为什么重要：** 测试揭示当描述总结技能的工作流时，代理可能遵循描述而不是阅读完整技能内容。说"任务间代码审查"的描述导致代理做一次审查，即使技能的流程图清楚显示两次（规格合规然后代码质量）。

当描述更改为仅"使用时在当前会话中执行具有独立任务的实现计划"（无工作流总结）时，代理正确读取流程图并遵循两阶段审查过程。

**陷阱：** 总结工作流的描述创建代理将采取的快捷方式。技能体成为代理跳过的文档。

```yaml
# ❌ 坏：总结工作流 - 代理可能遵循这个而不是阅读技能
description: 使用时执行计划 - 每个任务分派子代理，任务间有代码审查

# ❌ 坏：太多过程细节
description: 使用时TDD - 先写测试，观察失败，写最小代码，重构

# ✅ 好：仅触发条件，无工作流总结
description: 使用时在当前会话中执行具有独立任务的实现计划

# ✅ 好：仅触发条件
description: 使用时实现任何功能或bug修复，在编写实现代码之前
```

**内容：**
- 使用具体触发、症状和情况表示此技能适用
- 描述*问题*（竞争条件、不一致行为），而不是*语言特定症状*（setTimeout、sleep）
- 除非技能本身特定于技术，否则保持触发技术无关
- 如果技能特定于技术，在触发中明确说明
- 以第三人称编写（注入系统提示）
- **永远不要总结技能的过程或工作流**

```yaml
# ❌ 坏：太抽象、模糊，不包括何时使用
description: 用于异步测试

# ❌ 坏：第一人称
description: 当测试使用setTimeout/sleep且不稳定时我可以帮助你

# ❌ 坏：提及技术但技能不特定于它
description: 使用时测试使用setTimeout/sleep且不稳定

# ✅ 好：以"Use when"开始，描述问题，无工作流
description: 使用时测试有竞争条件、时间依赖或不一致通过/失败

# ✅ 好：特定于技术的技能，带显式触发
description: 使用时使用React Router并处理认证重定向
```

- 系统调试 → Shell/Python

### 9.10 铁律（与TDD相同）

```
没有失败测试就没有技能
```

这适用于新技能和对现有技能的编辑。

编写技能前测试？删除它。重新开始。
编辑技能没有测试？相同违规。

**没有例外：**
- 不用于"简单添加"
- 不用于"只添加部分"
- 不用于"文档更新"
- 不保留未测试更改作为"参考"
- 不在运行测试时"适配"
- 删除意味着删除

### 9.11 测试所有技能类型

不同技能类型需要不同的测试方法：

#### 纪律强制技能（规则/要求）

**示例：** TDD、完成前验证、编码前设计

**测试使用：**
- 学术问题：他们理解规则吗？
- 压力场景：他们在压力下遵守吗？
- 多个压力组合：时间 + 沉没成本 + 疲劳
- 识别合理化并添加显式计数器

**成功标准：** 代理在最大压力下遵守规则

#### 技术技能（操作指南）

**示例：** 基于条件的等待、根因追踪、防御编程

**测试使用：**
- 应用场景：他们能正确应用技术吗？
- 变化场景：他们处理边缘情况吗？
- 缺失信息测试：指令有空白吗？

**成功标准：** 代理成功将技术应用于新场景

#### 模式技能（心理模型）

**示例：** 降低复杂性、信息隐藏概念

**测试使用：**
- 识别场景：他们识别模式何时适用吗？
- 应用场景：他们能使用心理模型吗？
- 反例：他们知道何时不应用吗？

**成功标准：** 代理正确识别何时/如何应用模式

#### 参考技能（文档/API）

**示例：** API文档、命令参考、库指南

**测试使用：**
- 检索场景：他们能找到正确信息吗？
- 应用场景：他们能正确使用找到的内容吗？
- 差距测试：常见用例覆盖了吗？

**成功标准：** 代理找到并正确应用参考信息

### 9.12 常见跳过测试的借口

| 借口 | 现实 |
|------|------|
| "技能显然清楚" | 对你清楚 ≠ 对其他代理清楚。测试它。 |
| "它只是参考" | 参考可以有空白、不清晰部分。测试检索。 |
| "测试过度" | 未测试的技能有问题。总是。15分钟测试节省数小时。 |
| "我会在问题出现时测试" | 问题 = 代理无法使用技能。部署前测试。 |
| "太乏味测试" | 测试比调试生产中的坏技能少乏味。 |
| "我有信心它好" | 过度自信保证问题。无论如何测试。 |
| "学术审查足够" | 阅读 ≠ 使用。测试应用。 |
| "没时间测试" | 部署未测试技能比稍后修复它更浪费时间。 |

**所有这些都意味着：部署前测试。没有例外。**

### 9.13 匹配形式到失败

在编写指导之前，分类基线失败。一种形式对一种失败类型有效，但对另一种显著适得其反。

| 基线失败 | 正确形式 | 错误形式 |
|---------|---------|---------|
| 压力下跳过/违反规则（知道更好，无论如何做） | 禁令 + 合理化表 + 红旗（见防弹下面） | 软指导（"优先..."、"考虑..."） |
| 合规，但输出形状错误（膨胀提示、埋没判决、重述规格） | 正面配方或合同：陈述输出是什么——其部分，按顺序 | 禁令列表（"不要重述"、"永远不要叙述"） |
| 从他们已经产生的东西中省略必需元素 | 结构性：模板中他们填充的必需字段或槽 | 模板附近的散文提醒 |
| 行为应依赖于条件 | 条件键控到可观察谓词（"如果简报存在，引用它"） | 无条件规则 + 豁免条款 |

**为什么禁令在塑造问题上适得其反：** 在竞争激励下（"使提示自包含"），代理与"不要X"谈判。在分派提示指导的逐字措辞测试中，禁令臂产生了明显更多不需要的内容而不是配方臂（完全分离的分布），甚至比无指导控制趋势更差——微测你自己的案例而不是假设，但永远不要默认伸手拿禁令。配方留下 nothing 谈判：输出匹配陈述的形状或不匹配。

**无论你选择哪种形式的规则：**
- **没有细微差别条款。** "不要X除非它重要"重新开放谈判——在获胜配方上附加单个细微差别条款将其从一致降级为噪音在同一措辞测试中。将真实例外表达为自己的可观察谓词条件。
- **豁免条款不范围。** "此限制不适用于代码块"仍然抑制代码块。如果输出的某部分必须豁免，重构使规则无法触及它。

### 9.14 防弹技能对抗合理化

强制纪律的技能（如TDD）需要抵抗合理化。代理很聪明，会在压力下找到漏洞。

**范围：** 此工具包用于纪律失败——知道规则但在压力下跳过的代理。对于错误形状输出或省略元素，基于禁令的防弹适得其反；使用匹配形式到失败中的形式。

**心理学说明：** 理解为什么说服技术有效帮助你系统地应用它们。见persuasion-principles.md了解研究基础（Cialdini, 2021; Meincke et al., 2025）关于权威、承诺、稀缺、社会证明和统一原则。

### 9.15 显式关闭每个漏洞

不要只陈述规则——禁止特定变通方法：

<坏>
```markdown
代码在测试之前？删除它。
```
</坏>

<好>
```markdown
代码在测试之前？删除它。重新开始。

**没有例外：**
- 不保留作为"参考"
- 不在写测试时"适配"
- 不看它
- 删除意味着删除
```
</好>

### 9.16 处理"精神vs字母"论点

在早期添加基础原则：

```markdown
**违反规则的字母就是违反规则的精神。**
```

这切断了整个类别的"我在遵循精神"合理化。

### 9.17 构建合理化表

从基线测试中捕获合理化（见下面的测试部分）。代理做的每个借口都进入表：

```markdown
| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码会出错。测试只需30秒。 |
| "我之后再测试" | 之后写的测试立即通过证明 nothing。 |
| "测试后写达到相同目标" | 测试后 = "这做什么？" 测试前 = "这应该做什么？" |
```

### 9.18 创建红旗列表

使代理在合理化时容易自我检查：

```markdown
## 红旗 - 停止并重新开始

- 代码在测试之前
- "我已经手动测试过了"
- "测试后达到相同目的"
- "这是关于精神不是仪式"
- "这不同因为..."

**所有这些都意味着：删除代码。用TDD重新开始。**
```

### 9.20 技能的RED-GREEN-REFACTOR

遵循TDD循环：

#### RED：写失败测试（基线）

在没有技能的情况下运行压力场景with子代理。记录确切行为：
- 他们做了什么选择？
- 他们使用了什么合理化（逐字）？
- 哪些压力触发了违规？

这是"观察测试失败"——你必须在编写技能之前看到代理自然做什么。

#### GREEN：写最小技能

编写针对这些特定合理化的技能。不要为假设情况添加额外内容。

用相同场景运行带技能。代理现在应该遵守。

#### REFACTOR：关闭漏洞

代理找到新合理化？添加显式计数器。重新测试直到防弹。

#### 微测试措辞在完整场景之前

完整压力场景运行是最终门，但它们慢且每次迭代昂贵。首先用微测试验证措辞本身：

1. **每次调用一个新鲜上下文样本** — 原始API调用，或单次子代理如果你没有API访问。系统提示 = 指导将生活在的真实上下文（完整技能或提示模板，不是孤立的指导）；用户消息 = 诱使失败的任务。
2. **总是包括无指导控制。** 如果控制不显示失败，没有什么需要修复——停止，不要编写指导。
3. **每个变体5+次。** 单样本撒谎。
4. **手动读取每个标记匹配。** 如果你喜欢，可以编程评分，但模板回声和引用的反例伪装为命中；自动计数单独高估失败和成功。
5. **方差是指标。** 当指导落地时，rep收敛于相同形状。五次不同解释 across 五次 rep 意味着措辞不绑定——在添加单词之前收紧形式。

微测试验证措辞；它们不替代纪律技能的压力场景。

**测试方法：** 见[testing-skills-with-subagents.md](testing-skills-with-subagents.md)了解完整测试方法论：
- 如何编写压力场景
- 压力类型（时间、沉没成本、权威、疲劳）
- 系统地堵住漏洞
- 元测试技术

### 9.22 停止：移至下一个技能前

**编写任何技能后，你必须停止并完成部署过程。**

**不要：**
- 批量创建多个技能而不测试每个
- 在当前技能验证前移至下一个技能
- 跳过测试因为"批处理更高效"

**下面的部署检查清单对每个技能是强制性的。**

部署未测试技能 = 部署未测试代码。这是质量标准违规。

### 9.23 技能创建检查清单（TDD适配）

**重要：为下面的每个检查清单项目创建待办事项。**

**RED阶段 - 写失败测试：**
- [ ] 创建压力场景（纪律技能3+组合压力）
- [ ] 在没有技能的情况下运行场景 - 逐字记录基线行为
- [ ] 识别合理化/失败中的模式

**GREEN阶段 - 写最小技能：**
- [ ] 名称仅使用字母、数字、连字符（无括号/特殊字符）
- [ ] YAML前置元数据带必需`name`和`description`字段（总计最多1024字符）
- [ ] 描述以"Use when..."开始，包括具体触发/症状
- [ ] 描述以第三人称编写
- [ ] 关键词 throughout 用于搜索（错误、症状、工具）
- [ ] 清晰概述带核心原则
- [ ] 解决RED阶段中识别的特定基线失败
- [ ] 指导形式匹配失败类型（见匹配形式到失败）
- [ ] 对于行为塑造指导：措辞微测试对抗无指导控制（5+次，每个标记匹配手动读取）——纯参考技能不适用
- [ ] 代码内联或链接到单独文件
- [ ] 一个优秀示例（不是多语言）
- [ ] 运行带技能场景 - 验证代理现在遵守

**REFACTOR阶段 - 关闭漏洞：**
- [ ] 从测试中识别新合理化
- [ ] 添加显式计数器（如果是纪律技能）
- [ ] 从所有测试迭代构建合理化表
