# 独立审查：定义与实现逐项对应

## REVIEW-01：第三场景，不是父 Agent 的放行操作

每个冻结树节点在审查场景有自己的完整PDCA任务、新Agent。执行Agent的Check属于自检；独立审查不得由原执行Agent继续充当，也不得把审查插为所有任务Do→Check的父层审批。

审查Agent只读固定本体/接口/suite、对应真实实现、明确导入的孩子审查包和证据。禁止读取执行Agent的活动对话来补齐缺失合同或受其解释左右；实现者说明可作具名待核实材料。共同模型仍可能共享偏差，新上下文不自动保证独立正确，应依赖外部事实、反例与可复核oracle。

## Plan / Do / Check / Act

Plan：固定工作/树/节点/release，列明全部约束与审查方法；采用节点verification suite，先测试审查方法对已知正确、已知违例、缺证据样本的识别力。实际用户确认按CONFIRM-01。

Do：逐约束从定义找到具体实现位置和真实观测；反向从实现检查未授权/额外行为与遗漏映射。重跑全部必需适用案例，核查测试器/错误变体、原始证据和版本；父节点必须检查真实组合、边界/错误传播与全局义务，不能只按孩子多数票通过。

Check：评价审查覆盖、误报/漏报控制与结论证据是否充分；同时单独记录被审查对象 subject_conformance（pass/fail/unknown）。执行缺失/不满足即fail；关键事实无法取得为unknown，不能假报完整审查。审查任务的verdict评价审查工作本身，不混淆两个维度。

Act：发布不可变审查包、约束/实现/证据矩阵、缺陷及影响；需要修复按REWORK-01派发原节点的执行或建模新attempt。审查任务不修改被审对象，也不把新测试期望偷偷写回冻结规范。

## 审查完整性与终止

每个必需节点均有当前release对应结论，父组合和根目标通过且必需覆盖无unknown/not_run/stale时可得整树subject_conformance=pass。工作索引再根据这些固定报告核对阻断缺陷关闭，才允许release_approved。审查任务交付报告不得等待自己将要支持的issue关闭；报告完成、对象符合、缺陷关闭和发布按VERDICT-01分层。父Agent不得代替孩子自己的任务确认。

审查任务内部Check不自动派生第四场景或审查的审查；需要额外独立复核时必须具名节点/场景/新attempt与明确风险，不通过通用递归模板无限创建任务。

## 输出

使用 `templates/conformance-review.md`；subject_node/tree/release、review_task_id、subject_conformance、任务verdict、每约束实现定位与真实证据、重跑run列表、组合结果、缺陷及未确定项必须可复核。报告发现实现错误而审查任务成功是允许且重要的正常路径。

## 3.3：审查复用与共享候选

当前目标审查检查固定definition_refs、有效契约、案例来源、局部delta、采用和当前可信公告，不默认采用库最新版本。对共享修订的独立审查检查候选最终manifest、base、变更类别和正反例区分力；不替发布者改写候选。审查报告正常完成与共享发布许可/跨树迁移完成分别记录。


## 从固定材料独立形成对应关系

先固定协议快照、被审源码/材料集合、业务定义与本次审查输入，不能用版本号、schema名、目录存在或完成报告代替逐成员字节。要求集从原目标/已确认定义独立展开，逐项记录实现和证据；反向检查额外成员/行为、版本漂移和被删除义务。报告的代码摘录也属于待核验材料，发现与模型不符必须报告差异，不能因标题写着“验证的数据结构”就采信。

每项结论写明声明一致性、布局、实现逻辑或实际行为范围；方法不能超出证据能力。结构大小/对齐需实际环境与数值；协议图需版本、模式、发送/接收方、方向和状态前置；阈值需单位、边界、配置与测量方式。缺源码/运行轨迹只报告未知及取证方案，不推断线上具体错误。

审查任务质量、subject_conformance、delivery_usable、release_approved分别按VERDICT-01判定。发现确定违例可令subject_conformance=fail，同时列其余unknown；资料不足而未发现确定违例时unknown。缺任务/确认/终态不能把维护审计升级成完整PDCA交付。缺陷需稳定ID、原位置、事实类型、影响、修复对象及关闭回归；误报以追加裁决更正，不抹掉首次判断。


## 真实记录的时点审查与可执行取证

先登记来源类别与当次声明采用的协议/对象版本。用户确认源自实际运行的records按真实案例处理；格式缺陷或导出缺项不改变来源类别。明确区分：已观察到的违例、现有材料不足以判定的事实、本案例不适用/未覆盖的行为。证据缺失先查生成、保存、导出和读取环节，不直接填not_run；新规范只用于新采用检查，不倒推历史违规。

对可机械判定的要求，verification_action应实际读取固定双方并输出具名差异；人工判定也保留材料边界、逐项观察及理由。先核对本次执行状态、输入摘要和方法范围，再核对结论。若声明26个成员却展示45个成员，不论报告自评如何，精确声明一致性均不能pass；其他源码行为仍按自身证据判断，不能据此猜哪份头文件是真实版本。

摘要/覆盖/完成报告从同一份已核验观察生成，任何独立填写的汇总都须反向核对。补充反例既检验检测器，也检验失败能否传到最终结论；不要只证明某个工具能发现差异，而让实际Check忽略其输出。

## 核验发现：先明确主张，再尝试反驳

本节用于审查任务Do中的具体发现核验；普通任务Check可用既有证据复核自己的判断。它不是第四场景，不自动派新Agent，也不授权Check新增范围外实验或修改被审业务对象；原REWORK允许的测试环境/夹具修复仍适用，不能改变冻结产物或oracle。没有发现仍须完成原必需审查覆盖。

1. **缩小主张。** 写明固定版本/位置、规则、触发条件及声称影响。区分表达内部矛盾、实现逻辑问题与已观察运行故障；不要从一种直接推断另一种。
2. **追到可达条件。** 核对入口、调用者、数据/状态流与执行环境。安全问题说明攻击者原有权限；并发/跨组件问题核对相关顺序、不变量和真实边界，不仅匹配危险语句。
3. **主动查反证。** 检查上游验证、锁/所有权、原子性、配置、错误处理或不可达前提是否足以阻止本例。列出检查过的位置和观察；“没有找到”不等于“保护不存在”。
4. **给有界结论。** 确认违例需充分的触发与违反判据证据；否定该发现需具体反证；不足为unknown并列取证方案。不把怀疑强制分成真/假，也不以风险名称推算已发生影响。
5. **消费而非堆积。** 将发现、反证和局限回链要求及subject_conformance。确定违例令对象fail，其余未知仍保留；没有确定违例且必需事实不足时unknown。否定一个发现不证明整个对象pass。

在现有issues/审查正文中记录：`稳定ID、事实范围、对象与位置、主张/触发、支持证据、反证及是否充分、判定理由、影响/未知、修复对象与关闭回归`。后续证据推翻早期判断时追加纠正，保留原观察。简单单组件线性核验即可；并发、跨模块或证据矛盾时加深追踪，仍受原合同与预算约束。需要范围外实验时走REWORK-01后继，不能静默扩权。

例：单看复制函数缺长度检查不能确认越界；需核对所有可达调用入口是否已限制长度。一个入口有检查不证明其他入口安全；无法取得另一入口时保留该路径unknown。
